`docs/platforms/javascript/common/configuration/releases.mdx:30-43` markets Release Health and links to Session APIs, and `docs/platforms/javascript/common/configuration/apis.mdx:922-941` documents `startSession` (`:927`), `endSession` (`:931`) and `captureSession` (`:935-941`). Neither file has `supported` or `notSupported` frontmatter, and the Sessions block carries no `PlatformSection` gate, so both render on the Cloudflare guide as if `Sentry.startSession()` were available there.

It is not. `packages/cloudflare/src/index.ts` exports none of the three, so importing them from `@sentry/cloudflare` yields `undefined`. The same file does export the `Session` type at `:12`, so editor autocomplete suggests sessions exist while the functions do not. Bun (`packages/bun/src/index.ts:33-35`) and Deno (`packages/deno/src/index.ts:87-89`) export all three, which is why the pages read correctly on those guides.

Gating is the change to make. The Cloudflare client does inherit the session plumbing — `packages/cloudflare/src/client.ts:24` extends `ServerRuntimeClient`, and core implements `captureSession` at `packages/core/src/client.ts:399` and `sendSession` at `:596` — but no Workers run in the audit exercised those functions through `@sentry/core`, so the page should not send readers down that path on the strength of the source alone.

What to change:

- Gate the Sessions section in `apis.mdx` and the Release Health block in `releases.mdx:30-43` away from `javascript.cloudflare`.
- If the sections stay ungated, state plainly on the Cloudflare rendering that `@sentry/cloudflare` exports none of `startSession`, `endSession` and `captureSession`.
- Say that the exported `Session` is a type only, so its presence in autocomplete does not mean the APIs are there.
