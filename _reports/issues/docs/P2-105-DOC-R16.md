`docs/platforms/javascript/guides/cloudflare/features/durableobject.mdx` documents two things: storage spans at `:33-37` and RPC trace propagation at `:39-41`. The intro at `:8` says the wrapper instruments Durable Objects but never lists which handlers produce telemetry, so a reader debugging a WebSocket or alarm workload has nothing to go on.

On develop, `packages/cloudflare/src/instrumentations/instrumentDurableObjectHandlers.ts:44-129` wraps five handlers by default: `fetch` (`:44`), `alarm` (`:66`), `webSocketMessage` (`:85`), `webSocketClose` (`:102`) and `webSocketError` (`:119`), each producing one span per invocation. The last four go through `wrapMethodWithSentry` with `origin: 'auto.faas.cloudflare.durable_object'` (`:78`, `:95`, `:112`, `:129`), and that origin is used both as the span's `sentry.origin` attribute and as the `mechanism.type` of exceptions the wrapper captures (`packages/cloudflare/src/wrapMethodWithSentry.ts:72-76` and `:168-176`). `fetch` runs through the request wrapper instead: its span is an `http.server` span with origin `auto.http.cloudflare`, while errors thrown inside it carry mechanism `auto.faas.cloudflare.durable_object` (`packages/cloudflare/src/wrapRequestHandlerWithInit.ts:30-33`). The WebSocket error handed to `webSocketError` is captured with its own mechanism, `auto.faas.cloudflare.durable_object_websocket` (`:135`).

The `alarm` span is an `op: function` span named `alarm` that starts a new trace carrying `sentry.previous_trace` and a span link back to the `setAlarm` span. Two neighbouring facts belong on the page as well: `stub.fetch()` produces no `http.client` span, and under the stream lifecycle the Durable Object request span is named `GET` with the URL as an attribute.

What to change:

- Add a section listing the instrumented handlers: `fetch`, `alarm`, `webSocketMessage`, `webSocketClose`, `webSocketError`.
- Say what each produces — one span per WebSocket message, one per close, one per alarm firing.
- Distinguish origin from mechanism: spans from the four non-`fetch` handlers carry `sentry.origin: auto.faas.cloudflare.durable_object`, and errors thrown in them arrive with `mechanism: auto.faas.cloudflare.durable_object`.
- Note the alarm's new trace and its link back to `setAlarm`, that `stub.fetch()` produces no `http.client` span, and that the request span is named `GET` with the URL as an attribute in stream mode.
