The tracing verification step at `index.mdx:444-470` tells the reader to create `src/routes/sentry-test.tsx`, throw from it and expect an issue, which never arrives on SolidStart 2. `guides/deno/index.mdx:1-18` covers only the Deno SDK, not a node-server Nitro build run under Deno.

Verified on SolidStart 2.0.2 with Nitro 3 beta, Vite 8 and `@sentry/solidstart` 10.67.0: install with npm and `--legacy-peer-deps`, and put `solidStart({ appRoot: './src' })`, `sentrySolidStart()` imported from `@sentry/solidstart/vite`, and `nitro({ serverDir: './server' })` in `vite.config.ts`. Initialise in a Nitro startup plugin (`server/plugins/sentry.ts`) that calls `Sentry.init()`; no `--import` preload and no instrument file are needed, because the Sentry Vite plugin bakes the library instrumentation into the bundle. Build with `NODE_ENV=production npx vite build` on Node — the plugin skips its instrumentation pass in development, and that pass is what produces the database spans — then run the `node-server` output with `PORT=<port> HOST=127.0.0.1 deno run -A .output/server/index.mjs` on Deno 2.9.0. For error capture, register a try/catch middleware as the first entry of the array form of `createMiddleware` and call `Sentry.captureException` there.

Works today:

- Incoming `sentry-trace`/`baggage` continuation.
- Database spans for `mysql2`, injected at build time by the Sentry Vite plugin.
- Logs.
- Errors from API routes, with the middleware above; errors thrown inside `'use server'` actions are already captured by the shipped `withServerActionInstrumentation` wrapper, mechanism `auto.function.solidstart`.
- Parameterized names, with `setHttpServerSpanRouteAttribute` from `@sentry/server-utils`: an `onBeforeResponse` middleware that rebuilds the pattern from `event.params` covers API routes, and a `useCurrentMatches()` call in the Router root covers SSR pages. Verified in both trace lifecycles.
- Outgoing `fetch()`, with `winterCGFetchIntegration()` from `@sentry/vercel-edge` in the Nitro startup plugin, gated on Deno so a Node build does not get duplicate spans. It bundles cleanly into the node-server output and is an extra install.

Known limits:

- Unhandled errors from API routes are not captured on their own: SolidStart answers 500 and no event is sent, on Deno and on Node alike, so the guide's own verification snippet reports nothing. The object form of `createMiddleware` cannot fix this, because neither of its lifecycles wraps the handler; the array form is required, with the existing `sentryBeforeResponseMiddleware()` spread in through a nested object-form call.
- The Nitro error hook cannot help either: SolidStart builds its own inner H3 instance whose default `onError` turns the throw into a 500, so `@sentry/nitro`'s `error` hook never fires and adding `@sentry/nitro` as a module changes nothing.
- The SDK does not name server transactions: SolidStart mounts one catch-all Nitro route, so without the middleware above names arrive as the raw path with source `url`. `setHttpServerSpanRouteAttribute` is not re-exported from `@sentry/solidstart`, so the app has to depend on `@sentry/server-utils` directly, and only the segment span is renamed; the inner non-segment `http.server` spans stay `GET` under the stream lifecycle.
- Scope data set during one request is inherited by later requests in the process: the first `setTag` lands on the shared default isolation scope. Node with the same build is clean. The mechanism was not established for this stack.
- Outgoing `fetch()` is not instrumented without the integration above; `node:http`/`node:https` clients produce `http.client` spans with headers on Deno either way.
