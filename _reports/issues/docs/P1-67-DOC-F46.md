The combination is documented. `docs/platforms/javascript/guides/cloudflare/frameworks/sveltekit.mdx:1-9` is a "SvelteKit on Cloudflare" page that renders the shared include; the Cloudflare branch is `platform-includes/getting-started-complete/javascript.sveltekit.mdx:299-347`, with the `sequence(initCloudflareSentryHandle({...}), sentryHandle())` snippet at `:310-343`, `handleErrorWithSentry` at `:340-342`, "Configure Vite" at `:351-376` with `sentrySvelteKit()` at `:369`, and the wrangler config at `:378-387`. Two things the run needed are absent: `grep -rn noExternal docs/platforms/javascript platform-includes` returns zero hits, and no page describes how the segment span is named on Cloudflare.

Verified on the develop line: SvelteKit 2.70 with `@sveltejs/adapter-cloudflare` 5, `compatibility_date: "2026-05-01"`, `compatibility_flags: ["nodejs_compat"]`, `sentrySvelteKit()` from `@sentry/sveltekit/vite` before `sveltekit()`, and `src/hooks.server.ts` exactly as the include shows. `vite build`, then `wrangler dev`.

Works today:

- Unhandled errors through `handleErrorWithSentry` (mechanism `auto.function.sveltekit.handle_error`), per-request isolation, incoming trace continuation, outgoing `fetch` spans with propagation headers, `Sentry.logger` logs.
- `db` spans from the build-time transform `sentrySvelteKit()` already installs, with no extra configuration on a pnpm install.

Known limits:

- The transaction/segment span is named from the raw URL under `traceLifecycle: 'static'` and by HTTP method alone under the default `'stream'`; the SvelteKit route id and `http.route` only reach a child span. This hits every route except `/`, not just parameterized ones, because the Cloudflare wrapper keeps only a name whose source is already `route`.
- SvelteKit's native tracing (`kit.experimental.tracing.server`) makes this worse rather than better: on Cloudflare it removes the route-named `http.server` span entirely, leaving the route only as an attribute on a `function` span.
- On a flat `node_modules` (npm or Yarn) the build fails until `ssr: { noExternal: ['@sentry/core', '@sentry/conventions', '@opentelemetry/api'] }` is added to `vite.config.js`.

What to change on `docs/platforms/javascript/guides/cloudflare/frameworks/sveltekit.mdx`:

- Keep the include and add a "Route Names on Cloudflare Workers" section stating the naming limit above and showing the verified fix: one user-land `handle` inserted between `initCloudflareSentryHandle` and `sentryHandle` in the `sequence`, which takes `getRootSpan(getActiveSpan())` from `@sentry/sveltekit`, calls `updateName` on it with ``${event.request.method} ${event.route.id}`` and sets `sentry.segment.name.source` to `route` plus `http.route`. Use `updateName` and the source attribute, not `Sentry.updateSpanName`, which stamps the source `custom`. It works in both trace lifecycles.
- Add a "Database Spans" section stating that no extra setup is needed on pnpm and giving the `ssr.noExternal` entry for npm and Yarn installs.
