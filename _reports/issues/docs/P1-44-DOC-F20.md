Nothing covers this combination: `grep -rni express docs/platforms/javascript/guides/deno/` and `grep -rni deno docs/platforms/javascript/guides/express/` both return zero hits. `docs/platforms/javascript/guides/express/index.mdx:4-5` declares `sdk: sentry.javascript.node` with `fallbackGuide: javascript.node`, and `:12` is a bare `<PlatformContent includePath="getting-started-node" />`, so the whole guide assumes `@sentry/node` on Node. `docs/platforms/javascript/guides/deno/index.mdx:1-230` names no framework.

Verified on Express 5.2.1 and Deno 2.9.0 in two shapes. Both start the same way: `npm install express@5 mysql@2` plus `@sentry/deno` into a real on-disk `node_modules`, and a `deno.json` with `{"nodeModulesDir": "manual"}`; the app runs with `deno run --allow-net --allow-env --allow-read --allow-sys app.ts`. Shape A is the plain one: an `instrument.ts` that calls `Sentry.init({ dsn, tracesSampleRate: 1.0 })` from `@sentry/deno` and is the first import of the app file. Shape B adds library instrumentation: the same file starts with `import "@sentry/deno/import";`, then imports a six-line JSON load hook, then inits. The load hook is `Module.registerHooks({ load(url, context, nextLoad) { const result = nextLoad(url, context); if (url.endsWith(".json") && result.format !== "json") result.format = "json"; return result; } })` from `node:module`, registered after the Sentry hook; without it Express never imports. No `integrations` entry is needed in either shape, because `expressIntegration()` is already in the Deno SDK's default set.

Works today:

- Both shapes: incoming requests produce `http.server` transactions, and `Sentry.logger` logs arrive.
- Shape B: parameterized names `GET /users/:id` with source `route`, plus a `handler /users/:id` child span.
- Shape B: unhandled route errors as events with mechanism `auto.http.express` and `transaction: "GET /error"`; Express still answers 500.
- Shape B: database spans for a module-scope `mysql@2` connection, as a child of the handler span.
- Shape B: per-request isolation across concurrent requests with distinct trace ids, and incoming `sentry-trace`/`baggage` continuation. Both were measured on this shape only.
- Shape A error capture, with `setupExpressErrorHandler(app)` imported from `@sentry/server-utils`: route errors arrive with mechanism `auto.middleware.express`.
- Outgoing `fetch()`, with `fetchIntegration()` imported from `@sentry/cloudflare` and passed to `Sentry.init`: `http.client` spans with origin `auto.http.fetch` parented under the handler span, and `sentry-trace`/`baggage` on the wire, in both trace lifecycles. It means installing `@sentry/cloudflare` in a Deno app.

Known limits:

- Shape A names transactions `GET /users/42` with source `url` and produces no handler spans and no database spans.
- Shape A captures nothing for a thrown route error unless `setupExpressErrorHandler` is added: Express's default error handler swallows the throw and the SDK prints no warning, so the 500 is invisible in Sentry.
- `setupExpressErrorHandler` has to come from `@sentry/server-utils`; `@sentry/deno` does not re-export it.
- `import "@sentry/deno/import"` needs the companion JSON load hook because of denoland/deno#36240: with any module load hook registered, `require('*.json')` compiles as JavaScript, and Express dies at import time on `require('./codes.json')` inside `statuses`.
- Outgoing `fetch()` is not instrumented by default in either shape: the Deno SDK's default integrations trace only `node:http`/`node:https`, so without the integration above a handler's `fetch()` gets no span and sends no trace headers.

What to change:

- Add `docs/platforms/javascript/guides/deno/frameworks/express.mdx` with the install, `deno.json`, both init shapes including the JSON load hook, the run command and the capability split above.
- Add a shared "Outgoing fetch requests" note to `guides/deno/index.mdx`.
