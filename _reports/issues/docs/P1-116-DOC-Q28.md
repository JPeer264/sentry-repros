`common/install/esm-without-import.mdx:28-30` says that with a direct first-line import only native Node.js APIs can be instrumented and the SDK will not capture framework-specific data. Observed on develop: `import "./instrument.mjs"` as the first line of the Express app produced exactly the `--import` output, with middleware and handler spans, route-named segments (`GET /users/:id`, source `route`) and `auto.http.express` error events; the Node run's Express check saw the same, and the Fastify run got the same hook and handler spans and `auto.function.fastify` events from a first-line import (QS-fastify, variant self-import). Koa is the counter-example: its first-line import produced url-named `GET` segments and no router or middleware span (QS-koa, variant self-import), so the page should name what is covered and what is not instead of a blanket warning. Hapi behaves like Fastify: the first-line import produced the same items as `--import`, every Hapi span, route name and error (QS-hapi, variant self-import). Hono too: `sentry(app)` patches the app instance at registration time, and the first-line import produced the same route-named segments, middleware spans and errors as `--import` (QS-hono, variant self-import).

What to change:

- Turn the page into the bundler-plus-top-level-import method the SDK team settled on 2026-09-09 (DOC-Q85): say that a plain first-line import instruments only what registers at runtime (measured: Express, Fastify, Hapi and Hono yes, Koa no), show `import "./instrument.mjs"; await import("./app.mjs");` as the bundler-free way to keep the init ahead of the framework, and name the bundler plugin as the way to instrument everything without `--import`; the NestJS copy of the page, `guides/nestjs/install/esm-without-import.mdx:18-20`, needs the same qualification, since the guide's default CommonJS build gets full Nest and Express spans from a first-line import (QS-nestjs, variant cjs).
