Verified on the develop line: Nuxt 4.2 with the `cloudflare_module` preset, `compatibility_date: "2026-05-01"`, `compatibility_flags: ["nodejs_compat"]`, and `server/plugins/sentry.ts` registering `sentryCloudflareNitroPlugin` from `@sentry/nuxt/module/plugins`. Six of seven capabilities worked with that wiring, with no bundler plugin and no extra Sentry step, but two `nuxt.config.ts` settings that no page mentions were needed to get there: `nitro.cloudflare: { nodeCompat: true, deployConfig: false }`, and `nitro.alias: { 'readable-stream': 'node:stream' }` for the bundled `mysql` driver to boot under unenv. Install only `@sentry/nuxt` and `@sentry/cloudflare`: adding `@sentry/nitro` pulls `nitro@3` in next to Nuxt 4's nitropack. Verification has to run on a build, since the SDK is inert under `nuxt dev` (orchestrion is skipped in dev and there is no workerd): `nuxt build`, then `wrangler dev`.

Works today:

- Unhandled server route errors through Nitro's error hook, parameterized route names for routes such as `server/api/users/[id].ts` (`GET /api/users/:id`, source `route`, with `http.route`), per-request isolation, incoming trace continuation, outgoing `fetch` spans with propagation headers, `db` spans with no manual bundler step, `Sentry.logger` logs.

Known limits:

- A server route with no parameters gets no `http.route` attribute, so its span is named by HTTP method alone under the default `traceLifecycle: 'stream'` and from the request URL, with source `url`, under `'static'`. Parameterized routes such as `server/api/users/[id].ts` are unaffected.
- Nothing is reported under `nuxt dev` at all; the instrumentation exists only in a built Worker.
