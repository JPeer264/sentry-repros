Nothing documents this combination in either direction. `grep -rn -i cloudflare docs/platforms/javascript/guides/solidstart/` returns zero hits across `index.mdx`, `install/`, `features/` and `profiling/`. `docs/platforms/javascript/guides/cloudflare/frameworks/` has no `solidstart.mdx` and the framework list at `docs/platforms/javascript/guides/cloudflare/index.mdx:16-23` omits SolidStart. The generic Workers entry pattern the run relied on is documented only at `guides/cloudflare/index.mdx:111`, with no SolidStart context.

Verified on the develop line: SolidStart 1.3 with the `cloudflare-module` Nitro preset, `compatibility_date: "2026-05-01"`, `compatibility_flags: ["nodejs_compat"]`. `@sentry/solidstart` itself does not run on Workers, so keep it for the browser and wire the server side by hand: set `server: { preset: 'cloudflare-module', rollupConfig: { external: ['@sentry/cloudflare'] } }` in `app.config.ts` so Nitro does not inline a second SDK copy, then write a `worker.mjs` that wraps the built Nitro handler with `Sentry.withSentry()` from `@sentry/cloudflare` and point wrangler's `main` at that wrapper. Add a Nitro server plugin registered through `server.plugins` that forwards Nitro's `error` hook to `Sentry.captureException`, otherwise thrown server errors never become events. Nitro emits no wrangler config for the `cloudflare-module` preset, so write `wrangler.jsonc` by hand: `main` pointing at the wrapper, plus an assets entry for `.output/public` with its `ASSETS` binding. Do not skip `rollupConfig.external`: without it Nitro inlines a second `@sentry/cloudflare`, and the failure is silent rather than loud, because `Sentry.setTag` and `Sentry.captureException` in a route handler then run against an uninitialised client while the wrapper's request transactions keep arriving and make the setup look healthy.

Works today:

- Server errors through the Nitro error hook, per-request isolation, incoming trace continuation, outgoing `fetch` spans with propagation headers, `Sentry.logger` logs, and browser errors with `Sentry.init` from `@sentry/solidstart` in `src/entry-client.tsx`.

Known limits:

- Server transactions never carry the file-route pattern: under `traceLifecycle: 'static'` the name is the raw request URL with source `url`, and under the default `'stream'` the path is gone altogether and the span is named bare `GET`. There is no Sentry SolidStart router integration on this runtime.
- Errors thrown while a page renders on the server stay uncaptured even with the Nitro error plugin, because SolidStart streams the render through a detached pipe.
- There is no server-to-client trace continuation: nothing injects a `sentry-trace` meta tag into the SSR HTML.
- Database spans were not exercised, and no Sentry database instrumentation path exists for this vinxi/Nitro/rollup build shape.
