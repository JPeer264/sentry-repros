## 15. Correct the Bun integrations table in platform-includes/.../javascript.bun.mdx

**Audit item:** DOC-B2 · **Type:** docs-change · **Finding:** The Bun integrations table lists three integrations that are not installed and omits eleven that are

`platform-includes/configuration/integrations/javascript.bun.mdx:5-37` lists `dedupeIntegration` (`:9`), `nativeNodeFetchIntegration` (`:24`) and `inboundFiltersIntegration` (`:14`) as auto-enabled, and `pinoIntegration` at `:47`, while `fsIntegration` is shown for Bun with no row.

What was observed: the Bun SDK installs 42 integrations. It ships `fetchIntegration` rather than `nativeNodeFetchIntegration`, installs inbound filtering as `EventFilters`, and does not install `dedupeIntegration`. The channel-based integrations only produce spans after a `Bun.build` with `@sentry/bun/plugin`.

What to change:

- Drop the `dedupeIntegration` row; rename `nativeNodeFetchIntegration` to `fetchIntegration`; rename `inboundFiltersIntegration` to the installed `eventFiltersIntegration`.
- Add rows for the eleven installed integrations listed above.
- Add a "Requires `@sentry/bun/plugin`" column and tick it for the channel-based rows.
- Fix the gating so `common/configuration/integrations/pino.mdx` is shown for Bun, and give `fsIntegration` a row or hide it.

- Add an "Enable library instrumentation" step to `guides/deno/index.mdx` with first-line `import '@sentry/deno/import';` as the primary form and `nodeModulesDir: "auto"` in `deno.json`.
- Show the file-path `--import` flag as the alternative; do not show the bare specifier form.
- State that dependencies which `require()` a JSON file fail to import under the hook.
- State which instrumentation works without the hook.

## 19. Show one complete deno run command with all four permission flags in the Deno guide

**Audit item:** DOC-D3 · **Type:** docs-change · **Finding:** The permission section is incomplete and the two commands are shown as alternatives

`guides/deno/index.mdx:106` shows `deno run --allow-net=<ingest> index.ts` and `:125` shows `deno run --allow-read=./src index.ts` as two separate commands, while the init snippets on the same page name the file `main.ts`. Neither `--allow-env` nor `--allow-sys` is mentioned, and `packages/deno/README.md` mentions no flag at all.

What was observed on deno 2.9.0: with only `--allow-net` and `--no-prompt`, events carry `server_name: null`, no OS version, an absolute filesystem path as the frame filename and no context lines. With the `@sentry/deno/import` hook line present, the same flags do not degrade but crash: `NotCapable: Requires env access, run again with the --allow-env flag`, raised from the vendored `debug` package inside `@sentry/server-runtime-injection` at module load (getting-started reproduction QS-deno, 2026-09-08). With all permissions granted, the same app reports the hostname, the OS version, an `app:///`-prefixed filename and context lines. No warning is printed in the restricted run. Every Deno e2e app runs with `--allow-net --allow-env --allow-read`, and the docker-backed ones add `--allow-sys`.

What to change:

- Replace the two commands at `:106` and `:125` with a single `deno run --allow-net=<ingest> --allow-read --allow-env --allow-sys main.ts`, using the same filename as the init snippets.
- Add a table naming what each flag unlocks: `--allow-net` event delivery, `--allow-read` source context lines and app-relative frame paths, `--allow-env` `SENTRY_*` lookups and `serverName`, `--allow-sys` hostname and OS version.
- Add the same table to `packages/deno/README.md`.
