## 1. Fix the tracing verify snippet on the browser getting-started page: await inside a non-async function

**Audit item:** DOC-Q7 · **Type:** docs-change · **Finding:** The browser tracing verify snippet is a syntax error

`platform-includes/getting-started-verify/javascript.mdx:53-68` tells the reader to update the button handler so that it starts a span around a simulated longer operation, and shows `function triggerError() { await Sentry.startSpan(...) }`. The function is not `async`.

Observed with the snippet copied verbatim into a page: Chrome reports `Uncaught SyntaxError: await is only valid in async functions and the top level bodies of modules`, discards the whole script block, and the "Break the World" button next to it throws `ReferenceError`. With `async function triggerError()` the same page produces the span (`test Example Frontend Span`) inside the pageload span envelope.

What to change:

- Make the handler `async function triggerError()` in the snippet, and keep the button call as it is.
- Say what arrives: one span envelope with the pageload segment and the manual span as a child, no transaction envelope, because the default lifecycle is stream (DOC-Q1).

## 2. Fix the React Router v6 and v7 page snippets that fail on React 19

**Audit item:** DOC-Q12 · **Type:** docs-change · **Finding:** Three React Router page snippets do not run on React 19

Three snippets on the React Router pages fail when copied verbatim into a React 19 app. The declarative-mode snippet at `guides/react/features/react-router/v7.mdx:71-108` renders with `ReactDOM.render` (`:101`), which react-dom 19 no longer exports: `TypeError: import_react_dom.default.render is not a function` at boot, nothing renders, and the SDK reports its own docs page crash. The same call sits at `v6.mdx:94`, `v6.mdx:150` and `v7.mdx:155`.

The `useRoutes` snippet at `v7.mdx:122-160` imports `wrapUseRoutes` (`:131`) but calls `wrapUseRoutesV7` (`:147`), and uses `Sentry`, `ReactDOM` and `BrowserRouter` without importing them: `ReferenceError: Sentry is not defined`, the SDK never initializes and zero envelopes arrive. `v6.mdx:117-155` has the same mismatch.

The custom `errorElement` snippet at `v7.mdx:239-255` is a `jsx` block that contains the TypeScript cast `useRouteError() as Error` (`:244`) and imports from `react-router-dom` (`:240`) while the page installs `react-router`: esbuild stops with `Expected ";" but found "as"` and an unresolved import. The same cast is at `v8.mdx:246` and `v6.mdx:239`.

With the three defects fixed, the page's wiring works: pageload and navigation segments named `/users/:userId` with source `route`, and the `errorElement` boundary captures the route render error.

What to change:

- Render with `ReactDOM.createRoot(document.getElementById("root")).render(...)`, as `v8.mdx:104` already does, in all four places.
- In the `useRoutes` snippets import `* as Sentry from "@sentry/react"`, call `Sentry.wrapUseRoutesV7` (or `Sentry.wrapUseRoutes`), and import `BrowserRouter` and `ReactDOM`.
- Drop the cast or tag the block `tsx`, and import `useRouteError` from the package the page installs.

## 5. Fix the extensionless instrument import on the Express, Fastify, Koa, Hapi and Connect guides and the esm-without-import page

**Audit item:** DOC-Q25 · **Type:** docs-change · **Finding:** The Express, Fastify, Koa, Hapi and Connect guides' ESM tabs import the instrument file without its extension

`platform-includes/getting-started-use/javascript.express.mdx:22` starts the ESM app with `import "./instrument";`, while the config step creates `instrument.mjs`. Node ESM does not probe extensions: the app never starts, `Error [ERR_MODULE_NOT_FOUND]: Cannot find module .../instrument ... Did you mean to import "./instrument.js"?`. With `import "./instrument.mjs"` the same app produces exactly the `--import` output. The same extensionless import sits at `common/install/esm-without-import.mdx:55`, and the orphaned `platform-includes/getting-started-add-top-level-import/javascript.express.mdx` imports `./instrument.js`. The Fastify tab has the same defect at `platform-includes/getting-started-use/javascript.fastify.mdx:20`, with the same `ERR_MODULE_NOT_FOUND` (QS-fastify, variant esm-tab), and so does the Koa tab at `getting-started-use/javascript.koa.mdx:20`; on Koa the corrected first-line import starts the app but loses every router and middleware span and the route names, so the Koa tab should rely on the `node --import` command instead (QS-koa, variants esm-tab and self-import). The Hapi tab at `getting-started-use/javascript.hapi.mdx:28` fails the same way, and its corrected first-line import loses nothing (QS-hapi, variants esm-tab and self-import), and so does the Connect tab at `getting-started-use/javascript.connect.mdx:20` (QS-connect, variant esm-tab). The NestJS guide has its own page, `guides/nestjs/install/esm-without-import.mdx:41-51`, whose `main.ts` imports `./instrument` without extension and does not start as ESM either (QS-nestjs, variant esm-verbatim).

What to change:

- Import `./instrument.mjs` in the Express, Fastify, Hapi and Connect ESM tabs, drop the import from the Koa tab in favour of `--import`, matching the file the config step creates, and fix `esm-without-import.mdx:55` the same way.
