Nothing under `docs/platforms/javascript/guides/solidstart/` mentions Bun. `solidstart/index.mdx:5-8` gives only `categories: [browser, server]`, `solidstart/index.mdx:277` tells you to add an `--import` flag to `NODE_OPTIONS`, and the two start scripts at `solidstart/index.mdx:297-298` are `start:vinxi` with `NODE_OPTIONS` and `start:node` with `node --import ./.output/server/instrument.server.mjs .output/server/index.mjs`; `solidstart/install/cli-import.mdx:33,45` repeats them. The whole guide targets SolidStart 1 (`app.config.ts` with `withSentry`, `NODE_OPTIONS` and `vinxi`); `sentrySolidStart` appears in the docs only in the v8-to-v9 migration note about the removed `sentrySolidStartVite` plugin. A SolidStart 2 page is therefore needed for every runtime, not only Bun.

Verified on SolidStart 2 (`@solidjs/start` 2.0.2, Nitro 3) with `@sentry/solidstart` 10.67.0 (develop, 6f2da7483d) on Bun 1.4.0: in `vite.config.ts` use `sentrySolidStart({ sourcemaps: { disable: true } })` from `@sentry/solidstart/vite` alongside `solidStart({ appRoot: './src', middleware: './src/middleware.ts' })` and `nitro({ serverDir: './server' })` — the last is what makes `server/plugins/sentry.ts` load at all. Put `Sentry.init` inside that Nitro plugin, add `sentryBeforeResponseMiddleware()` in `src/middleware.ts`, run `vite build`, then `bun .output/server/index.mjs`. Install `@sentry/nitro` alongside `@sentry/solidstart` and `@sentry/bun`, with `npm install --legacy-peer-deps`: `@sentry/nitro` 10.67.0 pins a nitro range that the 3.0 beta cannot satisfy. Add `bunHttpServerIntegration()` and `fetchIntegration()` from `@sentry/bun` to `integrations`, guarding the fetch one on `typeof Bun !== 'undefined'` so a Node deployment of the same build does not get two spans; the two integrations were probed in separate follow-up runs and never together in one run. Database spans need a workaround for a Bun bug: Bun garbage-collects the SDK's `diagnostics_channel` subscriptions, so pin the channels on `globalThis` after `Sentry.init()` in `server/plugins/sentry.ts` — `globalThis.__sentryPinnedChannels = ['mysql2:query', 'mysql2:execute', 'mysql2:connect', 'mysql2:pool:connect', 'orchestrion:mysql:query'].map(n => dc.tracingChannel(n))` — or use an equivalent `bun --preload pin.mjs` file if the Nitro plugin cannot be touched.

Works today:

- Per-request isolation, one scope and one trace per request
- Incoming `sentry-trace`/`baggage` continuation
- Outgoing `fetch` spans with propagation headers
- `mysql2` 3.20.0+ and `mysql` v2 database spans alike, once the tracing channels are pinned. No build step and no driver import order is required; every channel-based integration on Bun is exposed to the same bug, not only databases
- `Sentry.logger` log envelopes
- Errors from server functions wrapped in `withServerActionInstrumentation`, and errors thrown in a file API route once the h3 middleware below is added. The recorded verdict for errors is partial: page-render errors stay dark either way

Known limits:

- Errors thrown while a page component renders on the server are not reported, on Bun and on Node alike. File API route errors are reported only if `src/middleware.ts` wraps `next()` in a `try`/`catch` that calls `Sentry.captureException(error, { mechanism: { handled: false, type: 'solidstart.middleware' } })` and re-throws — `createMiddleware` accepts a raw h3 middleware array on SolidStart 2, so this composes with `sentryBeforeResponseMiddleware()`. The guide's own Verify step at `solidstart/index.mdx:444-453`, a `sentry-test.tsx` route throwing from `GET`, is exactly the case that produces no event without it.
- Server transactions are named from the raw URL (`GET /users/456`, source `url`) rather than the route pattern, on Bun and on Node alike, and under the `stream` default the segment collapses further to a bare `GET`. App code can fix the name: call `getRootSpan(getActiveSpan()).updateName(...)` and set `http.route` and `sentry.segment.name.source`, verified on both runtimes and both lifecycles.
- `bunHttpServerIntegration({ spans: false })` also isolates requests and continues traces but drops the `node:http` server span; the default is the parity choice. The `NITRO_PRESET=bun` plus `bunServerIntegration()` path was tried and rejected.
- `@sentry/bun` adds roughly 2.4 MB to the server bundle.
- `contexts.runtime.name` is `node` under Bun.

What to change:

- New page `docs/platforms/javascript/guides/bun/frameworks/solidstart.mdx` with the `bun .output/server/index.mjs` start command, the full SolidStart 2 Vite config, the two `@sentry/bun` integrations with the runtime guard, the channel pin and the capability list.
- Add the route-naming workaround and the unreported-error notes to `guides/solidstart/index.mdx`, and correct the Verify step at `:444-453`, which currently demonstrates the one case that sends nothing.
- `guides/solidstart/` needs a SolidStart 2 setup for every runtime: the documented `app.config.ts` plus `withSentry` plus `vinxi` shape does not apply, and `sentrySolidStart` is otherwise undocumented.
