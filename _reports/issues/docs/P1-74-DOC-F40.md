Nothing documents Hapi on Workers. `docs/platforms/javascript/guides/hapi/index.mdx:4-5` sets `sdk: sentry.javascript.node` with `fallbackGuide: javascript.node` and its whole body is one include at `:12`. `docs/platforms/javascript/guides/cloudflare/frameworks/` holds no `hapi.mdx` and the framework list at `guides/cloudflare/index.mdx:16-23` omits Hapi. Separately, `packages/server-utils/package.json:30-62` exports seven orchestrion entry points (`./orchestrion/config` plus six bundler entries: vite, rollup, webpack, webpack-loader, esbuild and bun), and the only mention of any of them in the docs is one line of the v10-to-v11 migration guide at `common/migration/v10-to-v11/index.mdx:1297`; no how-to page explains them.

Verified on the develop line: `@hapi/hapi` 21 on workerd with `compatibility_date: "2026-05-01"` and `compatibility_flags: ["nodejs_compat", "enable_nodejs_http_server_modules"]`, served through `httpServerHandler` from `cloudflare:node` and wrapped with `Sentry.withSentry()` from `@sentry/cloudflare`. Build-time instrumentation is what makes the framework visible, by either of two public routes: `sentryCloudflareVitePlugin()` from `@sentry/cloudflare/vite` in a Vite build, or `sentryOrchestrionPlugin()` from `@sentry/server-utils/orchestrion/esbuild` when you pre-bundle the Worker yourself and point wrangler's `main` at the output (an esbuild banner that backs `require` with statically imported `node:` builtins is needed, or workerd fails at startup on `node:async_hooks`). With build-time instrumentation on, register routes and call `server.start()` inside the first `fetch`, never at module scope: the injected wrapper around `Server.prototype.route` starts a span, and the isolate then fails to boot with "Disallowed operation called within global scope". `hapiIntegration()` is not in the Cloudflare default integrations and is not re-exported by `@sentry/cloudflare`, so add it by hand from `@sentry/server-utils`.

Works today:

- Parameterized transaction names (`GET /users/{id}`, source `route`) with nested router and extension spans, per-request isolation, incoming trace continuation, outgoing `fetch` spans with propagation headers, `db` spans from a `mysql` query, `Sentry.logger` logs, all on a build-time-instrumented bundle.
- Route handler errors, after adding an `onRequest` extension that drops the premature `close` event: `server.ext('onRequest', (request, h) => { const res = request.raw.res; const on = res.on.bind(res); res.on = (e, l) => (e === 'close' ? res : on(e, l)); return h.continue; })`. With that in place `hapiIntegration()` captures the throw itself, with the transaction name and mechanism `auto.function.hapi`.
- On a plain `wrangler` build, parameterized names from a four-line `onPreResponse` extension: `Sentry.updateSpanName(root, `${request.method.toUpperCase()} ${request.route.path}`)` plus `root.setAttribute(Sentry.SENTRY_SEGMENT_NAME_SOURCE, 'route')` on `Sentry.getRootSpan(Sentry.getActiveSpan())`, all exports of `@sentry/cloudflare`.

Known limits:

- Without the `onRequest` fix, nothing is captured: on workerd the `node:http` `ServerResponse` emits `close` before `finish` with `writableEnded` still false, hapi reads that as a client disconnect, answers 499 and never fires its `request`/`error` event. A `server.ext('onPreResponse')` that calls `Sentry.captureException` when `request.response.isBoom` is the fallback on builds without the instrumentation.
- A plain `wrangler` build emits no database spans and no router or extension spans, and names the transaction from the raw URL unless you add the `onPreResponse` rename; wrangler's own bundler takes no plugins.
- `mysql` 2.x works unchanged; `mysql2` needs `disableEval: true` in the connection options.
