`docs/platforms/javascript/guides/nuxt/features/nitro-deployment-presets.mdx:7` claims that the SDK supports different Nitro deployment presets, "most of which work out of the box", and the 11-line file then documents only Cloudflare Pages at `:9-11`. The Nuxt guide has no Deno mention anywhere, so a reader picking the `deno_server` preset gets no warning. `guides/nuxt/install/cli-import.mdx:37` gives the start command as `node --import ...`, which has no Deno equivalent.

Verified on Nuxt 4.5.2 with `@sentry/nuxt` 10.67.0 and Deno 2.9.0: do not set a Nitro preset. Build the default `node-server` output with `npx nuxt build`, keep `sentry: { autoInjectServerSentry: 'top-level-import' }` in `nuxt.config.ts` and a root `sentry.server.config.ts` that calls `Sentry.init()`, then run the output under Deno with `cd .output/server && PORT=<port> deno run --allow-net --allow-read --allow-write --allow-env --allow-sys --allow-ffi --unstable-byonm ./index.mjs`. Nitro's node-server entry uses `node:http`, which the SDK instruments on Deno, and the module injects the config import into the entry correctly with this preset. For database drivers add `nitro: { externals: { inline: ['generate-function', 'named-placeholders'] } }`. For outgoing requests, add `winterCGFetchIntegration()` from `@sentry/vercel-edge` to `Sentry.init`.

Works today:

- Errors from nitro route handlers, with request data and source context.
- Parameterized `GET /api/users/:id` with source `route`, in both trace lifecycles, and `getActiveSpan()` defined inside handlers. A control run of the same output under Node produced the same shape.
- Database spans for `mysql2`, with the `externals.inline` entry above; on the node-server output they attach to ordinary route handlers with no code change.
- `http.client` spans and `sentry-trace`/`baggage` on `fetch` and nitro's `$fetch`, with `winterCGFetchIntegration()`. It was measured on the `deno_server` build under the default `stream` lifecycle, and `@sentry/vercel-edge` is an extra package to install.
- Logs.

Known limits:

- With `nitro: { preset: 'deno_server' }` there is no request instrumentation at all: no `http.server` spans, `getActiveSpan()` is undefined in handlers, every request shares one isolation scope and one trace id so tags and users leak, and incoming trace headers are ignored.
- With `deno_server` and `autoInjectServerSentry: 'top-level-import'`, the module writes the config import into a file literally named `.output/server/deno.json start` instead of the entry, so the wrapper entry that imports `./sentry.server.config.mjs` before `./index.mjs` has to be written by hand.
- Under `deno_server` with `traceLifecycle: 'static'`, an outgoing `fetch` outside an explicit `Sentry.startSpan` is dropped with `no_parent_span`, because there is no server span to parent it to.
- Outgoing `fetch` is not instrumented on Deno without the integration above.
- Route-name enrichment does not run on error responses, on Deno and on Node alike: a thrown handler reports `GET /api/users/boom` with source `url`.
- The runtime debug line "Bundler plugin ran, injected libraries=[]" does not mean instrumentation is missing; that list is only filled during the build.
- Per-request isolation and incoming trace continuation were measured only on the `deno_server` build, where they fail. They are not yet measured on the node-server output.

What to change:

- `guides/nuxt/features/nitro-deployment-presets.mdx:7`: qualify the "work out of the box" claim; add a Deno section next to Cloudflare Pages at `:9` with the run command and the `deno_server` warning.
- `guides/nuxt/install/cli-import.mdx:37`: the `node --import` start command has no Deno equivalent; give the `deno run` form for the node-server output.
- Cross-link a Deno framework page for Nuxt.
