`docs/platforms/javascript/guides/cloudflare/frameworks/remix.mdx` is 60 lines and does not describe a working Workers setup: `:39-49` installs only `@sentry/remix` with no `@sentry/cloudflare`, and `:55-58` embeds the shared include. In that include, the Cloudflare branch at `platform-includes/getting-started-complete/javascript.remix.mdx:250-294` covers Cloudflare Pages only, and the "Capture Server-Side Errors" step at `:296-329` sits outside any PlatformSection and tells every reader to import from bare `@sentry/remix` at `:314`. Verified on the develop line: Remix v2 (2.17.5) with the Remix Vite plugin on workerd, `compatibility_date: "2026-05-01"`, `compatibility_flags: ["nodejs_compat"]`. Install `@sentry/remix` and `@sentry/cloudflare`; npm needs `--legacy-peer-deps`, because `@remix-run/cloudflare` pins `@cloudflare/workers-types` `^4` while wrangler 4 pins `^5`. In `app/entry.server.tsx`, `export const handleError = sentryHandleError` imported from `@sentry/remix/cloudflare`. In the worker entry, `Sentry.withSentry()` from `@sentry/cloudflare` around a handler built with `createRequestHandler(instrumentBuild(remixBuild))`; do not reach for `makeWrappedCreateRequestHandler` from `@sentry/remix/cloudflare` as well, which on Cloudflare reports every request twice, as two `http.server` transactions in two different traces. In `vite.config.ts`, `sentryCloudflareVitePlugin()` from `@sentry/cloudflare/vite` at its defaults alongside the Remix plugin, with `ssr: { target: 'webworker', noExternal: ['mysql', /^@sentry\//, '@opentelemetry/api'] }` (`noExternal: true` is the blunt version of the same thing). Build with `remix vite:build`: a plain `vite build` under Vite 6 silently builds only the client and skips `build/server`.

This item prescribes `sentryCloudflareVitePlugin()` because that is what was run. The Remix Vite plugin's own Cloudflare behavior, `sentryRemixVitePlugin` from `@sentry/remix/vite`, which on the v11 line applies the build-time instrumentation transform itself, was not exercised in this audit.

Works today:

- Loader, action and resource-route errors, parameterized route names with `http.route`, incoming trace continuation, outgoing `fetch` spans with propagation headers, `db` spans from `mysql`, `Sentry.logger` logs.
- Per-request isolation, with the `withSentry` plus `instrumentBuild` entry above.

Known limits:

- Importing from bare `@sentry/remix` in a `webworker` SSR build leaves `handleError` undefined and captures nothing.
- `wrapRequestHandler` from `@sentry/cloudflare/request` establishes no request isolation on Workers: it is the one Cloudflare wrapper that never calls `setAsyncLocalStorageAsyncContextStrategy`, so under concurrency every `setTag`, `setUser` and request-data write is global to the isolate and bleeds into unrelated later requests, and no event carries request data at all. It exists for runtimes that cannot enable `nodejs_compat`, such as Shopify Oxygen.
- A route with no loader or action stays method-only.
- With `instrumentBuild` alone the event's `transaction` field is unset, because nothing calls `isolationScope.setTransactionName`, so error grouping loses the route.
- Without `sentryCloudflareVitePlugin()` there are no database spans and no warning; `mysql2` is unusable on workerd.
