- [ ] **P0** · DOC-Q44 · The Koa verify snippet uses a router the guide never creates
  `platform-includes/getting-started-verify/javascript.koa.mdx:7` and `:13-15` tell the reader to add `router.get("/debug-sentry", ...)` to the main application file. The guide's application file (`getting-started-use/javascript.koa.mdx`) creates no router and no step installs `@koa/router`; pasted as instructed the app dies at startup with `ReferenceError: router is not defined`, captured as `auto.node.onuncaughtexception`. The only Koa snippet that creates a router, `getting-started-add-top-level-import/javascript.koa.mdx`, is rendered by no page.
  **Change:** Add `npm install @koa/router` to the install step and `import Router from "@koa/router"; const router = new Router(); app.use(router.routes());` to both getting-started-use tabs, as the unrendered include already does.
  Draft: [Add the router to the Koa getting-started snippets that the verify step relies on](<https://gist.github.com/JPeer264/6d973a8266700d0cecbca9ed27cf8b21#10-add-the-router-to-the-koa-getting-started-snippets-that-the-verify-step-relies-on>)

## Should land

- [ ] **P1** · DOC-Q45 · With a direct import Koa still needs setupKoaErrorHandler, the migration page says otherwise
  `common/migration/v10-to-v11/index.mdx:715-719` says Koa errors are captured by the integration now, so `setupKoaErrorHandler(app)` is no longer needed. True with `--import`, `NODE_OPTIONS`, `--require` and a CommonJS `require`: five events with `auto.middleware.koa` and no handler call, with and without tracing. With the direct first-line import that `common/install/esm-without-import.mdx:53-63` documents, the orchestrion callback channel never fires and without the call no Koa error reaches Sentry at all: only the sentinel arrived and Koa logged the errors to stderr. That page says only that framework spans are lost.
  **Change:** Say on both pages that with a direct first-line import Koa error capture still requires `Sentry.setupKoaErrorHandler(app)`, next to the span loss.
  Note: qualifies SDK-1482 for the direct-import case.
  Draft: [Qualify the Koa error handler claims on the migration and esm-without-import pages](<https://gist.github.com/JPeer264/6d973a8266700d0cecbca9ed27cf8b21#120-qualify-the-koa-error-handler-claims-on-the-migration-and-esm-without-import-pages>)
- [ ] **P1** · DOC-Q46 · The Koa integration page names the wrong mechanism, enablement rule and version range
  `common/configuration/integrations/koa.mdx:21` says the integration captures spans using `@opentelemetry/instrumentation-koa`. That package is not installed (not a dependency of `@sentry/node` or `@sentry/server-utils`); every Koa span has origin `auto.http.koa` from the SDK's own `orchestrion:koa:use` channel, which needs the SDK loaded before `koa` through `--import`, `NODE_OPTIONS` or `require`. A first-line ESM import yields url-named `GET` segments and no router or middleware span.
  `:19` says the integration is enabled when performance monitoring is enabled; with no `tracesSampleRate` it is still installed (23 default integrations include Koa) and its auto-registered error listener captured all five errors. `:54` lists `koa ^2.0.0`; koa 3.2.1 is fully instrumented and the build's range is `>=2.0.0 <4`. `:29-50` show `ignoreLayersType` as the only option, and there is no status filter: `ctx.throw(404, ...)` and `ctx.throw(503, ...)` both arrive as unhandled events, while Express and Fastify have `shouldHandleError`.
  **Change:** Describe the diagnostics-channel mechanism and its loading requirement, say the integration is always on and creates spans only with tracing, list `koa ^2.0.0 || ^3.0.0`, and say that every error Koa emits is reported, with `ignoreErrors` or `beforeSend` as the filter.
  Draft: [Rewrite the Koa integration page around the diagnostics-channel instrumentation](<https://gist.github.com/JPeer264/6d973a8266700d0cecbca9ed27cf8b21#121-rewrite-the-koa-integration-page-around-the-diagnostics-channel-instrumentation>)
