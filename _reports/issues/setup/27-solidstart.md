Docs changes for the SolidStart guide that a new user hits between install and the first event on v11, from the runtime docs audit (develop `03aaf42455` and `6f2da7483d`, docs `aebda0ee4`). Each item links to its issue draft in the secret gist (https://gist.github.com/JPeer264/6d973a8266700d0cecbca9ed27cf8b21); the reproductions are [`quickstarts/solidstart/`](<https://github.com/JPeer264/sentry-repros/tree/issue-linear-runtime-improvements/quickstarts/solidstart>) in the audit repository.

## Must land

- [ ] **P0** · DOC-Q103 · The guide describes SolidStart 1; on SolidStart 2 its config, start command and middleware import do not exist
  `npm install @solidjs/start` gives 2.0.4 today, and the guide targets SolidStart 1. `guides/solidstart/index.mdx:208-231` and `:335-352` (and the install pages) wrap `app.config.ts` with `withSentry` and `defineConfig` from `@solidjs/start/config`; SolidStart 2 has no `app.config.ts`, that module exports no `defineConfig`, and the file is ignored at build. The develop SDK's SolidStart 2 plugin is `sentrySolidStart` from `@sentry/solidstart/vite` in `vite.config.ts`, which no page prints.
  `:277-301` (and `install/cli-import.mdx:25-48`, `install/limited-server-tracing.mdx:43`) say the build creates `.output/server/instrument.server.mjs` and start with `node --import` on it or `vinxi start`; on SolidStart 2 the build emits no such file, the command exits with `ERR_MODULE_NOT_FOUND`, and vinxi is not installed. `node --import ./src/instrument.server.ts .output/server/index.mjs` works on Node 26 and delivers the server SDK with 46 integrations, client and server spans in one trace, and propagation to a downstream fetch.
  `features/middleware.mdx:11` imports `sentryBeforeResponseMiddleware` from `@sentry/solidstart/middleware`: `ERR_PACKAGE_PATH_NOT_EXPORTED`, the package exports `.`, `./solidrouter` and `./vite`; `index.mdx:192` imports it from `@sentry/solidstart`, which works.
  **Change:** Add the `vite.config.ts` snippet (`solidStart()`, `sentrySolidStart({ org, project, authToken })` from `@sentry/solidstart/vite`, `nitro()`) and a SolidStart 2 run step next to the SolidStart 1 snippets, label the current steps SolidStart 1, and change the middleware import path to `@sentry/solidstart`.
  Draft: [Add a SolidStart 2 setup to the SolidStart guide: the Vite plugin, the start command and the middleware import path](<https://gist.github.com/JPeer264/6d973a8266700d0cecbca9ed27cf8b21#24-add-a-solidstart-2-setup-to-the-solidstart-guide-the-vite-plugin-the-start-command-and-the-middleware-import-path>)

## Should land

- [ ] **P1** · DOC-Q104 · The Vite plugin deletes every source map below the project root, node_modules included
  `guides/solidstart/index.mdx:324-352` says adding `org`, `project` and `authToken` uploads source maps, and says nothing about deletion. Without an auth token the plugin logs `Will not upload source maps` and then deletes 3,543 `*.map` files, 3,519 of them under `node_modules/`, because the automatic `sourcemaps.filesToDeleteAfterUpload` is `["./**/*.map"]`; seven maps remained in `node_modules` after one build.
  **Change:** State that the plugin deletes every `*.map` below the project root unless `sourcemaps.filesToDeleteAfterUpload` is narrowed, and recommend `sourcemaps: { disable: true }` when no auth token is configured.
  Draft: [Warn on the SolidStart guide that the plugin deletes every *.map below the project root unless told otherwise](<https://gist.github.com/JPeer264/6d973a8266700d0cecbca9ed27cf8b21#145-warn-on-the-solidstart-guide-that-the-plugin-deletes-every-map-below-the-project-root-unless-told-otherwise>)
- [ ] **P1** · DOC-Q105 · The verify button promises an API-route error that is never sent; server functions undocumented
  `guides/solidstart/index.mdx:444-462` says clicking the button triggers a frontend error, an error in the API route and a trace. `GET /sentry-test` answers 500 and produces server spans with status `error` in the client's trace, and the client captures `Sentry Test Error`, but no server event for `Sentry Example API Route Error` is sent; h3 prints the error to stderr and the SDK debug log shows no capture. A throwing `"use server"` function reaches the client as a caught error with a `POST /_server` span of status `ok` and no server event; `withServerActionInstrumentation` exists in the package and no page mentions it. The Deno and Cloudflare cells recorded the same gap (DOC-F34, DOC-F51).
  **Change:** Say the API-route error shows up as an errored server span only, show how to capture it, and document `withServerActionInstrumentation` for server functions.
  Draft: [Say on the SolidStart guide which server errors are captured, and document withServerActionInstrumentation](<https://gist.github.com/JPeer264/6d973a8266700d0cecbca9ed27cf8b21#146-say-on-the-solidstart-guide-which-server-errors-are-captured-and-document-withserveractioninstrumentation>)
