Docs changes for the Deno guide that a new user hits between install and the first event on v11, from the runtime docs audit (develop `03aaf42455` and `6f2da7483d`, docs `aebda0ee4`). Each item links to its issue draft in the secret gist (https://gist.github.com/JPeer264/6d973a8266700d0cecbca9ed27cf8b21); the reproductions are linked from each draft in the audit repository.

## Must land

- [ ] **P1** · DOC-D1 · No instrumentation step; the import hook is undocumented
  `guides/deno/index.mdx` renders `import * as Sentry from "npm:@sentry/deno"` through the `___SDK_PACKAGE___` placeholder at `:44` and `:66` (the literal specifier is not in the file), and shows two permission flags. It never states that the database, messaging, AI and framework integrations in the default set require the `@sentry/deno/import` hook, nor that the `Deno.serve` and `node:http` server spans work without it. `packages/deno/README.md:60-83` has a version of this section, but its `--import=@sentry/deno/import` form at `:70` does not resolve.
  What was observed on deno 2.9.0 and 2.8.3: a first-line `import '@sentry/deno/import';` before `Sentry.init` registers the hook and instruments `mysql.createConnection`. `--import=@sentry/deno/import` fails with `Module not found`; `--import=./node_modules/@sentry/deno/build/import.mjs` registers the hook. Without the hook the SDK installs 39 integrations at `6f2da7483d`, reports no injection and prints nothing. The `deno-mysql` and `deno-pg` e2e apps use the first-line import form, with `nodeModulesDir: "manual"` and an installed `node_modules`. Any dependency that `require()`s a JSON file currently crashes under the hook.
  **Change:** Add an "Enable library instrumentation" step to `guides/deno/index.mdx` with first-line `import '@sentry/deno/import';` as the primary form. State that the hook needs the package resolvable from `node_modules`, so `deno.json` has to set `nodeModulesDir` to `"auto"`, or to `"manual"` with an install step, which is what every Deno e2e app does. Show the file-path `--import` flag as the alternative; do not show the bare specifier form. State that dependencies which `require()` a JSON file fail to import under the hook. State which instrumentation works without the hook.
  Draft: [Document the @sentry/deno/import hook in the Deno guide](<https://gist.github.com/JPeer264/6d973a8266700d0cecbca9ed27cf8b21#42-document-the-sentrydenoimport-hook-in-the-deno-guide>)
- [ ] **P1** · DOC-D3 · The documented permission flags crash the app under the hook, and silently degrade without it
  `guides/deno/index.mdx:100` shows `deno run --allow-net=<ingest> index.ts` and `:119` shows `deno run --allow-read=./src index.ts` as two separate commands, while the init snippets on the same page name the file `main.ts`. Neither `--allow-env` nor `--allow-sys` is mentioned, and `packages/deno/README.md` mentions no flag at all.
  What was observed on deno 2.9.0: with only `--allow-net` and `--no-prompt`, events carry `server_name: null`, no OS version, an absolute filesystem path as the frame filename and no context lines. With the `@sentry/deno/import` hook line present, the same flags do not degrade but crash: `NotCapable: Requires env access, run again with the --allow-env flag`, raised from the vendored `debug` package inside `@sentry/server-runtime-injection` at module load (getting-started reproduction QS-deno, 2026-09-08). With all permissions granted, the same app reports the hostname, the OS version, an `app:///`-prefixed filename and context lines. No warning is printed in the restricted run. Every Deno e2e app runs with `--allow-net --allow-env --allow-read`; `deno-mysql`, `deno-pg` and `deno-redis` add `--allow-sys --allow-write`, and `deno-streamed` adds `--allow-sys`.
  **Change:** Replace the two commands at `:100` and `:119` with a single `deno run --allow-net=<ingest> --allow-read --allow-env --allow-sys main.ts`, using the same filename as the init snippets. Add a table naming what each flag unlocks: `--allow-net` event delivery, `--allow-read` source context lines and app-relative frame paths, `--allow-env` `SENTRY_*` lookups and `serverName`, `--allow-sys` hostname and OS version. Add the same table to `packages/deno/README.md`.
  Draft: [Show one complete deno run command with all four permission flags in the Deno guide](<https://gist.github.com/JPeer264/6d973a8266700d0cecbca9ed27cf8b21#44-show-one-complete-deno-run-command-with-all-four-permission-flags-in-the-deno-guide>)
- [ ] **P0** · DOC-R2 · The crons page recommends an integration that crashes init on Deno 2.9
  `platform-includes/crons/setup/javascript.deno.mdx:1` heads its first section "Automatic Check-Ins (Recommended)" and `:12` tells the reader to pass `Sentry.denoCronIntegration()` to `Sentry.init`.
  That call crashes startup on Deno 2.9.0 and later. `packages/deno/src/integrations/deno-cron.ts:23` assigns `Deno.cron = new Proxy(Deno.cron, ...)` inside `setupOnce`, i.e. inside `Sentry.init`. On Deno 2.8.3 `Deno.cron` is a writable data property and the integration works: a cron firing at the minute boundary produced one `in_progress` and one `ok` check-in. From Deno 2.9.0 `Deno.cron` is a getter-only accessor, so the assignment throws `TypeError: Cannot set property cron of #<Object> which has only a getter` and the process exits 1 before any user code runs.
  There is a second failure mode without the unstable flag. When `Deno.cron` is absent the guard at `deno-cron.ts:18-21` returns silently, so the integration is an inert no-op and the SDK gives no warning, while the reader's own `Deno.cron(...)` call throws `TypeError: Deno.cron is not a function`. The integration is also not in the Deno default set (`packages/deno/src/sdk.ts:31-49`), although its own JSDoc at `deno-cron.ts:64` says "Enabled by default in the Deno SDK".
  **Change:** Remove the "Recommended" framing and the `denoCronIntegration()` snippet, or state that it makes `Sentry.init` throw on Deno 2.9.0 and later and works only up to Deno 2.8.3. Lead with the `Sentry.withMonitor` / `Sentry.captureCheckIn` sections already on the page. State that `Deno.cron` needs `--unstable-cron`, and that without the flag the integration silently does nothing. Say that the integration has to be passed in `integrations` explicitly; it is not in the Deno default set.
  Draft: [Stop recommending denoCronIntegration() on the Deno crons page](<https://gist.github.com/JPeer264/6d973a8266700d0cecbca9ed27cf8b21#29-stop-recommending-denocronintegration-on-the-deno-crons-page>)
