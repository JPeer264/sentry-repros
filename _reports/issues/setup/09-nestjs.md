Docs changes for the NestJS guide that a new user hits between install and the first event on v11, from the runtime docs audit (develop `03aaf42455` and `6f2da7483d`, docs `aebda0ee4`). Each item links to its issue draft in the secret gist (https://gist.github.com/JPeer264/6d973a8266700d0cecbca9ed27cf8b21); the reproductions are [`quickstarts/nestjs/`](<https://github.com/JPeer264/sentry-repros/tree/issue-linear-runtime-improvements/quickstarts/nestjs>) in the audit repository.

## Must land

- [ ] **P0** · DOC-Q57 · The NestJS tracing verify snippet kills the process
  `platform-includes/getting-started-verify/javascript.nestjs.mdx:30-49` updates `/debug-sentry` with `Sentry.startSpan(...)` whose callback throws inside `setTimeout(..., 99)`. The route answers 200 and the test span is sent, then the throw fires outside the Nest pipeline: captured as `auto.node.onuncaughtexception`, and the Nest process exits, so the app is dead after one hit. The snippet also shows no controller class and no `Sentry` import.
  **Change:** Throw synchronously inside the callback or await a delay, wrap the snippet in a controller with `import * as Sentry from "@sentry/nestjs"`, and say the result is a span inside the request trace.
  Draft: [Fix the NestJS tracing verify snippet: its delayed throw is an uncaught exception that exits the app](<https://gist.github.com/JPeer264/6d973a8266700d0cecbca9ed27cf8b21#13-fix-the-nestjs-tracing-verify-snippet-its-delayed-throw-is-an-uncaught-exception-that-exits-the-app>)
- [ ] **P0** · DOC-Q58 · The NestJS ESM start script is not a runnable command
  `guides/nestjs/install/esm.mdx:33-36` shows `"start": "--import ./instrument.mjs nest start"`. Executed as an npm script it fails with `sh: --: invalid option`: the line names no `node` binary, and `nest start` does not accept `--import`. The `NODE_OPTIONS` form at `:41` works, as does `node --import ./dist/instrument.js dist/main.js`.
  **Change:** Show a real command such as `node --import ./instrument.mjs dist/main.js`, or lead with the `NODE_OPTIONS` form.
  Draft: [Replace the NestJS ESM start script with a command that runs](<https://gist.github.com/JPeer264/6d973a8266700d0cecbca9ed27cf8b21#14-replace-the-nestjs-esm-start-script-with-a-command-that-runs>)

## Should land

- [ ] **P1** · DOC-Q59 · No NestJS error reaches Sentry without SentryGlobalFilter; the guide says otherwise
  `platform-includes/getting-started-capture-errors/javascript.nestjs.mdx:1` says Sentry captures by default the unhandled exceptions that no error filter catches. With the guide's setup up to `guides/nestjs/index.mdx:102-117` (`SentryModule.forRoot()`, no filter) the unhandled controller error produced no event: Nest's built-in exception handler catches everything, and nothing reaches Sentry until `SentryGlobalFilter` or `@SentryExceptionCaptured()` is added. `:2` says HttpExceptions are not captured by default; that holds for 404, 503 and a bare `HttpException` with status 500 alike, the filter has no status threshold and no option, and `shouldHandleError` exists only for Express and Fastify.
  **Change:** State that Nest's default exception handler swallows every error, so the filter or the decorator is required for any HTTP error, move that step before Verify, and say that 5xx HttpExceptions are included with no option to change it.
  Draft: [Say on the NestJS guide that SentryGlobalFilter is required for any HTTP error to be captured, and move it before Verify](<https://gist.github.com/JPeer264/6d973a8266700d0cecbca9ed27cf8b21#128-say-on-the-nestjs-guide-that-sentryglobalfilter-is-required-for-any-http-error-to-be-captured-and-move-it-before-verify>)
- [ ] **P1** · DOC-Q60 · The Nest integration page names the wrong mechanism, enablement rule and Nest 4
  `common/configuration/integrations/nest.mdx:19-21` says the integration is enabled with performance monitoring and captures spans using `@opentelemetry/instrumentation-nestjs-core`. That package is not installed (only `@opentelemetry/api` is); the Nest integration is installed with and without tracing (24 of 24 integrations in the errors-only run), and every Nest span comes from the SDK's own diagnostics-channel instrumentation (`auto.http.nestjs`, `auto.middleware.nestjs`). `:31` says Nest.js 4.0.0 or later is supported; the build injects into `@nestjs/core` 8 through 12 and the package peer range starts at 8.
  **Change:** Describe the built-in instrumentation of `@nestjs/core`, `@nestjs/common`, `@nestjs/schedule`, `@nestjs/event-emitter` and `@nestjs/bullmq`, say it is always installed, and list Nest.js 8 through 12.
  Draft: [Rewrite the Nest integration page around the diagnostics-channel instrumentation](<https://gist.github.com/JPeer264/6d973a8266700d0cecbca9ed27cf8b21#129-rewrite-the-nest-integration-page-around-the-diagnostics-channel-instrumentation>)
