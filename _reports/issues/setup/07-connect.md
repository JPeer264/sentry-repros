Docs changes for the Connect guide that a new user hits between install and the first event on v11, from the runtime docs audit (develop `03aaf42455` and `6f2da7483d`, docs `aebda0ee4`). Each item links to its issue draft in the secret gist (https://gist.github.com/JPeer264/6d973a8266700d0cecbca9ed27cf8b21); the reproductions are [`quickstarts/connect/`](<https://github.com/JPeer264/sentry-repros/tree/issue-linear-runtime-improvements/quickstarts/connect>) in the audit repository.

## Must land

- [ ] **P0** · DOC-Q52 · The Connect guide and integration page describe a removed instrumentation; every printed app crashes
  `common/migration/v10-to-v11/index.mdx:1370` records that the Connect instrumentation was removed, and the develop build confirms it: `@sentry/node` exports neither `setupConnectErrorHandler` nor `connectIntegration`, installs no `Connect` integration (46 with tracing, 23 without), and carries no orchestrion config or diagnostics-channel subscriber for connect. The docs still describe it in six places.
  `platform-includes/getting-started-use/javascript.connect.mdx:11` and `:28` call `Sentry.setupConnectErrorHandler(app)` after `connect()`: every app the guide prints crashes with `TypeError: Sentry.setupConnectErrorHandler is not a function` before it listens, under `--import`, CommonJS, a first-line import and `NODE_OPTIONS`; the orphaned `getting-started-add-top-level-import/javascript.connect.mdx:9` and `:24` do the same. `common/configuration/integrations/connect.mdx:23-27` passes `integrations: [Sentry.connectIntegration()]`, which throws inside the instrument file so the SDK never initializes; `:3`, `:19` and `:21` say the integration is enabled by default and captures spans with `@opentelemetry/instrumentation-connect` (and the sentence says "for the Hapi framework"). The integrations table row at `platform-includes/configuration/integrations/javascript.connect.mdx:7`, the request-handler row at `v10-to-v11/index.mdx:436` and the `Connect` entry of `common/install/late-initialization.mdx:113` repeat it.
  With the handler line deleted the guide app runs and delivers the generic Node telemetry only: `http.server` segments named `GET` with source `url` and no `http.route`, no handler or middleware span, logs, and no automatic capture of a thrown handler error (DOC-Q53).
  **Change:** Delete the `setupConnectErrorHandler(app)` line from both tabs and the orphaned include, and say that v11 has no Connect-specific instrumentation: requests appear as method-named `http.server` segments. Replace the Connect integration page with a removal notice pointing at the migration entry, drop the table row, drop Connect from the request-handler row at `:436` and from the late-initialization list.
  Draft: [Rewrite the Connect guide and integration page for v11, whose SDK has no Connect instrumentation](<https://gist.github.com/JPeer264/6d973a8266700d0cecbca9ed27cf8b21#12-rewrite-the-connect-guide-and-integration-page-for-v11-whose-sdk-has-no-connect-instrumentation>)

## Should land

- [ ] **P1** · DOC-Q53 · The Connect verify route never reaches Sentry without an error middleware
  `platform-includes/getting-started-verify/javascript.connect.mdx:7` and `:13-15` say that `app.use("/debug-sentry", (req, res) => { throw new Error(...) })` creates an issue. On the app that starts (the handler line removed, DOC-Q52), the request answers 500 from Connect's `finalhandler`, Connect prints the stack, and no event reaches Sentry in any variant, with or without tracing; thrown and `next(err)` errors (404, 503, 500) are all swallowed. The guide also renders no capture-errors step, because `getting-started-capture-errors` has no Connect include (DOC-Q31). The only Connect error that arrived was the unhandled rejection of the async tracing snippet (DOC-Q27).
  **Change:** Add an error-handling middleware `(err, req, res, next)` that calls `Sentry.captureException(err)` before `next(err)` as the prerequisite of the verify route, and state that v11 captures no Connect errors on its own.
  Draft: [Say on the Connect guide that errors need an error-handling middleware, and show it](<https://gist.github.com/JPeer264/6d973a8266700d0cecbca9ed27cf8b21#125-say-on-the-connect-guide-that-errors-need-an-error-handling-middleware-and-show-it>)
