- [ ] **P0** · DOC-Q7 · The tracing verify snippet is a SyntaxError: await in a non-async function
  `platform-includes/getting-started-verify/javascript.mdx:53-68` tells the reader to update the button handler so that it starts a span around a simulated longer operation, and shows `function triggerError() { await Sentry.startSpan(...) }`. The function is not `async`.
  Observed with the snippet copied verbatim into a page: Chrome reports `Uncaught SyntaxError: await is only valid in async functions and the top level bodies of modules`, discards the whole script block, and the "Break the World" button next to it throws `ReferenceError`. With `async function triggerError()` the same page produces the span (`test Example Frontend Span`) inside the pageload span envelope.
  **Change:** Make the handler `async function triggerError()` in the snippet, and keep the button call as it is. Say what arrives: one span envelope with the pageload segment and the manual span as a child, no transaction envelope, because the default lifecycle is stream (DOC-Q1).
  Draft: [Fix the tracing verify snippet on the browser getting-started page: await inside a non-async function](<https://gist.github.com/JPeer264/6d973a8266700d0cecbca9ed27cf8b21#1-fix-the-tracing-verify-snippet-on-the-browser-getting-started-page-await-inside-a-non-async-function>)

- [ ] **P1** · DOC-Q63 · Debug IDs need a build_id section and a streaming loader the guide never mentions
  `guides/wasm/index.mdx:65` says the integration provides Debug IDs, Debug Files, Code IDs, Code Files and memory addresses. With a module that has no `build_id` custom section (nothing in the guide's install or Rust steps adds one; `wasm-split` does) the event carries only `instruction_addr` and `platform: native` on the wasm frame, no `addr_mode` and no `debug_meta`: the registry skips modules without `build_id`. With the section present the full set arrives (`addr_mode: rel:0`, a `debug_meta.images` entry of type `wasm` with code_id, code_file, debug_file and debug_id). The page never mentions `wasm-split`, `build_id`, DWARF or the debug file upload.
  Loading also matters and the page (`:160`, `:176-179`) is silent on it: a module loaded with `WebAssembly.instantiate(bytes)` after `fetch().arrayBuffer()` is named `wasm://wasm/<hash>` by Chrome, so even with `build_id` no image matches and no `addr_mode` or `debug_meta` is attached; `instantiateStreaming` and `compileStreaming` keep the URL and match.
  **Change:** State at `:65` that the module must carry a `build_id` section (`wasm-split`) and that the DWARF debug file has to be uploaded, link the debug files docs, and add that symbolication needs a loader that keeps the module URL.
  Draft: [Say on the WebAssembly guide what the integration needs: a build_id section, a URL-keeping loader and uploaded debug files](<https://gist.github.com/JPeer264/6d973a8266700d0cecbca9ed27cf8b21#130-say-on-the-webassembly-guide-what-the-integration-needs-a-build_id-section-a-url-keeping-loader-and-uploaded-debug-files>)
