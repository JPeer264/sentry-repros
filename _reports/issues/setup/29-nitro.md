## Must land

- [ ] **P0** · DOC-Q78 · The install fails on current Nitro betas and the config never registers the verify route
  `guides/nitro/index.mdx:23` says a Nitro application 3.0.260415-beta or newer, and `:50` installs `@sentry/nitro`. `npm install` fails with `ERESOLVE` for every Nitro beta newer than 3.0.260415-beta, the registry's latest 3.0.260903-beta included, because the peer range accepts only 3.0.0, 3.0.260311-beta and 3.0.260415-beta; the exact 260415 beta installs.
  `:86-99` wraps `defineNitroConfig({ ... })` with no `serverDir`, and `:208` adds `routes/debug-sentry.ts` at the project root. Nitro 3 defaults to `serverDir: false`, scans nothing, and every route including `/debug-sentry` answers 404 with no event; with `serverDir: "./server"` and the file at `server/routes/debug-sentry.ts` the route creates the issue.
  **Change:** State the exact Nitro versions the peer range accepts and that newer betas need `--legacy-peer-deps` until the range is widened; add `serverDir: "./server"` to the config snippet and name the verify file `server/routes/debug-sentry.ts`. The same peer range blocks the SolidStart guide: plain `npm install @sentry/solidstart` fails with `ERESOLVE` because `@sentry/nitro` rejects the nitro beta SolidStart 2 needs, and `--legacy-peer-deps` is required (QS-solidstart).
  Draft: [Fix the Nitro guide's version claim and add serverDir to its config](<https://gist.github.com/JPeer264/6d973a8266700d0cecbca9ed27cf8b21#18-fix-the-nitro-guides-version-claim-and-add-serverdir-to-its-config>)

  `guides/nitro/index.mdx:273` says the error hook captures unhandled errors and skips 3xx and 4xx HTTPErrors: true on nitro 3.0.260415-beta; on 3.0.260903-beta every handler error is captured twice (`auto.http.nitro.onTraceError` plus `auto.function.nitro.captureErrorHook`) and the 404 HTTPError is reported. `:203-214` and `:228-249` say the verify route's `Error("My first Sentry error!")` creates the issue; the event's outermost exception is `HTTPError: My first Sentry error!`, Nitro's 500 wrapper, with the thrown Error as a chained cause, so the issue is titled HTTPError. `:289` says middleware spans use `op: 'middleware.nitro'`; the h3 spans have op `middleware` and are named after the route (`middleware GET /api/users/:id`), never after the middleware. `:286` says the SDK creates transactions for incoming requests; only span items arrive. `:291` says 4xx HTTPErrors do not mark the span errored; the `/error-404` segment arrives with status `error` and status code 404.
  **Change:** Scope the error-hook claim to the verified Nitro versions and note the newer betas' duplicates, tell the reader the issue is titled HTTPError with the original error chained, change the op to `middleware` with route naming, say request spans instead of transactions, and drop or restrict the 4xx claim.
