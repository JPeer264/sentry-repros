Runtime Quick Starts

Proposed quick start pages for the Bun, Deno and Cloudflare guides. Each step was run as written against the develop build, and against the published 10.73.0 where the tables say so, and the deep probe report fed back the caveats. The last section maps every claim to its run.

Bun

Works with Bun 1.3.14 or later. Runtime spans (errors, Bun.serve requests, fetch, logs) work on every supported Bun version. Library spans (databases, AI SDKs, Express, Koa, Hapi) need a bundle built with the Sentry plugin, see step 3. Fastify and mysql2 3.20 or later publish their own events and need no build step. Import database drivers and create clients at module scope: a driver whose module first loads inside a request records no spans on every Bun version. See Bun runtime notes.

Before SDK 11.0

On SDK 10.x, outgoing fetch and node:http servers (Express, Koa, Hapi, Fastify, next start) are not instrumented on Bun: no fetch spans or trace headers, and no request isolation on node:http. The plugin build (step 3) adds database and AI spans only. See Bun on SDK 10.x for the two workarounds.

1. Install

bashbun add @sentry/bun

2. Configure

Create instrument.ts and preload it. Everything the SDK wraps (Bun.serve, fetch, node:http, uncaught errors) is patched when init() runs, so it has to run before the rest of your app loads, and a preloaded module was evaluated once per process in our runs, also under bun --hot.

instrument.tsimport * as Sentry from "@sentry/bun";

Sentry.init({
  dsn: "___PUBLIC_DSN___",

  // Capture 100% of transactions. Lower this in production.
  tracesSampleRate: 1.0,

  // User data and headers are sent by default; Bun.serve never sends request bodies.
  // To keep user data out: dataCollection: { userInfo: false },
});
app.tsimport * as Sentry from "@sentry/bun";

Bun.serve({
  port: 3000,
  routes: {
    "/users/:id": (req) => Response.json({ id: req.params.id }),
  },
});
bashbun --preload ./instrument.ts app.ts

Or add preload = ["./instrument.ts"] to bunfig.toml and run bun app.ts. An import "./instrument"; as the first line of the entry file also works for bun app.ts and bun --watch, but not for bun --hot, which re-evaluates the entry on every reload and then records one extra request span per reload.

This is enough for:

  • Uncaught errors, unhandled rejections and errors thrown from Bun.serve routes.
  • An http.server span per request; a streamed response ends it when the handler returns, not when the stream closes. Routes declared in Bun.serve({ routes }) are named by their pattern (GET /users/:id); a plain fetch handler is named by method only.
  • http.client spans with sentry-trace and baggage headers on outgoing fetch and node:http requests.
  • Logs from Sentry.logger.* and console breadcrumbs.

3. Instrument your libraries

Database drivers, AI SDKs and the Express, Koa and Hapi integrations record spans through node:diagnostics_channel events that the Sentry bundler plugin injects into those packages at build time. bun run on unbundled source cannot inject them, so those integrations stay silent there. Bundle your app with @sentry/bun/plugin:

build.tsimport { sentryBunPlugin } from "@sentry/bun/plugin";

await Bun.build({
  entrypoints: ["./app.ts"],
  outdir: "./dist",
  target: "bun",
  // Keep the SDK external and let the plugin bundle every instrumented package.
  external: ["@sentry/*"],
  // Readable stack traces locally, and the input for source map upload.
  sourcemap: "external",
  plugins: [sentryBunPlugin()],
});
bashbun run build.ts
bun --preload ./instrument.ts dist/app.js

Instrumented packages listed in external are bundled anyway, because a package that is resolved from node_modules at runtime never passes through the plugin. Run the bundle with bun --preload ./instrument.ts dist/app.js, or bundle instrument.ts in by importing it from the entry.

Single-file executables are bundles too, so the plugin applies, but only through the JavaScript API: Bun.build({ compile: { outfile: "./app" }, plugins: [sentryBunPlugin()] }). Drop the external line for a compiled build, because an executable cannot resolve external packages at runtime. bun build --compile on the command line cannot take plugins. Development with bun --watch app.ts records runtime spans only.

4. Verify

Add a route that throws and a manual span, then request them:

app.tsBun.serve({
  routes: {
    "/debug-sentry": () => {
      throw new Error("My first Sentry error!");
    },
    "/debug-span": async () => {
      await Sentry.startSpan({ op: "test", name: "My First Test Span" }, async () => {
        await Bun.sleep(100);
      });
      Sentry.logger.info("Span recorded", { route: "/debug-span" });
      return new Response("ok");
    },
  },
});

In Sentry you should see one issue, two http.server traces (GET /debug-sentry with an error, GET /debug-span with a child span) and one log line. The client is cached per isolate, so hitting /debug-sentry a second time sends no second issue until a different event goes out; that is the dedupe integration, not a lost event. Pass enableDedupe: false in the options to turn it off.

5. Add readable stack traces with source maps

Bundled stack traces point into dist/app.js. Inject debug IDs and upload the maps from the sourcemap: "external" build above:

bashnpx @sentry/cli sourcemaps inject ./dist
npx @sentry/cli sourcemaps upload --org ___ORG_SLUG___ --project ___PROJECT_SLUG___ ./dist

The Sentry wizard has no Bun bundler preset; the CLI commands above are the supported path. See Source Maps.

6. Frameworks on Bun

Every framework SDK we tested runs on Bun with the develop line, but they are Node SDKs: Bun never publishes Node's request channel and Node's fetch instrumentation never fires. Install @sentry/bun next to your framework SDK and add its two integrations to the server init. That change restores request spans, per-request isolation, incoming trace continuation and outgoing fetch spans for the framework SDKs. The table below lists what each framework needs on top.

sentry.server.config.ts (Nuxt, Next.js, Astro) or instrument.server.ts (SvelteKit, React Router, TanStack Start)import * as Sentry from "@sentry/nuxt"; // or @sentry/nextjs, @sentry/sveltekit, @sentry/astro, ...
import { bunServerIntegration, bunHttpServerIntegration, fetchIntegration } from "@sentry/bun";

const onBun = typeof Bun !== "undefined";

Sentry.init({
  dsn: "___PUBLIC_DSN___",
  tracesSampleRate: 1.0,
  // Only on Bun, so the same file works under Node without duplicate spans.
  integrations: onBun
    ? [fetchIntegration(), bunServerIntegration(), bunHttpServerIntegration()]
    : [],
});

bunServerIntegration covers servers built on Bun.serve (Nitro's bun preset, Astro standalone), bunHttpServerIntegration covers node:http servers (Express custom servers, next start, Nitro's node-server preset). Adding both is safe.

Database spans need one more line, because Bun drops diagnostics_channel subscriptions that nothing else references before the driver loads. Pin the channels for the drivers you use right after Sentry.init():

same file, after Sentry.init()import * as dc from "node:diagnostics_channel";

globalThis.__sentryPinnedChannels ??= [
  "mysql2:query", "mysql2:execute", "mysql2:connect", "mysql2:pool:connect",
  "orchestrion:mysql2:query", "orchestrion:mysql:query",
].map((name) => dc.tracingChannel(name));

Deno

Works with Deno 2.8.3 or later. The SDK is in beta.

1. Install

bashdeno add npm:@sentry/deno

Add nodeModulesDir to deno.json. The library instrumentation in step 3 rewrites packages while they load, and it only sees packages that live in a local node_modules directory, not in Deno's global npm cache.

deno.json{
  "nodeModulesDir": "auto",
  "imports": {
    "@sentry/deno": "npm:@sentry/deno"
  }
}

2. Configure

Initialize the SDK at the top of your entry file. The first import registers the library instrumentation hook (step 3); it has to be the first import of the program, before any package you want instrumented has loaded.

main.tsimport "@sentry/deno/import";
import * as Sentry from "@sentry/deno";

Sentry.init({
  dsn: "___PUBLIC_DSN___",

  // Capture 100% of transactions. Lower this in production.
  tracesSampleRate: 1.0,

  // User data, headers and HTTP bodies are sent by default. To keep them out:
  // dataCollection: { userInfo: false, httpBodies: [] },
});

Deno.serve({ port: 3000 }, (req) => new Response("Hello"));

Run it with the permissions the SDK uses:

bashdeno run --allow-net --allow-env --allow-read=. --allow-sys=hostname,osRelease main.ts
FlagWhat it unlocks
--allow-netSending events. Narrow it to your ingest host: --allow-net=___ORG_INGEST_DOMAIN___, plus whatever your app needs.
--allow-envRequired by the first-line @sentry/deno/import hook, which exits with NotCapable: Requires env access without it. Also SENTRY_DSN, SENTRY_RELEASE and the other SENTRY_* variables. A scoped --allow-env=... is not enough for the hook.
--allow-read=.Source lines in stack traces and app:// paths instead of absolute file paths. Read access is checked per file for context lines and on the working directory for path normalization, so --allow-read=./src leaves your entry file bare and every filename absolute.
--allow-sys=hostname,osReleaseserver_name and the OS version on events.

Without a flag the SDK skips that feature silently, with no warning and no permission prompt.

The same applies to deno serve: export default { fetch } is instrumented like Deno.serve, and deno serve --parallel starts one SDK per worker without duplicating anything.

This is enough for:

  • Uncaught errors, unhandled rejections and errors thrown from Deno.serve handlers.
  • An http.server span per Deno.serve request, named by HTTP method. Deno.serve has no router, so route names come from a framework; see Frameworks on Deno.
  • Server and client spans for node:http, with sentry-trace and baggage headers on outgoing node:http requests. A synchronous throw inside a node:http listener is swallowed by Deno and never reaches Sentry; catch and report it yourself.
  • Logs from Sentry.logger.*, plus console and fetch breadcrumbs.

Outgoing fetch() calls record a breadcrumb only. They do not get a span and do not carry trace headers yet, so a trace ends at the first fetch to another service. Track progress in sentry-javascript#23891.

3. Instrument your libraries

The import "@sentry/deno/import" line from step 2 installs a module hook that injects node:diagnostics_channel events into database drivers, AI SDKs and web frameworks as they load. With it in place, mysql, pg, postgres, mongodb, ioredis, openai, @anthropic-ai/sdk, the Vercel AI SDK and the rest of the integration list record spans without further setup. Fastify and mysql2 (3.20 or later) publish their own events and work without the hook. Hono is a plain fetch handler and needs no hook either.

Two Deno limits apply to the hook. First, a Deno bug makes every require() of a JSON file fail once a module hook is registered (denoland/deno#36240), so Express, Hapi, Fastify and mysql2 crash on import. Register this second hook right after the Sentry import until the fix ships:

main.tsimport "@sentry/deno/import";
import { registerHooks } from "node:module";
registerHooks({
  load(url, context, next) {
    const result = next(url, context);
    if (result && result.format == null && url.endsWith(".json")) result.format = "json";
    return result;
  },
});

Second, the hook transforms CommonJS builds only. A package that loads its ES module build (the OpenAI SDK, for example) is not instrumented; point the import map at the package's CommonJS entry ("openai": "npm:openai/index.js") or run with --conditions=require.

If you forget the import, the SDK still installs the integrations and records nothing for those libraries, without a warning.

4. Verify

main.tsDeno.serve({ port: 3000 }, async (req) => {
  const { pathname } = new URL(req.url);
  if (pathname === "/debug-sentry") {
    throw new Error("My first Sentry error!");
  }
  if (pathname === "/debug-span") {
    await Sentry.startSpan({ op: "test", name: "My First Test Span" }, async () => {
      await new Promise((resolve) => setTimeout(resolve, 100));
    });
    Sentry.logger.info("Span recorded", { route: pathname });
  }
  return new Response("ok");
});

In Sentry you should see one issue, two GET traces (one with an error, one with a child span) and one log line.

5. Source maps

Deno runs your TypeScript directly, so stack traces point at your source files and no upload is needed for a plain deno run. If you bundle for deployment (deno bundle, esbuild), upload the maps with npx @sentry/cli sourcemaps inject and upload. See Source Maps.

6. Frameworks on Deno

Hono, Oak, Fresh, Express, Fastify, Koa, Hapi, NestJS, Next.js, Nuxt, SvelteKit, Astro, React Router and TanStack Start all run on Deno with the develop line, and errors, route names, isolation and incoming traces work for most of them with the wiring from steps 1 to 3. Two things apply to all of them.

Outgoing fetch() is not traced on Deno. The Deno SDK instruments node:http only, so a global fetch() gets no span and no sentry-trace header and the trace stops at the first downstream service. Until the SDK ships a fetch integration, register one from @sentry/core primitives:

instrument.tsimport "@sentry/deno/import";
import * as Sentry from "@sentry/deno";
import { addFetchInstrumentationHandler, defineIntegration, getClient, instrumentFetchRequest, isSentryRequestUrl } from "@sentry/core";

const spans = {};
const denoFetchIntegration = defineIntegration(() => ({
  name: "DenoFetch",
  setupOnce() {
    addFetchInstrumentationHandler((handlerData) => {
      const client = getClient();
      if (!client || isSentryRequestUrl(handlerData.fetchData.url, client)) return;
      instrumentFetchRequest(handlerData, () => true, () => true, spans, { spanOrigin: "auto.http.fetch" });
    });
  },
}));

Sentry.init({
  dsn: "___PUBLIC_DSN___",
  tracesSampleRate: 1.0,
  integrations: [denoFetchIntegration()],
});

The import hook and CommonJS JSON. Registering any load hook on Deno 2.9 breaks require("*.json") inside CommonJS packages (Hapi, Koa's dependencies, NestJS). Add a JSON hook next to the Sentry import, or skip the hook and bundle with esbuild and sentryOrchestrionPlugin() from @sentry/server-utils/orchestrion/esbuild:

instrument.ts, before the framework importimport * as Module from "node:module";

Module.registerHooks({
  load(url, context, nextLoad) {
    const result = nextLoad(url, context);
    return url.endsWith(".json") ? { ...result, format: "json", shortCircuit: true } : result;
  },
});

Cloudflare

Using a framework? Astro, Hono, Hydrogen, Next.js, Nuxt, React Router, Remix, SvelteKit and TanStack Start each have their own page under Frameworks on Cloudflare. This page covers a plain Worker. For Cloudflare Pages, see Cloudflare Pages.

1. Install

bashnpm install @sentry/cloudflare

2. Configure

The SDK needs Node.js APIs from the Workers runtime. Enable nodejs_compat with a compatibility_date of 2024-09-23 or later (withSentry needs it; the request wrapper from @sentry/cloudflare/request boots with nodejs_als alone, but on develop pass it traceLifecycle: "static", because that entry has no async context strategy under the streaming default):

wrangler.jsonc{
  "name": "my-worker",
  "main": "src/index.ts",
  "compatibility_date": "2024-09-23",
  "compatibility_flags": ["nodejs_compat"]
}

Wrap the Worker's exported handler with withSentry. The options callback receives env, so secrets and per-environment settings can come from bindings.

src/index.tsimport * as Sentry from "@sentry/cloudflare";

export default Sentry.withSentry(
  (env) => ({
    dsn: "___PUBLIC_DSN___",

    // Capture 100% of transactions. Lower this in production.
    tracesSampleRate: 1.0,

    // Send user data and HTTP bodies with events. Remove to keep the defaults.
    dataCollection: {},
  }),
  {
    async fetch(request, env, ctx) {
      return new Response("Hello");
    },
  } satisfies ExportedHandler<Env>,
);
bashnpx wrangler dev

This is enough for:

  • Errors thrown from fetch, scheduled and queue handlers. The email and tail handlers are wrapped too, but were not exercised in this audit.
  • An http.server span per request, named by HTTP method. Route names come from a framework; see Hono on Cloudflare.
  • http.client spans with sentry-trace and baggage headers on outgoing fetch. Calls through service bindings and Durable Object stubs carry the headers but get no span of their own.
  • Spans for D1 queries, R2 operations and Queue producers on the env the handler receives, without wrapping anything. Workers AI calls are instrumented in code but were not exercised in this audit.
  • Logs from Sentry.logger.* and console breadcrumbs.

Durable Objects, Workflows and Agents are classes, not handlers, and need their own wrapper. A wrapped Durable Object also records a span per webSocketMessage, per webSocketClose and per alarm, next to its storage spans: Durable Objects, Workflows, Agents SDK.

Not included: KV operations produce no spans, and there are no automatic release health sessions on Workers. For sessions, add @sentry/core as a direct dependency and call its startSession() and endSession() inside the handler; @sentry/cloudflare does not re-export them.

Work you hand to ctx.waitUntil() runs after the handler returned, and an error thrown there is not captured. Attach the capture yourself:

typescriptctx.waitUntil(work().catch((e) => Sentry.captureException(e)));

Do not await Sentry.flush() inside that task on SDK 10.x; the end-of-request flush already waits for every waitUntil promise.

Before SDK 11.0

On SDK 10.x, dataCollection: { httpBodies: [] } does not switch off incoming request bodies on Workers; pass integrations: [Sentry.httpServerIntegration({ maxRequestBodySize: "none" })] instead. Also on 10.x, all scheduled and queue runs of one isolate share a trace id.

3. Instrument bundled libraries with Vite (recommended)

Database drivers and AI SDKs are bundled into the Worker, so the runtime cannot patch them. Build with Vite and the Sentry plugin, which injects node:diagnostics_channel events into those packages at build time and wraps your Worker entry for you:

vite.config.tsimport { cloudflare } from "@cloudflare/vite-plugin";
import { sentryCloudflareVitePlugin } from "@sentry/cloudflare/vite";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [cloudflare(), sentryCloudflareVitePlugin()],
});
bashvite build
npx wrangler deploy --config dist/my-worker/wrangler.json

vite dev is instrumented the same way. The plugin also wraps the default export and any Durable Object, Workflow, Agent or WorkerEntrypoint class listed in the wrangler config, and adds those bindings to rpcTracePropagationBindings, so with the plugin in place you can leave withSentry out of your code. Keep step 2 for builds that do not go through Vite. Options and the list of instrumented packages: Vite plugin.

On SDK versions before 11.0 the plugin is a no-op unless you pass sentryCloudflareVitePlugin({ _experimental: { useDiagnosticsChannelInjection: true } }), and it never wraps your entry, so keep withSentry.

4. Verify

src/index.tsasync fetch(request, env, ctx) {
  const { pathname } = new URL(request.url);
  if (pathname === "/debug-sentry") {
    throw new Error("My first Sentry error!");
  }
  if (pathname === "/debug-span") {
    await Sentry.startSpan({ op: "test", name: "My First Test Span" }, async () => {
      await fetch("https://example.com");
    });
    Sentry.logger.info("Span recorded", { route: pathname });
  }
  return new Response("ok");
},

In Sentry you should see one issue, two GET traces (one with an error, one with a child span and an http.client span) and one log line. Spans measure wall time between I/O; CPU-only work shows as 0ms on Workers.

Node HTTP frameworks on Workers

Express, Koa, Hapi and NestJS run on Workers behind Cloudflare's Node HTTP server support. Set both compatibility flags and serve through httpServerHandler.

wrangler.jsonc{
  "compatibility_date": "2026-05-01",
  "compatibility_flags": ["nodejs_compat", "enable_nodejs_http_server_modules"]
}
src/index.tsimport { httpServerHandler } from "cloudflare:node";
import * as Sentry from "@sentry/cloudflare";

export default Sentry.withSentry(
  (env) => ({ dsn: "___PUBLIC_DSN___", tracesSampleRate: 1.0 }),
  httpServerHandler({ port: 8080 }),
);

Route names, framework spans and database spans need the channels injected at build time. Build with Vite and sentryCloudflareVitePlugin(), or with sentryOrchestrionPlugin() from @sentry/server-utils/orchestrion/esbuild. A Worker bundled by wrangler alone produces none of them and logs no warning.

FrameworkWhat to add
ExpressBuild with the Vite plugin: it injects the Express channels, so route errors, route names and handler spans arrive with no extra call. On a wrangler-only build none of the three exist.
KoaConstruct the app, register middleware and listen inside the fetch handler, not at module scope: instrumented middleware registration starts a span, and workerd forbids that at startup. The Vite plugin registers the error listener for you.
HapiAn onRequest extension that drops workerd's premature close event, or hapi turns every response into a 499 and its error event never fires.
NestJSThe documented Node wiring: SentryModule.forRoot() and SentryGlobalFilter as APP_FILTER. With mysql2 pass disableEval: true to createPool.
FastifyDoes not run on Workers. Module-scope construction is rejected, and lazy construction hits a second restriction.

Oak, Fresh and Elysia also run on Workers. Elysia needs new Elysia({ aot: false }). Oak and Fresh need a middleware to name the root span. Full records in the deep probe report.

src/hooks.server.ts (SvelteKit route names)import { getActiveSpan, getRootSpan, initCloudflareSentryHandle, sentryHandle } from "@sentry/sveltekit";
import { sequence } from "@sveltejs/kit/hooks";

const nameRootSpanByRoute = ({ event, resolve }) => {
  const routeId = event.route?.id;
  const activeSpan = getActiveSpan();
  if (routeId && activeSpan && !event.isSubRequest) {
    const rootSpan = getRootSpan(activeSpan);
    rootSpan.updateName(`${event.request.method} ${routeId}`);
    rootSpan.setAttributes({ "sentry.segment.name.source": "route", "http.route": routeId });
  }
  return resolve(event);
};

Findings that came out of the quick-start runs

  • K11 (Bun, code). In a plugin build, a driver whose instrumented module first loads inside a request (mysql's lib/Connection.js loads on createConnection) never gets spans, on every later request too; a connection created at module scope does. Same on develop and 10.73.0, bun 1.4.0 and 1.3.14. On bun 1.4.0 the injected channel itself stops firing in that case (../qs/chan/scenario-lazy.mjs), on 1.3.14 it fires and only the SDK span is missing. Repro: ../qs/bun/app-noend.ts versus app-modconn.ts. The e2e app bun-mysql creates its connection at module scope, so CI cannot see this.
  • K12 (Deno, docs and code). @sentry/deno/import only transforms packages under a local node_modules; with Deno's default npm cache layout nothing is injected and nothing warns. The guide sets nodeModulesDir: "auto"; the SDK should warn when the hook registered and no node_modules path was ever seen.
  • The 10.x Bun plugin build instruments database drivers but not Express, Koa, Hapi or Fastify; the guide's step 3 wording ("Express, Koa, Hapi and Fastify integrations") is true on develop only. The 10.x page needs the shorter list.
