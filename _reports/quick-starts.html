Runtime Quick Starts

Proposed quick start pages for the Bun, Deno and Cloudflare guides. Each step was run as written against the develop build, and the deep probe report fed back the caveats. The last section maps every claim to its run.

Bun

Works with Bun 1.3.14 or later. Runtime spans (errors, Bun.serve requests, fetch, logs) work on every supported Bun version. Library spans (databases, AI SDKs, Express, Koa, Hapi) need a bundle built with the Sentry plugin, see step 3. Fastify and mysql2 3.20 or later publish their own events and need no build step. For drivers Sentry instruments by code injection, mysql@2 among them, import the driver and create the client at module scope: a module that first loads inside a request records no spans, on every Bun version. Drivers that publish their own channels, mysql2 3.20 or later among them, are not affected. See Bun runtime notes.

Before SDK 11.0

On SDK 10.x, outgoing fetch and node:http servers (Express, Koa, Hapi, Fastify, next start) are not instrumented on Bun: no fetch spans or trace headers, and no request isolation on node:http. The plugin build (step 3) adds database and AI spans only. See Bun on SDK 10.x for the two workarounds.

1. Install

bashbun add @sentry/bun

2. Configure

Create instrument.ts and preload it. Everything the SDK wraps (Bun.serve, fetch, node:http, uncaught errors) is patched when init() runs, so it has to run before the rest of your app loads, and a preloaded module was evaluated once per process in our runs, also under bun --hot.

instrument.tsimport * as Sentry from "@sentry/bun";

Sentry.init({
  dsn: "___PUBLIC_DSN___",

  // Capture 100% of transactions. Lower this in production.
  tracesSampleRate: 1.0,

  // User data and headers are sent by default; Bun.serve never sends request bodies.
  // To keep user data out: dataCollection: { userInfo: false },
});
app.tsimport * as Sentry from "@sentry/bun";

Bun.serve({
  port: 3000,
  routes: {
    "/users/:id": (req) => Response.json({ id: req.params.id }),
  },
});
bashbun --preload ./instrument.ts app.ts

Or add preload = ["./instrument.ts"] to bunfig.toml and run bun app.ts. An import "./instrument"; as the first line of the entry file also works for bun app.ts and bun --watch, but not for bun --hot, which re-evaluates the entry on every reload and then records one extra request span per reload.

This is enough for:

  • Uncaught errors, unhandled rejections and errors thrown from Bun.serve routes.
  • An http.server span per request; a streamed response ends it when the handler returns, not when the stream closes. Routes declared in Bun.serve({ routes }) are named by their pattern (GET /users/:id); a plain fetch handler is named by method only.
  • http.client spans with sentry-trace and baggage headers on outgoing fetch and node:http requests.
  • Logs from Sentry.logger.* and console breadcrumbs.

3. Instrument your libraries

Database drivers, AI SDKs and the Express, Koa and Hapi integrations record spans through node:diagnostics_channel events that the Sentry bundler plugin injects into those packages at build time. bun run on unbundled source cannot inject them, so those integrations stay silent there. Bundle your app with @sentry/bun/plugin:

build.tsimport { sentryBunPlugin } from "@sentry/bun/plugin";

await Bun.build({
  entrypoints: ["./app.ts"],
  outdir: "./dist",
  target: "bun",
  // Keep the SDK external and let the plugin bundle every instrumented package.
  external: ["@sentry/*"],
  // Readable stack traces locally, and the input for source map upload.
  sourcemap: "external",
  plugins: [sentryBunPlugin()],
});
bashbun run build.ts
bun --preload ./instrument.ts dist/app.js

Instrumented packages listed in external are bundled anyway, because a package that is resolved from node_modules at runtime never passes through the plugin. Run the bundle with bun --preload ./instrument.ts dist/app.js, or bundle instrument.ts in by importing it from the entry.

With debug: true, an unbundled run prints No available Node API to register diagnostics-channel injection hooks; skipping. at startup and No diagnostics-channel injection detected. Channel-based integrations will not record spans. after the first request. Both lines describe exactly the gap this step closes; runtime instrumentation is unaffected by them, and without debug: true nothing is printed at all.

Single-file executables are bundles too, so the plugin applies, but only through the JavaScript API: Bun.build({ compile: { outfile: "./app" }, plugins: [sentryBunPlugin()] }). Drop the external line for a compiled build, because an executable cannot resolve external packages at runtime. bun build --compile on the command line cannot take plugins. Development with bun --watch app.ts records runtime spans only.

4. Verify

Add a route that throws and a manual span, then request them:

app.tsBun.serve({
  routes: {
    "/debug-sentry": () => {
      throw new Error("My first Sentry error!");
    },
    "/debug-span": async () => {
      await Sentry.startSpan({ op: "test", name: "My First Test Span" }, async () => {
        await Bun.sleep(100);
      });
      Sentry.logger.info("Span recorded", { route: "/debug-span" });
      return new Response("ok");
    },
  },
});

In Sentry you should see one issue and two traces: GET /debug-sentry carrying the error, and GET /debug-span carrying the manual span and the outgoing http.client span as children of the request span. Under the default stream lifecycle those three ship in one span envelope and no transaction envelope is sent at all. The error event has no transaction field on Bun, so the issue groups without a route while the request span is still named GET /debug-sentry. The log line arrives on the logger's flush timer, a few seconds later.

5. Add readable stack traces with source maps

Bundled stack traces point into dist/app.js. Inject debug IDs and upload the maps from the sourcemap: "external" build above:

bashnpx @sentry/cli sourcemaps inject ./dist
npx @sentry/cli sourcemaps upload --org ___ORG_SLUG___ --project ___PROJECT_SLUG___ ./dist

The Sentry wizard has no Bun bundler preset; the CLI commands above are the supported path. See Source Maps.

6. Frameworks on Bun

Every framework SDK we tested runs on Bun with the develop line, but they are Node SDKs: Bun never publishes the http.server.request.start channel the Node request span opens from, and Node's fetch instrumentation listens on undici channels Bun's native fetch never emits. Install @sentry/bun next to your framework SDK and add the integrations that server needs to its server init. That restores request spans, per-request isolation, incoming trace continuation and outgoing fetch spans. The table below lists what each framework needs on top.

sentry.server.config.ts (Nuxt, Next.js, Astro) or the server instrumentation file (SvelteKit, React Router, TanStack Start, SolidStart)import * as Sentry from "@sentry/nuxt"; // or @sentry/nextjs, @sentry/sveltekit, @sentry/astro, ...
import { bunServerIntegration, bunHttpServerIntegration, fetchIntegration } from "@sentry/bun";

const onBun = typeof Bun !== "undefined";

Sentry.init({
  dsn: "___PUBLIC_DSN___",
  tracesSampleRate: 1.0,
  // Only on Bun, so the same file works under Node without duplicate spans.
  integrations: onBun
    ? [fetchIntegration(), bunServerIntegration(), bunHttpServerIntegration()]
    : [],
});

bunServerIntegration covers servers built on Bun.serve (Nitro's bun preset), bunHttpServerIntegration covers node:http servers (Express custom servers, SvelteKit's adapter-node output, Nitro's node-server preset). Adding both is safe. Keep the onBun gate on fetchIntegration: the same build under Node emits two http.client spans per request without it.

Database and cache spans need one more line, because Bun garbage-collects a diagnostics_channel object that only Sentry's subscriber holds, so the subscriptions made at init() are gone a tick later. Pin the channels for the drivers you use right after Sentry.init(). It is harmless on Node, so it can be applied unconditionally:

same file, after Sentry.init()import * as dc from "node:diagnostics_channel";

globalThis.__sentryPinnedChannels ??= [
  "mysql2:query", "mysql2:execute", "mysql2:connect", "mysql2:pool:connect",
  "ioredis:command", "ioredis:connect",
  "orchestrion:mysql:query", "orchestrion:mysql2:query", "orchestrion:mysql2:execute",
].map((name) => dc.tracingChannel(name));

Deno

Works with Deno 2.8.3 or later. The SDK is in beta.

1. Install

bashdeno add npm:@sentry/deno

Add nodeModulesDir to deno.json. The library instrumentation in step 3 rewrites packages while they load, and it only sees packages that live in a local node_modules directory, not in Deno's global npm cache. "auto" is the value that pairs with deno add; every run behind this page used "manual" with the packages put in place by npm install, which is what the framework rows assume too.

deno.json{
  "nodeModulesDir": "auto",
  "imports": {
    "@sentry/deno": "npm:@sentry/deno"
  }
}

2. Configure

Initialize the SDK at the top of your entry file. The first import registers the library instrumentation hook (step 3); it has to be the first import of the program, before any package you want instrumented has loaded.

main.tsimport "@sentry/deno/import";
import * as Sentry from "@sentry/deno";

Sentry.init({
  dsn: "___PUBLIC_DSN___",

  // Capture 100% of transactions. Lower this in production.
  tracesSampleRate: 1.0,

  // User data, headers and HTTP bodies are sent by default. To keep them out:
  // dataCollection: { userInfo: false, httpBodies: [] },
});

Deno.serve({ port: 3000 }, (req) => new Response("Hello"));

Run it with the permissions the SDK uses:

bashdeno run --allow-net --allow-env --allow-read=. --allow-sys=hostname,osRelease main.ts
FlagWhat it unlocks
--allow-netSending events. Narrow it to your ingest host: --allow-net=___ORG_INGEST_DOMAIN___, plus whatever your app needs.
--allow-envRequired by the first-line @sentry/deno/import hook, which exits with NotCapable: Requires env access without it. Also SENTRY_DSN, SENTRY_RELEASE and the other SENTRY_* variables.
--allow-read=.Source lines in stack traces and app:// paths instead of absolute file paths. Read access is checked per file for the context lines and on the working directory for the path normalization, so the flag has to cover both your entry file and the directory you start from.
--allow-sys=hostname,osReleaseserver_name and the OS version on events.

A missing --allow-read or --allow-sys is skipped silently: the events simply arrive without context lines, app:// paths, server_name or the OS version, with no warning and no permission prompt. A missing --allow-env is not silent, it is fatal: the hook exits the process before any of your code runs.

The same applies to deno serve: export default { fetch } is instrumented like Deno.serve, and deno serve --parallel starts one SDK per worker without duplicating anything.

This is enough for:

  • Uncaught errors, unhandled rejections and errors thrown from Deno.serve handlers.
  • An http.server span per Deno.serve request, named by HTTP method. Deno.serve has no router, so route names come from a framework; see Frameworks on Deno.
  • Server and client spans for node:http, with sentry-trace and baggage headers on outgoing node:http requests. A synchronous throw inside a node:http listener is swallowed by Deno and never reaches Sentry; catch and report it yourself.
  • Logs from Sentry.logger.*, plus console and fetch breadcrumbs.

Outgoing fetch() calls record a breadcrumb only. They get no span and no sentry-trace/baggage headers, so a trace ends at the first fetch to another service. @sentry/deno ships no fetch integration; two shipped ones run unmodified on Deno and close the gap, see Frameworks on Deno. Requests made with node:http/node:https are traced and propagated without any of that.

3. Instrument your libraries

The import "@sentry/deno/import" line from step 2 installs a module hook that injects node:diagnostics_channel events into database drivers, AI SDKs and web frameworks as they load. With it in place, mysql, pg, postgres, mongodb, ioredis, the AI SDKs and the rest of the integration list record spans without further setup, as long as the package loads its CommonJS build, see the second limit below. Fastify and mysql2 (3.20 or later) publish their own events and work without the hook. Hono is a plain fetch handler and needs no hook either.

Two Deno limits apply to the hook. First, a Deno bug makes every require() of a JSON file fail once a module hook is registered (denoland/deno#36240), so Express, Hapi, NestJS, Koa's dependencies and mysql2 fail at import. Register this second hook right after the Sentry import:

main.tsimport "@sentry/deno/import";
import { registerHooks } from "node:module";
registerHooks({
  load(url, context, next) {
    const result = next(url, context);
    if (result && result.format == null && url.endsWith(".json")) result.format = "json";
    return result;
  },
});

Fastify is the exception: it publishes its own channels, needs no hook, and dies at import inside ajv when one is registered, so leave the import line out of a Fastify app.

Second, the hook transforms CommonJS builds only. A package that loads its ES module build is not instrumented, and the OpenAI SDK is the case that was measured: only a createRequire load of it produced gen_ai spans, while a static ESM import came back untransformed.

If you forget the import, the SDK still installs the integrations and records nothing for those libraries, without a warning.

4. Verify

main.tsDeno.serve({ port: 3000 }, async (req) => {
  const { pathname } = new URL(req.url);
  if (pathname === "/debug-sentry") {
    throw new Error("My first Sentry error!");
  }
  if (pathname === "/debug-span") {
    await Sentry.startSpan({ op: "test", name: "My First Test Span" }, async () => {
      await new Promise((resolve) => setTimeout(resolve, 100));
    });
    Sentry.logger.info("Span recorded", { route: pathname });
  }
  return new Response("ok");
});

In Sentry you should see one issue and two traces, both named GET with source url: Deno.serve has no router, so the base setup names every server span by method. Under the default stream lifecycle the manual span ships in the same span envelope as the request span and no transaction envelope is sent; the error event carries no transaction field. One log line arrives on the flush timer.

5. Source maps

Deno runs your TypeScript directly, so stack traces point at your source files and no upload is needed for a plain deno run. If you bundle for deployment (deno bundle, esbuild), upload the maps with npx @sentry/cli sourcemaps inject and upload. See Source Maps.

6. Frameworks on Deno

Hono, Oak, Fresh, Elysia, Express, Fastify, Koa, Hapi, NestJS, Next.js, Nuxt, SvelteKit, Astro, React Router, Remix, TanStack Start and SolidStart all run on Deno with the develop line, and errors, route names, isolation and incoming traces work for most of them with the wiring from steps 1 to 3. Two things cut across the whole table.

Outgoing fetch() is not traced on Deno. The Deno SDK instruments node:http/node:https only, so a global fetch() gets no http.client span and no sentry-trace/baggage headers and the trace stops at the first downstream service. @sentry/deno ships no fetch integration of its own, and two shipped ones from other packages run unmodified on Deno: fetchIntegration() from @sentry/cloudflare and winterCGFetchIntegration() from @sentry/vercel-edge. Which one is at hand depends on the framework, because some framework SDKs already depend on one of the two; the table names it per row. Both are an extra dependency when nothing pulls them in already.

instrument.tsimport "@sentry/deno/import";
import * as Sentry from "@sentry/deno";
import { fetchIntegration } from "@sentry/cloudflare"; // or: winterCGFetchIntegration from "@sentry/vercel-edge"

Sentry.init({
  dsn: "___PUBLIC_DSN___",
  tracesSampleRate: 1.0,
  integrations: [fetchIntegration()],
});

Do not hand-write a fetch integration on top of @sentry/core primitives instead. In the Remix cell that shape propagated the headers and then suppressed every server transaction and span envelope for the whole process, while errors kept arriving; the same wiring on Remix is served by installGlobals(), whose polyfilled fetch runs on node:http.

The import hook and CommonJS JSON. Registering any load hook on Deno 2.9 breaks require("*.json") inside CommonJS packages (Hapi, Koa's dependencies, NestJS). Add a JSON hook next to the Sentry import, or skip the hook and bundle with esbuild and sentryOrchestrionPlugin() from @sentry/server-utils/orchestrion/esbuild:

instrument.ts, before the framework importimport * as Module from "node:module";

Module.registerHooks({
  load(url, context, nextLoad) {
    const result = nextLoad(url, context);
    return url.endsWith(".json") ? { ...result, format: "json", shortCircuit: true } : result;
  },
});

Cloudflare

Using a framework? Astro, Hono, Hydrogen, Next.js, Nuxt, React Router, Remix, SvelteKit and TanStack Start each have their own page under Frameworks on Cloudflare. This page covers a plain Worker. For Cloudflare Pages, see Cloudflare Pages.

1. Install

bashnpm install @sentry/cloudflare

2. Configure

The SDK needs Node.js APIs from the Workers runtime. Enable nodejs_compat with a compatibility_date of 2024-09-23 or later (withSentry needs it; the request wrapper from @sentry/cloudflare/request boots with nodejs_als alone, but on develop pass it traceLifecycle: "static", because that entry has no async context strategy under the streaming default; its events also carry no request data and it establishes no per-request isolation):

wrangler.jsonc{
  "name": "my-worker",
  "main": "src/index.ts",
  "compatibility_date": "2024-09-23",
  "compatibility_flags": ["nodejs_compat"]
}

Wrap the Worker's exported handler with withSentry. The options callback receives env, so secrets and per-environment settings can come from bindings.

src/index.tsimport * as Sentry from "@sentry/cloudflare";

export default Sentry.withSentry(
  (env) => ({
    dsn: "___PUBLIC_DSN___",

    // Capture 100% of transactions. Lower this in production.
    tracesSampleRate: 1.0,

    // Send user data and HTTP bodies with events. Remove to keep the defaults.
    dataCollection: {},
  }),
  {
    async fetch(request, env, ctx) {
      return new Response("Hello");
    },
  } satisfies ExportedHandler<Env>,
);
bashnpx wrangler dev

This is enough for:

  • Errors thrown from fetch, scheduled and queue handlers. The email and tail handlers are wrapped too, but were not exercised in this audit.
  • An http.server span per request, named by HTTP method. Route names come from a framework; see Hono on Cloudflare.
  • http.client spans with sentry-trace and baggage headers on outgoing fetch. Calls through service bindings and Durable Object stubs carry the headers but get no span of their own.
  • Spans for D1 queries, R2 operations and Queue producers on the env the handler receives, without wrapping anything. Workers AI calls are instrumented in code but were not exercised in this audit.
  • Logs from Sentry.logger.* and console breadcrumbs.

Durable Objects, Workflows and Agents are classes, not handlers, and need their own wrapper. A wrapped Durable Object also records one span per webSocketMessage, webSocketClose, webSocketError and alarm invocation, next to its storage spans; the alarm span starts a new trace linked back to the setAlarm span, and errors from those four handlers arrive with mechanism auto.faas.cloudflare.durable_object: Durable Objects, Workflows, Agents SDK.

Not included: KV operations produce no spans, and Workers send no release health sessions. @sentry/cloudflare exports none of startSession, endSession or captureSession, so the session APIs documented for the other SDKs do not exist here; the exported Session is a type only, which is why editor autocomplete suggests otherwise.

Work you hand to ctx.waitUntil() runs after the handler returned. An error thrown or a promise rejected there is not captured, on either trace lifecycle: the SDK hands the promise to the invocation and attaches no error capture to it. Attach one yourself:

typescriptctx.waitUntil(work().catch((e) => Sentry.captureException(e)));

The end-of-request flush already waits for every waitUntil promise, so the deferred work still gets its events out.

Before SDK 11.0

On SDK 10.x, dataCollection: { httpBodies: [] } does not switch off incoming request bodies on Workers; pass integrations: [Sentry.httpServerIntegration({ maxRequestBodySize: "none" })] instead. Also on 10.x, all scheduled and queue runs of one isolate share a trace id.

3. Instrument bundled libraries with Vite (recommended)

Database drivers and AI SDKs are bundled into the Worker, so the runtime cannot patch them. Build with Vite and the Sentry plugin, which injects node:diagnostics_channel events into those packages at build time and wraps your Worker entry for you:

vite.config.tsimport { cloudflare } from "@cloudflare/vite-plugin";
import { sentryCloudflareVitePlugin } from "@sentry/cloudflare/vite";
import { defineConfig } from "vite";

export default defineConfig({
  plugins: [cloudflare(), sentryCloudflareVitePlugin()],
});
bashvite build
npx wrangler deploy --config dist/my-worker/wrangler.json

vite dev is instrumented the same way. The plugin also wraps the default export and any Durable Object, Workflow, Agent or WorkerEntrypoint class listed in the wrangler config, and adds those bindings to rpcTracePropagationBindings, so with the plugin in place you can leave withSentry out of your code. It takes the options from an instrument.server.{ts,mts,js,mjs,cjs} file next to the wrangler main, whose default export is the options callback; with no such file the Worker reads the DSN, release, environment and sample rate from its env bindings at runtime instead. Keep step 2 for builds that do not go through Vite. Options and the list of instrumented packages: Vite plugin.

Pass wranglerConfigPath whenever the project holds more than one wrangler config, not only when the config sits at a custom path. The plugin takes the first default-named wrangler.json, wrangler.jsonc or wrangler.toml at the Vite root, and if that is not the Worker being built it instruments nothing while the build still succeeds: it only warns when no config parses at all. The check is the built entry, which contains a withSentry wrapper when auto-instrumentation ran.

On SDK versions before 11.0 the plugin is a no-op unless you pass sentryCloudflareVitePlugin({ _experimental: { useDiagnosticsChannelInjection: true } }), and it never wraps your entry, so keep withSentry.

4. Verify

src/index.tsasync fetch(request, env, ctx) {
  const { pathname } = new URL(request.url);
  if (pathname === "/debug-sentry") {
    throw new Error("My first Sentry error!");
  }
  if (pathname === "/debug-span") {
    await Sentry.startSpan({ op: "test", name: "My First Test Span" }, async () => {

In Sentry you should see one issue and two traces, both named GET with source url, one with the error and one carrying the manual span and the http.client span, plus one log line. Node HTTP frameworks on Workers

Express, Koa, Hapi and NestJS run on Workers behind Cloudflare's Node HTTP server support. Set both compatibility flags and serve through httpServerHandler.

wrangler.jsonc{
  "compatibility_date": "2026-05-01",
  "compatibility_flags": ["nodejs_compat", "enable_nodejs_http_server_modules"]

src/index.tsimport { httpServerHandler } from "cloudflare:node";

export default Sentry.withSentry(
  (env) => ({ dsn: "___PUBLIC_DSN___", tracesSampleRate: 1.0 }),
  httpServerHandler({ port: 8080 }),
);

Route names, framework spans and database spans come from channels injected at build time. Build with Vite and sentryCloudflareVitePlugin(), or pre-bundle the Worker with sentryOrchestrionPlugin() from @sentry/server-utils/orchestrion/esbuild and point wrangler's main at the output; wrangler's own bundler takes no plugins. Once instrumentation runs at build time, construct the app and start it inside the first fetch, never at module scope: the injected wrapper starts a span and workerd rejects that with "Disallowed operation called within global scope". A Worker bundled by wrangler alone still gets isolation, incoming trace continuation, outgoing fetch spans and logs, and no database spans at all; error capture and route names are then app-side, per framework below. mysql 2.x works unchanged; mysql2 needs disableEval: true in its connection options, with the connection opened inside the request handler.

Findings that came out of the quick-start runs

  • No transaction envelope is sent on any of the three runtimes. Under the default stream lifecycle the manual verify span ships as a child item inside a span envelope next to the request span, so the sample name "My First Test Transaction" that the shipped guides use no longer matches what arrives. Setting traceLifecycle: "static" brings the transaction envelope back, as the Cloudflare request variant shows.
  • Bun and Cloudflare error events carry no transaction field. The issue therefore groups without a route, although the request span is route-named on Bun. The same error on Node carries transaction: "GET /debug-sentry", so this is a runtime difference, not a property of the verify snippet. Files: quickstarts/bun/results-preload.json, quickstarts/cloudflare/results-base.json, quickstarts/node/results-import.json.
  • The documented Bun path warns twice about missing channel injection. Both lines are correct, both print only with debug: true, and no page explains which of the two a reader is looking at. Runtime instrumentation is unaffected; the plugin build in step 3 is what the lines are about. File: quickstarts/bun/app-preload.log.
  • The Deno guide's own flag set cannot start an app that carries the hook line. deno run --no-prompt --allow-net main.ts exits with NotCapable: Requires env access before any user code runs. Without the hook line the same flags do start the app, and then silently cost server_name, the OS version, context lines and app:/// paths, with nothing printed.
