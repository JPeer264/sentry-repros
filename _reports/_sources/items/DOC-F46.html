Document route naming and database-span setup for SvelteKit on Cloudflare Workers

Description

The combination is documented. docs/platforms/javascript/guides/cloudflare/frameworks/sveltekit.mdx:1-9 is a "SvelteKit on Cloudflare" page that renders the shared include; the Cloudflare branch is platform-includes/getting-started-complete/javascript.sveltekit.mdx:311-365, with the sequence(initCloudflareSentryHandle({...}), sentryHandle()) snippet at :322-352, handleErrorWithSentry at :354-360, "Configure Vite" with sentrySvelteKit() at :369-394 and the wrangler config at :396-405. Two things the run needed are absent: grep -rn noExternal docs/platforms/javascript platform-includes returns zero hits, and no page describes how the segment span is named on Cloudflare.

Verified on the develop line: SvelteKit 2.70 with @sveltejs/adapter-cloudflare 5, compatibility_date: "2026-05-01", compatibility_flags: ["nodejs_compat"], sentrySvelteKit() from @sentry/sveltekit/vite before sveltekit(), and src/hooks.server.ts exactly as the include shows. vite build, then wrangler dev.

Works today:

  • Unhandled errors through handleErrorWithSentry (mechanism auto.function.sveltekit.handle_error), per-request isolation, incoming trace continuation, outgoing fetch spans with propagation headers, Sentry.logger logs.
  • db spans from the build-time transform sentrySvelteKit() already installs, with no extra configuration on a pnpm install.

Known limits:

  • The transaction/segment span is named from the raw URL under traceLifecycle: 'static' and by HTTP method alone under the default 'stream'; the SvelteKit route id and http.route only reach a child span.
  • On a flat node_modules (npm or Yarn) the build fails until ssr: { noExternal: ['@sentry/core', '@sentry/conventions', '@opentelemetry/api'] } is added to vite.config.js.

What to change on docs/platforms/javascript/guides/cloudflare/frameworks/sveltekit.mdx:

  • Keep the include and add a "Route Names on Cloudflare Workers" section stating the naming limit above.
  • Add a "Database Spans" section stating that no extra setup is needed on pnpm and giving the ssr.noExternal entry for npm and Yarn installs.

Page: docs/platforms/javascript/guides/cloudflare/frameworks/sveltekit.mdx — replace the bare include passthrough with a page that keeps the include and adds "Route Names on Cloudflare Workers" (the raw-URL naming plus the intermediate `handle` workaround) and "Database Spans" (the npm/Yarn `ssr.noExternal` requirement) sections

Two things the run needed are absent from the include. (1) Route names are confirmed broken on Workers: unlike the Node SvelteKit SDK, the transaction/segment span is named by the Cloudflare request handler and keeps the raw URL — `GET /users/42` with `transaction_info.source: url` under `traceLifecycle: 'static'`, and bare `GET` with source `url` under the default `traceLifecycle: 'stream'` — never the SvelteKit route id. The page must state this and show the verified fix: a user-land `handle` inserted between `initCloudflareSentryHandle` and `sentryHandle` in the `sequence`, which renames the Cloudflare segment span using `getActiveSpan`/`getRootSpan` from `@sentry/sveltekit`; it works in both lifecycles. (2) Database spans come from the build-time transform that `sentrySvelteKit()` (:387) already installs, so no extra setup is needed and the connection may live at module scope or inside the handler — but only on pnpm's isolated `node_modules`. On a flat `node_modules` (npm or Yarn) the spans are missing until `ssr: { noExternal: [/^@sentry\//] }` is added to `vite.config.js`; that single regex is the minimal fix (naming only `@sentry/core` is not enough, and `@opentelemetry/api` need not be listed).
