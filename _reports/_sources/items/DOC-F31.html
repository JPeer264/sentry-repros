Add a React Router on Deno page with the Deno entry.server and Vite config

Description

docs/platforms/javascript/guides/react-router/ contains only index.mdx, manual-setup.mdx and profiling/, and grep -rni deno over it returns nothing; the reverse grep over guides/deno/ also returns nothing. The guide is Node-shaped throughout: index.mdx:7 categorises it server-node, and manual-setup.mdx:413-414 gives the only start command, a Node one.

Verified on React Router 7 in framework mode with @sentry/react-router 10.67.0 on Deno 2.9.0: npm install the app packages and the Sentry packages into a real node_modules, deno.json with {"nodeModulesDir": "manual"}. app/entry.server.tsx must use the web-stream renderer, renderToReadableStream from react-dom/server, because Deno resolves react-dom/server through the deno export condition and there is no renderToPipeableStream; wrap it with wrapSentryHandleRequest and export handleError = createSentryHandleError({ logErrors: true }). Add the sentryReactRouter Vite plugin and set ssr: { noExternal: true, external: ['@sentry/react-router', '@sentry/node'] } in vite.config.ts so drivers are instrumented at build time.

Works today:

  • Loader errors, mechanism react-router, surfaced by the handleError export.
  • GET /users/:id with op http.server and source route.
  • Per-request isolation and incoming trace continuation.
  • Database spans, with the Vite plugin and the ssr config above.
  • Logs.

Known limits:

  • Outgoing fetch() is not instrumented on Deno: no http.client span and no sentry-trace/baggage headers, so the trace ends at the server. node:http requests are traced and propagated.
  • Error events carry the raw path in their transaction field while the transaction itself carries the route pattern.

What to change:

  • Add docs/platforms/javascript/guides/deno/frameworks/react-router.mdx and cross-link it from guides/react-router/manual-setup.mdx near :413-414.

A React Router (framework mode) on Deno page must exist. It must say up front that the app runs on Deno but NOT with the `entry.server.tsx` the current guide shows, and give the working entry and install shape (`npm install` of react-router, the Sentry packages and the driver into a real `node_modules`). It must then document the two Deno-specific points. (1) Build-time instrumentation is required instead of the runtime require hook: add the documented `sentryReactRouter` Vite plugin, and set `ssr: { noExternal: true, external: ['@sentry/react-router', '@sentry/node'] }` in `vite.config.ts` so the injected snippet's CommonJS chunk does not default-import ESM-only `@sentry/core`. Without this, database spans are missing, because Deno cannot compile the `require('./package.json')` calls drivers such as mysql2 make at load time. (2) Outgoing requests made with Deno's built-in global `fetch` are not traced — no `http.client` span is created and no `sentry-trace`/`baggage` headers are attached — because Deno's `fetch` is native and does not emit the undici `diagnostics_channel` events the Node SDK subscribes to, so the trace ends at the server. The verified fix that needs no extra dependency is a userland integration passed to `Sentry.init`: `defineIntegration(() => ({ name: 'DenoFetch', setupOnce() { addFetchInstrumentationHandler(d => { const client = getClient(); if (!client || isSentryRequestUrl(d.fetchData.url, client)) return; instrumentFetchRequest(...); }); } }))` from public `@sentry/core` exports. Errors, route names, isolation, incoming trace continuation and logs all work.
