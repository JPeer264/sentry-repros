Proposed issue docs-change

Stop recommending denoCronIntegration() on the Deno crons page

Description

platform-includes/crons/setup/javascript.deno.mdx:1 heads its first section "Automatic Check-Ins (Recommended)" and :12 tells the reader to pass Sentry.denoCronIntegration() to Sentry.init.

That call crashes startup on Deno 2.9.0 and later. packages/deno/src/integrations/deno-cron.ts:23 assigns Deno.cron = new Proxy(Deno.cron, ...) inside setupOnce, i.e. inside Sentry.init. On Deno 2.8.3 Deno.cron is a writable data property and the integration works: a cron firing at the minute boundary produced one in_progress and one ok check-in. From Deno 2.9.0 Deno.cron is a getter-only accessor, so the assignment throws TypeError: Cannot set property cron of #<Object> which has only a getter and the process exits 1 before any user code runs.

There is a second failure mode without the unstable flag. When Deno.cron is absent the guard at deno-cron.ts:18-21 returns silently, so the integration is an inert no-op and the SDK gives no warning, while the reader's own Deno.cron(...) call throws TypeError: Deno.cron is not a function. The integration is also not in the Deno default set (packages/deno/src/sdk.ts:31-49), although its own JSDoc at deno-cron.ts:64 says "Enabled by default in the Deno SDK".

What to change

  • Remove the "Recommended" framing and the denoCronIntegration() snippet, or state that it makes Sentry.init throw on Deno 2.9.0 and later and works only up to Deno 2.8.3.
  • Lead with the Sentry.withMonitor / Sentry.captureCheckIn sections already on the page.
  • State that Deno.cron needs --unstable-cron, and that without the flag the integration silently does nothing.
  • Say that the integration has to be passed in integrations explicitly; it is not in the Deno default set.

Status quo. platform-includes/crons/setup/javascript.deno.mdx:1 heads the section "Automatic Check-Ins (Recommended)" and :12 shows `integrations: [Sentry.denoCronIntegration()]` as the way to monitor `Deno.cron` calls.

On develop. packages/deno/src/integrations/deno-cron.ts:23 assigns `Deno.cron = new Proxy(Deno.cron, ...)` in `setupOnce`. probes/D11 recorded the version split: on Deno 2.8.3 `Deno.cron` is a writable data property and the integration works (one `in_progress` and one `ok` check-in for monitor slug `probe`); on Deno 2.9.0 it is a getter-only accessor, so `Sentry.init` throws `TypeError: Cannot set property cron of #<Object> which has only a getter` and the process exits 1. Without `--unstable-cron` the guard at deno-cron.ts:18-21 returns silently, so the integration is an inert no-op and the user's own `Deno.cron(...)` throws `TypeError: Deno.cron is not a function`. The integration is also absent from the default set at packages/deno/src/sdk.ts:31-49, contradicting its own JSDoc at deno-cron.ts:64.

Work item. Drop the "Recommended" framing and the `denoCronIntegration()` snippet, or mark the integration as broken on Deno 2.9.0 and later. Lead the page with the `Sentry.withMonitor` / `Sentry.captureCheckIn` path that the other sections already document, state the `--unstable-cron` requirement and the silent no-op without it, and say the integration must be added explicitly. SDK side, D11 also recorded that `Object.defineProperty(Deno, 'cron', { value, writable: true, configurable: true })` succeeds on both Deno versions, so a one-line SDK fix would restore the integration; the docs change should link that follow-up rather than only steering readers away, and the JSDoc-versus-defaults contradiction is a separate SDK bug.
