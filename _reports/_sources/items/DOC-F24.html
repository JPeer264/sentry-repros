Add an Oak on Deno page: mount with Deno.serve(app.fetch)

Description

Oak appears nowhere in the docs: grep -rin '\boak\b' docs/ platform-includes/ and grep -rl '@oak/oak\|jsr:@oak' docs/ return nothing. docs/platforms/javascript/guides/deno/index.mdx:1-232 names no framework and never mentions Deno.serve, only bare deno run at :106 and :125; the Deno guide directory holds just index.mdx and two integration pages.

Verified on Oak 17.2.0 (jsr:@oak/oak) and Deno 2.9.0: deno.json with {"nodeModulesDir": "manual"} and imports for @oak/oak and @sentry/deno, @sentry/deno present in a real node_modules, plus npm install path-to-regexp@6.3.0, which Oak needs to boot under manual nodeModulesDir. Put import "@sentry/deno/import"; as the first line of the instrument file, then Sentry.init(), and mount the app with Deno.serve(app.fetch). Name routes with a router.use() middleware registered before the routes that calls Sentry.updateSpanName(Sentry.getActiveSpan(), \${ctx.request.method} ${ctx.matched?.at(-1)?.path}\) and sets Sentry.SENTRY_SEGMENT_NAME_SOURCE to route.

Works today:

  • Route errors, mechanism auto.http.deno, on the app.fetch path.
  • Per-request isolation and incoming trace continuation.
  • GET /users/:id with source route, via the naming middleware.
  • Database spans for mysql through the import hook, with the driver imported dynamically after init.
  • Logs, correlated to the request trace.

Known limits:

  • app.listen() runs handlers outside the request's async context: no active span, errors are never captured, and tags and trace ids leak between requests. Always mount with Deno.serve(app.fetch).
  • The naming middleware runs after await next(), so error responses keep the unparameterized name.
  • Without the middleware, spans are named by HTTP method or raw path only.
  • Outgoing fetch() is not instrumented; node:http requests are.

What to change:

  • Add docs/platforms/javascript/guides/deno/frameworks/oak.mdx, leading with the mounting rule.

Source: runtime docs audit, item DOC-F24, cell M-oak-deno

Page: guides/deno/frameworks/oak.mdx (new), with the `Deno.serve(app.fetch)` vs `app.listen()` warning as its first section

An Oak page must exist and must lead with the mounting shape, because the two Oak mounting styles are not equivalent for Sentry: mount with `Deno.serve(app.fetch)` and never with `app.listen()` — under `app.listen()` handlers run outside the request's async context, so there is no active span and errors are never captured at all. With `Deno.serve(app.fetch)`, errors, isolation, incoming trace continuation, database spans and logs all work with no extra wiring. Two caveats must be documented. (1) Route names: Oak spans are named by HTTP method only until the app names them; register a `router.use()` middleware BEFORE any route on that router that reads `ctx.matched?.at(-1)?.path` and calls `Sentry.updateSpanName(Sentry.getActiveSpan(), \`${ctx.request.method} ${route}\`)`. (2) Outgoing requests: `@sentry/deno` does not instrument Deno's global `fetch` — no `http.client` span, no `sentry-trace`/`baggage` header, so the downstream service starts a new trace. Two fixes were verified in both trace lifecycles: use `node:http` for the outgoing call (zero code beyond the client swap — `http.get(url, ...)` produced `http.client GET <url>` plus both headers), or keep `fetch` and register a userland fetch integration built from `@sentry/core` primitives. The page must also show the `deno.json` shape the run needed: `{"nodeModulesDir": "manual", "imports": {"@oak/oak": "jsr:@oak/oak@^17", "@sentry/deno": "npm:@sentry/deno"}}` with the SDK present in a real `node_modules`.

Where the docs stand: `grep -rin '\boak\b' docs/ platform-includes/` and `grep -rl '@oak/oak\|jsr:@oak' docs/` return nothing; docs/platforms/javascript/guides/deno/index.mdx:1-232 names no framework and never mentions `Deno.serve` (only bare `deno run` at :106 and :125); guides/deno/ contains only index.mdx and configuration/integrations/{breadcrumbs,contextlines}.mdx
