Proposed issue new-page

Add an Oak on Deno page: mount with Deno.serve(app.fetch)

Description

Oak appears nowhere in the docs: grep -rin '\boak\b' docs/ platform-includes/ and grep -rl '@oak/oak\|jsr:@oak' docs/ return nothing. docs/platforms/javascript/guides/deno/index.mdx:1-230 names no framework and never mentions Deno.serve, only bare deno run at :100 and :119; the Deno guide directory holds just index.mdx and two integration pages.

Verified on Oak 17.2.0 (jsr:@oak/oak) and Deno 2.9.0: deno.json with {"nodeModulesDir": "manual"} and imports for @oak/oak and @sentry/deno, @sentry/deno present in a real node_modules, plus npm install path-to-regexp@6.3.0, which Oak needs to boot under manual nodeModulesDir. Put import "@sentry/deno/import"; as the first line of the instrument file, then Sentry.init(), and mount the app with Deno.serve(app.fetch). Name routes with a middleware registered before app.use(router.routes()) that reads ctx.matched?.at(-1)?.path and, inside try { await next(); } finally { ... }, calls Sentry.updateSpanName(span, `${ctx.request.method} ${route}`) and sets both Sentry.SENTRY_SEGMENT_NAME_SOURCE to route and http.route to the route. A router.use((ctx, next) => { ...; return next(); }) registered before the routes is equivalent.

Works today:

  • Route errors, mechanism auto.http.deno, on the app.fetch path.
  • Per-request isolation and incoming trace continuation.
  • GET /users/:id with source route and http.route set, via the naming middleware, on the success and the error path, in both trace lifecycles, and with prefixed routers (GET /api/users/:id).
  • Database spans for mysql through the import hook, with the driver imported dynamically after init.
  • Logs, correlated to the request trace.

Known limits:

  • app.listen() runs handlers outside the request's async context: no active span, errors are never captured, and tags and trace ids leak between requests. Nothing in user code repairs it, so always mount with Deno.serve(app.fetch).
  • Naming code placed after await next() instead of in a finally block silently skips every request whose handler throws, so those keep the unparameterized name.
  • Without the middleware, spans are named by HTTP method only (stream) or by the raw path with source url (static); there is no Oak integration in @sentry/deno.
  • Oak types app.fetch as a Cloudflare handler, so ctx.request.ip is empty on Deno. The SDK still records the client address, which it takes from the Deno.serve connection info.
  • Outgoing fetch() is not instrumented; node:http requests are.

What to change:

  • Add docs/platforms/javascript/guides/deno/frameworks/oak.mdx, leading with the mounting rule.

Page: guides/deno/frameworks/oak.mdx (new), with the `Deno.serve(app.fetch)` vs `app.listen()` warning as its first section

An Oak page must exist and must lead with the mounting shape, because the two Oak mounting styles are not equivalent for Sentry: mount with `Deno.serve(app.fetch)` and never with `app.listen()` — under `app.listen()` handlers run outside the request's async context, so there is no active span, errors are never captured at all and the isolation scope leaks between requests. With `Deno.serve(app.fetch)`, errors, isolation, incoming trace continuation, database spans and logs all work with no extra wiring. Two caveats must be documented. (1) Route names: Oak spans are named by HTTP method only until the app names them; register a middleware BEFORE `app.use(router.routes())` that reads `ctx.matched?.at(-1)?.path` and names the span inside `try { await next(); } finally { ... }`, calling `Sentry.updateSpanName(span, \`${ctx.request.method} ${route}\`)` and then setting `Sentry.SENTRY_SEGMENT_NAME_SOURCE` to `'route'` and `http.route` to the route. The `finally` is the load-bearing part: the same code written after `await next()` never runs when the handler throws, so error responses keep the raw path. A router-level `router.use((ctx, next) => { ...; return next(); })` behaves identically, and both were verified in the `static` and `stream` lifecycles, including with prefixed routers. SDK-side, `setHttpServerSpanRouteAttribute` from `@sentry/server-utils` does exactly this job but is not re-exported from `@sentry/deno`, which is why the page has to spell the middleware out. (2) Outgoing requests: `@sentry/deno` does not instrument Deno's global `fetch` — no `http.client` span, no `sentry-trace`/`baggage` header, so the downstream service starts a new trace. The verified alternative is to make the call with `node:http` instead (`http.get(url, ...)` produced `http.client GET <url>` plus both headers, in both trace lifecycles); nothing shipped restores it for `fetch` itself on this stack. The page must also show the `deno.json` shape the run needed: `{"nodeModulesDir": "manual", "imports": {"@oak/oak": "jsr:@oak/oak@^17", "@sentry/deno": "npm:@sentry/deno"}}` with the SDK present in a real `node_modules`, and note that `ctx.request.ip` is empty because Oak types `app.fetch` as a Cloudflare handler.

Where the docs stand: `grep -rin '\boak\b' docs/ platform-includes/` and `grep -rl '@oak/oak\|jsr:@oak' docs/` return nothing; docs/platforms/javascript/guides/deno/index.mdx:1-230 names no framework and never mentions `Deno.serve` (only bare `deno run` at :100 and :119); guides/deno/ contains only index.mdx and configuration/integrations/{breadcrumbs,contextlines}.mdx
