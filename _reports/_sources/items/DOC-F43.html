DOC-F43NestJS on Cloudflare: documented noP1proven

Proposed issue new-page

Add a NestJS on Cloudflare Workers page using the esbuild orchestrion plugin

Description

Nothing documents NestJS on Workers. docs/platforms/javascript/guides/nestjs/index.mdx:5-9 sets fallbackGuide: javascript.node with server-node categories and carries no runtime caveat. docs/platforms/javascript/guides/cloudflare/frameworks/ has no nestjs.mdx, the framework list at guides/cloudflare/index.mdx:16-23 omits Nest, and neither httpServerHandler nor sentryOrchestrionPlugin appears anywhere under docs/ or platform-includes/.

Verified on the develop line: NestJS 11 with @nestjs/platform-express on workerd, compatibility_date: "2026-05-01", compatibility_flags: ["nodejs_compat", "enable_nodejs_http_modules", "enable_nodejs_http_server_modules"], served through httpServerHandler from cloudflare:node and wrapped with Sentry.withSentry() from @sentry/cloudflare. Nest must be booted lazily inside fetch, not at module scope. Bundle the Worker with esbuild plus sentryOrchestrionPlugin() from @sentry/server-utils/orchestrion/esbuild and point wrangler's main at the output. Error capture uses exactly the Node wiring: install @sentry/nestjs next to @sentry/cloudflare and register SentryModule.forRoot() in imports and SentryGlobalFilter from @sentry/nestjs/setup as an APP_FILTER provider.

Works today:

  • Unhandled controller errors through SentryGlobalFilter, parameterized route names with middleware and handler spans, per-request isolation, incoming trace continuation, outgoing fetch spans with propagation headers, db spans, Sentry.logger logs.

Known limits:

  • Plain wrangler bundling is not enough: without the orchestrion esbuild build there are no route names and no database spans.
  • mysql2 on workerd needs disableEval: true in the connection options, and the connection must be opened inside the request handler rather than at module scope.

What to change:

  • Add docs/platforms/javascript/guides/cloudflare/frameworks/nestjs.mdx with the wiring above and link it from guides/cloudflare/index.mdx:16-23.
  • Put the disableEval and connection-placement rules in a shared Workers database-driver note.

Source: runtime docs audit, item DOC-F43, cell M-nestjs-cf

Page: docs/platforms/javascript/guides/cloudflare/frameworks/nestjs.mdx (new), linked from guides/cloudflare/index.mdx:16-23; the mysql2 disableEval requirement belongs in a shared Workers database-driver note.

A page must say that NestJS 11 with the Express platform runs on workerd behind the node:http bridge, and that every capability except framework-swallowed errors works, but only with a hand-built esbuild bundle plus the orchestrion esbuild plugin; plain wrangler bundling is not sufficient. Error capture uses exactly the Node wiring: install @sentry/nestjs next to @sentry/cloudflare and register SentryModule.forRoot and the SentryGlobalFilter as APP_FILTER, with nothing Cloudflare-specific. Database spans require the build-time transform, work with both mysql drivers, and mysql2 additionally needs disableEval true or workerd rejects its generated row parsers; the connection must be opened inside the request, not at module scope. Route names, isolation, incoming trace, outgoing fetch and logs work as-is.

Where the docs stand: guides/nestjs/index.mdx:5-9 (Node fallback, server-node categories); guides/cloudflare/frameworks/ has no nestjs.mdx; guides/cloudflare/index.mdx:16-23 does not list Nest; no httpServerHandler or sentryOrchestrionPlugin mention anywhere in docs or platform-includes.

What ran: NestJS 11 (@nestjs/platform-express) on cloudflare (workerd via wrangler 4.56.0 dev, compatibility_date 2026-05-01). Cell record.
