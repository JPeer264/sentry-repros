DOC-F43NestJS on Cloudflare: documented noP1proven

Proposed issue new-page

Add a NestJS on Cloudflare Workers page using the esbuild orchestrion plugin

Description

Nothing documents NestJS on Workers. docs/platforms/javascript/guides/nestjs/index.mdx:5-9 sets fallbackGuide: javascript.node with server-node categories and carries no runtime caveat. docs/platforms/javascript/guides/cloudflare/frameworks/ has no nestjs.mdx, the framework list at guides/cloudflare/index.mdx:16-23 omits Nest, httpServerHandler appears nowhere under docs/ or platform-includes/, and sentryOrchestrionPlugin appears exactly once, in the v10-to-v11 migration guide at common/migration/v10-to-v11/index.mdx:1297, with no how-to page behind it.

Verified on the develop line: NestJS 11 with @nestjs/platform-express on workerd, compatibility_date: "2026-05-01", compatibility_flags: ["nodejs_compat", "enable_nodejs_http_modules", "enable_nodejs_http_server_modules"], served through httpServerHandler from cloudflare:node and wrapped with Sentry.withSentry() from @sentry/cloudflare. Nest must be booted lazily inside fetch, not at module scope. Bundle the Worker with esbuild plus sentryOrchestrionPlugin() from @sentry/server-utils/orchestrion/esbuild and point wrangler's main at the output. Three esbuild details decide whether the bundle boots at all: a banner whose createRequire shim strips the node: prefix (workerd's createRequire cannot resolve node:-prefixed builtins, and node:process additionally needs an alias returning globalThis.process), aliases stubbing class-validator, class-transformer, @nestjs/microservices* and @nestjs/websockets/socket-module, and leaving mainFields/conditions alone, because preferring ESM hands Express the ESM build of is-promise and the Worker dies on the first request. Error capture uses exactly the Node wiring: install @sentry/nestjs next to @sentry/cloudflare and register SentryModule.forRoot() in imports and SentryGlobalFilter from @sentry/nestjs/setup as an APP_FILTER provider.

Works today:

  • Unhandled controller errors through SentryGlobalFilter (mechanism auto.http.nestjs.global_filter, handled: false), parameterized route names with middleware and handler spans, per-request isolation, incoming trace continuation, outgoing fetch spans with propagation headers, db spans, Sentry.logger logs.
  • Expected HttpExceptions stay unreported (a NotFoundException yields status not_found and no event), the same behavior as on Node.
  • Error capture needs no bundler plugin: SentryGlobalFilter works on a plain wrangler build too, since @sentry/nestjs/setup depends only on @nestjs/* and @sentry/core.

Known limits:

  • Plain wrangler bundling gives no route names and no database spans: those need the orchestrion esbuild build.
  • mysql2 on workerd needs disableEval: true in the connection options, and the connection must be opened inside the request handler rather than at module scope.

What to change:

  • Add docs/platforms/javascript/guides/cloudflare/frameworks/nestjs.mdx with the wiring above and link it from guides/cloudflare/index.mdx:16-23.
  • Put the disableEval and connection-placement rules in a shared Workers database-driver note.

Source: runtime docs audit, item DOC-F43, cell M-nestjs-cf

Page: docs/platforms/javascript/guides/cloudflare/frameworks/nestjs.mdx (new), linked from guides/cloudflare/index.mdx:16-23; the mysql2 disableEval requirement belongs in a shared Workers database-driver note.

A page must say that NestJS 11 with the Express platform runs on workerd behind the node:http bridge, and that route names, handler spans and database spans need a hand-built esbuild bundle plus the orchestrion esbuild plugin; plain wrangler bundling is not sufficient for those. It must spell that build out, because the bundle does not boot without it: a createRequire banner that strips the node: prefix, stub aliases for class-validator, class-transformer, @nestjs/microservices* and @nestjs/websockets/socket-module, and no ESM-preferring mainFields or conditions, which would break express's require('is-promise'). Error capture is the exception, it needs no plugin and uses exactly the Node wiring: install @sentry/nestjs next to @sentry/cloudflare and register SentryModule.forRoot and the SentryGlobalFilter as APP_FILTER, with nothing Cloudflare-specific; expected HttpExceptions stay unreported, as on Node. Database spans require the build-time transform, work with both mysql drivers, and mysql2 additionally needs disableEval true or workerd rejects its generated row parsers; the connection must be opened inside the request, not at module scope. Isolation, incoming trace, outgoing fetch and logs work as-is on either build; route names, middleware and handler spans arrive with the orchestrion build.

Where the docs stand: guides/nestjs/index.mdx:5-9 (Node fallback, server-node categories); guides/cloudflare/frameworks/ has no nestjs.mdx; guides/cloudflare/index.mdx:16-23 does not list Nest; no httpServerHandler mention anywhere in docs or platform-includes, and the single sentryOrchestrionPlugin mention is the v10-to-v11 migration note at common/migration/v10-to-v11/index.mdx:1297.

What ran: NestJS 11 (@nestjs/platform-express) on cloudflare (workerd via wrangler 4.56.0 dev, compatibility_date 2026-05-01). Cell record: M-nestjs-cf.
