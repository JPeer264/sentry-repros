Proposed issue docs-change

Document Elysia on Deno: init from @sentry/deno, or add denoServeIntegration

Description

docs/platforms/javascript/guides/elysia/index.mdx:25 lists prerequisites as Bun or Node 18+ with the node adapter, and the install and configure snippets at :52-70 and :78-120 have only Bun and Node tabs, with Sentry.init imported from @sentry/elysia. platform-includes/performance/what-instrumentation-provides/javascript.elysia.mdx:9-12 enumerates exactly two runtimes and :6 claims parameterized route names unconditionally. A grep for deno over the Elysia guide returns nothing.

Verified on Elysia 1.4.30 and Deno 2.9.0: install the packages with npm into a real node_modules, set {"nodeModulesDir": "manual"} in deno.json, and pick one of two wirings. (1) Call Sentry.init() from @sentry/deno before Deno.serve and import only withElysia (and fetchIntegration) from @sentry/elysia. (2) Keep Sentry.init() from @sentry/elysia and pass integrations: [denoServeIntegration()], imported from @sentry/deno. Both need @sentry/deno installed alongside @sentry/elysia; both were exercised in the static and stream trace lifecycles. Mount with Deno.serve({ port }, withElysia(new Elysia()).get(...).fetch). Add import "@sentry/deno/import"; as the first line for database spans, and pass integrations: [fetchIntegration()] for outgoing requests.

Works today:

  • Route errors, mechanism auto.http.elysia.on_error.
  • GET /users/:id with op http.server and source route, with the Elysia lifecycle phases as child spans.
  • Per-request isolation and incoming trace continuation, with either wiring.
  • Outgoing http.client spans plus sentry-trace/baggage, with fetchIntegration(), which @sentry/elysia exports (it re-exports the @sentry/bun integration).
  • Database spans for mysql, and logs.

Known limits:

  • @sentry/elysia's own init() on its own delegates to @sentry/bun and does not instrument Deno.serve: there is no http.server span, every Elysia lifecycle phase becomes its own root transaction on one process-wide trace, incoming trace headers are ignored and the isolation scope carries the previous request's route into the next event. An outgoing fetch still produces an http.client span under the default stream lifecycle, but as a parentless segment; under static it is dropped for having no active span.
  • The wiring decides the reported SDK: with Sentry.init from @sentry/deno events carry sdk.name: sentry.javascript.deno; with the denoServeIntegration() variant they keep sentry.javascript.bun and contexts.runtime.name: bun, and sessions are emitted.
  • mysql2 cannot be imported while the Deno import hook is active: Deno compiles require('*.json') as JavaScript (denoland/deno#36240) and the import throws SyntaxError: Unexpected token ':'. Use mysql@2.

What to change:

  • guides/elysia/index.mdx:25 and the snippets at :52-70, :78-120: add Deno tabs with both wirings described above.
  • platform-includes/performance/what-instrumentation-provides/javascript.elysia.mdx:6,9-12: add a Deno bullet and qualify the route-name claim.
  • common/configuration/integrations/fetchIntegration.mdx:10: it states the integration "only works inside the Cloudflare Workers runtime", which the Deno runs disprove.

A page must state that Elysia 1.4 runs unchanged on Deno 2.9, mounted with Deno.serve and app.fetch, with nodeModulesDir manual and deps installed with npm, and that the wiring the guide shows today is wrong for this runtime. With Sentry.init from @sentry/elysia alone, route names, isolation and incoming trace continuation are all broken on Deno, because that init delegates to @sentry/bun, which does not instrument Deno.serve; every Elysia lifecycle phase becomes its own root transaction. Two wirings fix it, both built from shipped exports and both verified in the static and stream lifecycles: init from @sentry/deno and import only `withElysia` from @sentry/elysia (this also gets Deno's default integrations and tags events `sentry.javascript.deno`), or keep the @sentry/elysia init and add `denoServeIntegration()` from @sentry/deno (events then still self-report `sentry.javascript.bun` and `contexts.runtime.name: bun`). Neither needs a deep import into `build/esm`. Separately, the Deno SDK does not instrument global fetch; add `fetchIntegration()` — a real @sentry/elysia export, re-exported from @sentry/bun, not a hand-written shim — for http.client spans and trace headers. With that wiring, errors, database spans and logs work. The parameterized-route-names claim and the two-runtime list must both be corrected, and so must the fetchIntegration page, which still says the integration only works inside Cloudflare Workers.
