DOC-F10Next.js on Bun: documented noP1proven

Proposed issue new-page

Add a Next.js on Bun page for bun --bun, the fetch integration and the channel pin

Description

No page describes Next.js on Bun. docs/platforms/javascript/guides/nextjs/index.mdx:4 is sdk: sentry.javascript.nextjs, the runtime list at nextjs/index.mdx:51-53 names only Client, Server and Edge, and the documented register() block at nextjs/index.mdx:122-134 branches only on NEXT_RUNTIME === "nodejs" (:126) and "edge" (:129), with export const onRequestError = Sentry.captureRequestError; at :134. The Bun guide never mentions Next.js. One include already assumes the combination without saying how: platform-includes/logs/usage/javascript.nextjs.mdx:7 implies Bun is a supported Next.js server runtime.

Verified on Next.js 15.5.4 (app router) with @sentry/nextjs 10.67.0 (develop, 6f2da7483d) on Bun 1.4.0 and re-run on 1.4.2: withSentryConfig imported from the @sentry/nextjs/config subpath in next.config.mjs, the standard instrumentation.ts with the nodejs branch and captureRequestError re-exported as onRequestError, then bun --bun ./node_modules/.bin/next build and bun --bun ./node_modules/.bin/next start -p <port>. Pin typescript to 5.x or next build dies, and do not pass sendDefaultPii, which no longer exists on this line and is a TypeScript build error. Install @sentry/bun alongside @sentry/nextjs and add its fetchIntegration() to integrations in sentry.server.config.ts. Database and cache spans need a second addition in the same file, a workaround for a Bun bug: Bun garbage-collects the node:diagnostics_channel objects that only Sentry's subscriber references, so every subscription made by Sentry.init() is gone a tick later. Keep a strong reference to them right after the init call:

import * as dc from 'node:diagnostics_channel'; globalThis.__sentryKeptChannels = ['mysql2:query', 'mysql2:execute', 'mysql2:connect', 'mysql2:pool:connect', 'ioredis:command', 'ioredis:connect'].map(name => dc.tracingChannel(name));

Works today:

  • Unhandled route-handler errors
  • Route names GET /api/users/[id] with source route
  • Per-request isolation across concurrent requests
  • Incoming sentry-trace/baggage continuation
  • Outgoing fetch spans and propagation headers, with fetchIntegration() added
  • Database and cache spans for drivers that publish native diagnostics channels — mysql2 3.20.0 or later, ioredis 5.11.0 or later, node-redis 5.12.0 or later — once the channels are pinned as above, under both lifecycles
  • Sentry.logger log envelopes

Known limits:

  • Drivers below the native-channel cutoff stay unreachable on Next.js, because they need build-time injection and only ioredis is un-externalized for it.
  • There is no Sentry-specific Bun build step and none is possible: Next.js is built by webpack or turbopack, so the sentryBunPlugin() path other Bun framework pages rely on cannot be used here, and @sentry/nextjs/build/import-hook.mjs no-ops under Bun. The [Sentry] Runtime hook not registered line that reports this is only visible with debug: true.
  • contexts.runtime reports { name: 'node' } on every event even though process.versions.bun is set, so Bun events cannot be told apart from Node ones in Sentry.
  • Edge-runtime routes, middleware, server actions and browser-side capture were not exercised.

What to change:

  • New page docs/platforms/javascript/guides/bun/frameworks/nextjs.mdx with the install, the fetchIntegration() from @sentry/bun, the channel pin, the typescript 5.x requirement, the bun --bun build and start commands, and which instrumentation.ts branch runs under bun --bun.
  • guides/nextjs/index.mdx:151: withSentryConfig now comes from @sentry/nextjs/config. That is a v11-wide change documented in the v10-to-v11 guide at :1022, not a Bun step, and the Next.js guide still shows the old import.
  • Add a troubleshooting note under docs/platforms/javascript/guides/nextjs/ for a project root or ancestor directory named app; it applies to Node too.

Page: docs/platforms/javascript/guides/bun/frameworks/nextjs.mdx (new), plus a "Project directory named `app`" troubleshooting note under docs/platforms/javascript/guides/nextjs/

A page must say Next.js 15.5.4 (app router) builds and serves under `bun --bun ./node_modules/.bin/next build` / `bun --bun ./node_modules/.bin/next start` and that `@sentry/nextjs` initializes there, then name the three things the Node path does not need. (1) Install `@sentry/bun` alongside `@sentry/nextjs` and add its `fetchIntegration()` to `integrations` in `sentry.server.config.ts`; without it outgoing `fetch` produces no `http.client` span and no `sentry-trace`/`baggage` headers, because the Node SDK's HTTP instrumentation relies on undici diagnostics channels Bun never publishes. (2) After `Sentry.init()`, keep a strong reference to the tracing channels (`mysql2:query`, `mysql2:execute`, `mysql2:connect`, `mysql2:pool:connect`, `ioredis:command`, `ioredis:connect`) on `globalThis` — Bun collects channels that only Sentry's subscriber references, so the subscriptions made at init are gone a tick later and no db span is recorded. This is a workaround for a Bun bug and is harmless on Node. (3) State which `instrumentation.ts` branch runs under `bun --bun`, since the documented `register()` at :122-134 covers only `nodejs` and `edge`. A separate troubleshooting note applies to Node and Bun equally: do not name the project root, or any ancestor of your `app/` directory, `app` — Next.js derives the route on its OpenTelemetry spans by splitting the route file's absolute path on the first `/app/` segment (`getPathnameFromAbsolutePath`), so an extra `app` segment prefixes the transaction name with a spurious `/app` and leaves `event.transaction` (`GET /api/users/[id]`) disagreeing with the transaction envelope (`GET /app/api/users/[id]`). The source stays `route`, and the whole thing reproduces byte for byte on plain Node, so it belongs in Next.js troubleshooting rather than on a Bun page. The repo's nextjs-16-bun e2e app additionally passes `bunHttpServerIntegration({ spans: false })`; that was not exercised in this run and isolation was recorded working without it, so the page should not require it.

Where the docs stand: docs/platforms/javascript/guides/nextjs/index.mdx:4 (`sdk: sentry.javascript.nextjs`); nextjs/index.mdx:51-53 (the Client/Server/Edge list; :53 is the Edge bullet); nextjs/index.mdx:122-134 (`instrumentation.ts` branches only on `NEXT_RUNTIME === "nodejs"` at :126 and `"edge"` at :129, with `onRequestError` at :134); nextjs/index.mdx:151 (still imports `withSentryConfig` from the old path); common/migration/v10-to-v11/index.mdx:1022 (the `@sentry/nextjs/config` move); platform-includes/logs/usage/javascript.nextjs.mdx:7 (implies Bun is a supported Next.js server runtime); docs/platforms/javascript/guides/bun/ never mentions Next.js.
