Add a Remix v2 on Bun page for the Bun.build server bundle

Description

No page joins Remix and Bun. docs/platforms/javascript/guides/remix/index.mdx:12-16 carries the Remix 3 alert as the only runtime or version caveat, remix/index.mdx:58-97 covers only withSentry in root.tsx with no server entry, no instrumentation file and no run command, and remix/manual-setup.mdx:64 shows the Node install.

Verified on Remix v2 (@remix-run/dev Vite plugin with the @remix-run/express adapter) and @sentry/remix 10.67.0 on Bun 1.4.0: instrument.mjs imported as the first line of server.mjs, export const handleError = Sentry.sentryHandleError in app/entry.server.tsx, sentryRemixVitePlugin() in vite.config.ts, the mysql2 pool at module scope, then bundle the server entry with Bun.build({ entrypoints: ['./server.mjs'], outdir: './dist', target: 'bun', plugins: [sentryBunPlugin()] }) from @sentry/bun/plugin, keeping @sentry/* and express external, and run bun dist/server.js. Hold the adapter handler in a variable and wrap it in Sentry.withIsolationScope(() => Sentry.continueTrace({ sentryTrace, baggage }, () => remixHandler(req, res, next))), or add bunHttpServerIntegration({ spans: false }) from @sentry/bun to Sentry.init.

Works today:

  • Unhandled loader errors via the handleError hook
  • Route names GET users/:id with source route, plus LOADER routes/users.$id children
  • Per-request isolation and incoming trace continuation, with the wrapper above
  • Outgoing fetch spans with propagation headers
  • mysql2 database spans
  • Sentry.logger log envelopes

Known limits:

  • Plain bun server.mjs sends errors and logs only, with no transactions or spans at all.
  • The app's package.json must not carry "sideEffects": false, or the bundler drops side-effect-only imports and their libraries go uninstrumented.
  • The bundle is emitted without sourcemaps unless you enable them, so events lose context lines.

What to change:

  • New page docs/platforms/javascript/guides/bun/frameworks/remix.mdx with the build recipe, its two app-side requirements, the handler wrapper and the capability list.

Page: docs/platforms/javascript/guides/bun/frameworks/remix.mdx (new)

A page must say Remix v2 (`@remix-run/dev` vite plugin + `@remix-run/express` adapter) builds and runs on Bun 1.4.0 and `@sentry/remix` initializes there (`Sentry.isInitialized() === true`), then pick one of the two run shapes and disclose what the other loses. Plain `bun server.mjs` must be documented as giving errors and logs only — no transactions and no spans at all, not even a request span, and no outgoing-`fetch` span or trace headers. The working shape is to bundle the server entry with `Bun.build({ entrypoints: ['./server.mjs'], outdir: './dist', target: 'bun', plugins: [sentryBunPlugin()] })` from `@sentry/bun/plugin`, keeping `@sentry/*` external, and run `bun dist/server.js`; that yields route-named `http.server` transactions (`GET users/:id`, source `route`), `LOADER routes/users.$id` children, database spans and the outgoing `http.client` span with `sentry-trace`/`baggage`. The page must also state the two app-side requirements the bundle imposes: remove `"sideEffects": false` from the app's `package.json` or `Bun.build` tree-shakes the side-effect-only db import out and mysql2 is never transformed, and put `express` back on `external` after `sentryBunPlugin()` has run. Finally, because the bundle inlines `@remix-run/server-runtime`, Sentry's `createRequestHandler` patch never runs, so the app must hold the adapter handler in a variable and wrap it itself in `Sentry.withIsolationScope(...)` (not as a `next()`-style middleware) to get per-request isolation and incoming trace continuation.
