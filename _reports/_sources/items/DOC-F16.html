Add a Remix v2 on Bun page for the Bun.build server bundle

Description

No page joins Remix and Bun, and the current Remix guide documents no server entry, no instrumentation file and no run command for any runtime. docs/platforms/javascript/guides/remix/index.mdx:12-16 carries the Remix 3 alert as the only runtime or version caveat, and remix/index.mdx:58-97 ("Configure Server-Side Performance Monitoring") covers only withSentry in root.tsx; the page's headings are Install, Configure Server-Side Performance Monitoring, Tunneling, Data, Verify, Next Steps. remix/manual-setup.mdx:49 is the plain install and the whole page is 83 lines covering only Install. The server-entry, instrumentation-file and run-command content a Bun page would build on exists today only on the noindex remix/manual-setup__v8.x.mdx (:166-225, :285-294).

Verified on Remix v2 (@remix-run/* ^2.17.5, the @remix-run/dev Vite plugin with the @remix-run/express adapter, express 4, vite 5) and @sentry/remix 10.67.0 (develop, 6f2da7483d) on Bun 1.4.0 and re-run on 1.4.2, driver mysql2 3.24.3: instrument.mjs imported as the first line of server.mjs, export const handleError = Sentry.sentryHandleError in app/entry.server.tsx, sentryRemixVitePlugin() from the @sentry/remix/vite subpath in vite.config.ts (it moved there in v11; see the migration guide at :1287-1294), the mysql2 pool at module scope, then bundle the server entry with Bun.build({ entrypoints: ['./server.mjs'], outdir: './dist', target: 'bun', plugins: [sentryBunPlugin(), keepExternal] }) from @sentry/bun/plugin and run bun dist/server.js. Express is kept external by a small plugin placed after sentryBunPlugin() — { name: 'keep-external', setup(b) { b.config.external = [...(b.config.external ?? []), 'express']; } } — not by an external array entry, because the Sentry plugin removes the packages it instruments from that list; the route-names run reached a working state without externalizing express at all, so the two recorded runs differ here. Because the bundle inlines @remix-run/server-runtime, Sentry's createRequestHandler patch never runs, so hold the adapter handler in a variable and wrap it yourself: app.all('*', (req, res, next) => Sentry.withIsolationScope(scope => { scope.setSDKProcessingMetadata({ normalizedRequest: { url, method: req.method, headers: req.headers } }); return Sentry.continueTrace({ sentryTrace, baggage }, () => remixHandler(req, res, next)); })). The setSDKProcessingMetadata call is what puts request data on events.

Works today:

  • Unhandled loader errors via the handleError hook
  • Route names GET users/:id with source route — no leading slash — plus function LOADER routes/users.$id children, identical on the Node control
  • Per-request isolation and incoming trace continuation, with the wrapper above
  • mysql2 database spans
  • Sentry.logger log envelopes

Known limits:

  • Plain bun server.mjs sends errors and logs only, with no transactions or spans at all, and its events carry no transaction field, so errors group without a route. Isolation and incoming-trace continuation do work in that mode, and so do trace headers on outgoing fetch; adding fetchIntegration() from @sentry/bun also gives it an http.client span under the stream default, while under static the parentless client span is dropped. The repo's own e2e app create-remix-app-express/server.mjs uses this wiring and would produce zero spans on Bun.
  • Outgoing fetch spans in the bundled shape did not reproduce on the re-run: the recorder saw sentryTrace: null, baggage: null on every attempt, in both modes.
  • The bundle is target: 'bun' and cannot be run under Node.
  • The bundle is emitted without sourcemaps unless you enable them, so events lose context lines. sourcemap: 'external' is the expected fix and was not exercised.
  • Re-externalizing @remix-run/* instead of express restores isolation natively but removes every span, database spans included; bundling and transforming express breaks AsyncLocalStorage propagation across next() on Bun.
  • Browser-side capture was not exercised.

What to change:

  • New page docs/platforms/javascript/guides/bun/frameworks/remix.mdx with the build recipe, the keep-external plugin, the handler wrapper and the capability list.
  • guides/remix/: the guide needs the server entry, instrumentation file and run command that exist today only on the noindex v8 page, for every runtime — a Bun page has nothing to build on otherwise.
  • remix/manual-setup.mdx: cite the plain install at :49; :64 is the profiling variant.

A page must say Remix v2 (`@remix-run/dev` vite plugin + `@remix-run/express` adapter) builds and runs on Bun and `@sentry/remix` initializes there (`Sentry.isInitialized() === true`), then pick one of the two run shapes and disclose what the other loses. Plain `bun server.mjs` must be documented as giving errors and logs only — no transactions and no spans at all, not even a request span — with events that carry no transaction name, so errors group without a route; isolation and incoming-trace continuation do work there. The working shape is to bundle the server entry with `Bun.build({ entrypoints: ['./server.mjs'], outdir: './dist', target: 'bun', plugins: [sentryBunPlugin()] })` from `@sentry/bun/plugin` and run `bun dist/server.js`; that yields route-named `http.server` transactions (`GET users/:id`, source `route`), `LOADER routes/users.$id` children and database spans. Keep express external with a small plugin appended after `sentryBunPlugin()`, not with an `external` entry, because the Sentry plugin un-externalizes the packages it instruments. Because the bundle inlines `@remix-run/server-runtime`, Sentry's `createRequestHandler` patch never runs, so the app must hold the adapter handler in a variable and wrap it itself in `app.all('*', ...)` with `Sentry.withIsolationScope`, `setSDKProcessingMetadata({ normalizedRequest })` and `Sentry.continueTrace` to get per-request isolation, incoming trace continuation and request data on events. The root cause is that the CJS `loadModule('@remix-run/server-runtime', module)` monkeypatch and `withoutInstrumentedExternals` pull in opposite directions, so on Bun you can have spans or isolation but not both without the manual wrapper; an SDK-side fix there would remove the wrapper. The app's `package.json` must also not carry `"sideEffects": false`, or the bundler drops side-effect-only imports and their libraries go uninstrumented — that one comes from a follow-up run whose result was never recorded, and needs re-running before it is stated as verified. The same is true of the `bunHttpServerIntegration({ spans: false })` alternative to the wrapper: unrecorded, and the file that describes it also notes that `spans: true` names the transaction `GET *` and that plain `bun server-bunhttp.mjs` puts error events on a different trace id than the transaction.
