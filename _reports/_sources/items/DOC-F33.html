DOC-F33Remix on Deno: documented noP1proven

Proposed issue new-page

Add a Remix on Deno page covering installGlobals and the build-time setup

Description

The Remix guide names no runtime other than Node: docs/platforms/javascript/guides/remix/index.mdx:4-9 scopes the guide with Node categories and :12-16 carries only the Remix 3 alert, while platform-includes/getting-started-prerequisites/javascript.remix.mdx:1-7 requires just Remix 2.0.0+. Greps for deno, installGlobals and enableRuntimeChannelInjection over docs/ and platform-includes/ return zero; orchestrion returns two hits, both on common/migration/v10-to-v11/index.mdx (:689 and :1297), so the option and the plugin are documented nowhere outside the migration page.

Verified on Remix 2.17.5 with the Remix Vite plugin and a custom node:http server on Deno 2.9.0: install with npm under Node using --legacy-peer-deps, set deno.json to {"nodeModulesDir": "manual"}, add sentryRemixVitePlugin(), imported from @sentry/remix/vite, next to remix() in vite.config.ts, export handleError = Sentry.sentryHandleError from app/entry.server.tsx, and import instrument.server.mjs as the first line of the server entry with Sentry.instrumentBuild(build). Call installGlobals() from @remix-run/node at the top of app/entry.server.tsx, which is what remix reveal generates: it replaces Deno's native fetch with the node:http-backed polyfill, and outgoing requests are then traced. For database spans there are two shapes. Either import the driver before instrument.server.mjs, which needs no instrumentation path at all because mysql2 3.20+ publishes its own diagnostics channels; or set enableRuntimeChannelInjection: false and bundle the server entry with sentryOrchestrionPlugin() from @sentry/server-utils/orchestrion/esbuild, with @remix-run/server-runtime bundled, @sentry/* and mysql2 external, and a createRequire banner on the ESM output.

Works today:

  • Loader errors, mechanism auto.function.remix.server.
  • GET users/:id with source route, plus nested loader spans.
  • Per-request isolation and incoming trace continuation.
  • Outgoing http.client spans with trace headers, after installGlobals(), in both trace lifecycles.
  • Database spans for mysql2, through either shape above, and logs.

Known limits:

  • Without installGlobals(), outgoing fetch() produces no span and no sentry-trace/baggage headers. node:http and undici clients are traced without it.
  • installGlobals() called from the server entry must run after import './instrument.server.mjs'. Calling it before Sentry.init() silently drops every transaction and span envelope for the whole process while errors keep arriving. In app/entry.server.tsx, the position remix reveal generates, the ordering takes care of itself.
  • Replacing the polyfill with a hand-written fetch integration is not a substitute: it propagates the headers but suppresses every server transaction and span for the process.
  • The esbuild bundle needs the createRequire banner; without it the server dies with Dynamic require of "@sentry/server-utils" is not supported. Bundling @sentry/* instead of leaving it external fails the same way.
  • Turning the runtime hook off without the bundler plugin silently removes every server span, and leaving it on makes Deno abort at startup on a CommonJS dependency that does require('*.json').
  • Express cannot be used as the Remix server on Deno; it fails at import.

What to change:

  • Add docs/platforms/javascript/guides/deno/frameworks/remix.mdx and link it from guides/remix/frameworks/index.mdx, which today lists only the Cloudflare pages.
  • Name the supported runtimes in guides/remix/index.mdx:4-9 and in the prerequisites include, and document enableRuntimeChannelInjection and the orchestrion build plugin outside the migration page.

A page must state that Remix v2 runs on Deno 2.9 with @sentry/remix unchanged, and give the wiring the run required. Install with npm under Node using --legacy-peer-deps and set deno.json nodeModulesDir to manual; `deno add` does not resolve the transitive @sentry packages. Import the Vite plugin from `@sentry/remix/vite`, the subpath it now lives at. Call `installGlobals()` from `@remix-run/node` at the top of `app/entry.server.tsx`, or `fetch` in loaders and actions produces no `http.client` span and no trace headers, because Deno's native fetch is not instrumentable while the Remix polyfill is backed by `node:http`, which the Node SDK does instrument on Deno. The page must carry the ordering rule with it: if the call is made from the server entry instead, it has to come after `import './instrument.server.mjs'` — before `Sentry.init()` it silently drops every transaction and span envelope for the whole process while errors still arrive — and it must warn against the obvious alternative of a hand-written fetch integration, which propagates headers but suppresses all server spans. For database spans the page can offer the simple shape first: importing the driver before `instrument.server.mjs` is enough, since mysql2 3.20+ publishes its own diagnostics channels. The bundled shape, `enableRuntimeChannelInjection: false` plus `sentryOrchestrionPlugin()` from `@sentry/server-utils/orchestrion/esbuild` over the server entry, also works, and its details are load-bearing: `@remix-run/server-runtime` must be bundled because that is where the transform lands, `@sentry/*` and `mysql2` must stay external, and the ESM output needs a `createRequire` banner or it dies with `Dynamic require of "@sentry/server-utils" is not supported`. One thing to re-check before publishing that section: the Remix Vite plugin now applies the build-time instrumentation transform itself, and a manually added `sentryOrchestrionPlugin()` from `@sentry/server-utils/orchestrion/vite` is meant to be removed, so the separate esbuild pass may already be redundant for anything that goes through Vite — the run bundled a server entry that Vite never sees, which is why it was needed there. With this wiring, errors, parameterized route names, isolation, incoming trace continuation, outgoing fetch spans, db spans and logs all work.

Where the docs stand: guides/remix/index.mdx:4-9 (categories scope the guide to Node; no other runtime is named); index.mdx:12-16 (the only runtime caveat is the Remix 3 alert); platform-includes/getting-started-prerequisites/javascript.remix.mdx:1-7 (requires only Remix 2.0.0+); grep for deno over guides/remix returns zero; grep for installGlobals over docs and platform-includes returns zero; grep for enableRuntimeChannelInjection returns zero, and orchestrion returns only common/migration/v10-to-v11/index.mdx:689 and :1297, so both v11 surfaces are undocumented outside the migration page; guides/remix/ has no install/ directory, but it does have frameworks/index.mdx, which today lists only the Cloudflare pages.
