Proposed issue docs-change

Document the verified Hono on Deno setup and its outgoing fetch limit

Description

The Hono guide already claims Deno support: docs/platforms/javascript/guides/hono/index.mdx:12 lists Deno among the runtimes, :88-89 gives the Deno peer dependency as deno add npm:@sentry/deno, and :302-324 shows the Deno tab with import { sentry } from "@sentry/hono/deno", app.use(sentry(app, {...})) and Deno.serve(app.fetch). The page carries no runtime caveats around :360, and docs/platforms/javascript/guides/deno/index.mdx:1-230 never mentions node_modules, nodeModulesDir, the @sentry/deno/import hook or outgoing fetch.

Verified on Hono 4.13.7 with @sentry/hono/deno 10.67.0 on Deno 2.9.0: install @sentry/hono and @sentry/deno into a real on-disk node_modules with npm install, set {"nodeModulesDir": "manual"} in deno.json, put import "@sentry/deno/import"; as the first line of the entry file when you want database and library spans, then wire the middleware exactly as the current snippet shows and run deno run --allow-net --allow-env --allow-read --allow-sys main.ts.

Works today:

  • Unhandled route errors, with transaction: "GET /error" and mechanism auto.http.hono.context_error. Hono turns the throw into its own 500 response and the middleware's responseHandler reads context.error, so the event still arrives and the server span is marked internal_error.
  • Parameterized names GET /users/:id with source route.
  • Per-request isolation across concurrent requests.
  • Incoming sentry-trace/baggage continuation.
  • Database spans for mysql (requires the import hook line).
  • Logs.

Known limits:

  • Outgoing fetch() is not instrumented on Deno: no http.client span and no sentry-trace/baggage headers, so the downstream service starts a new trace. The default integrations of @sentry/deno carry denoHttpIntegration() for node:http/node:https and nothing that traces fetch; the breadcrumb integration patches fetch, so the call is still breadcrumbed while no span is started and no header is injected.
  • node:http/node:https clients are traced normally.
  • Without the import hook line, database and library spans are silently missing.

What to change:

  • guides/hono/index.mdx:88-89: show the deno.json and the npm-based install, not deno add alone.
  • guides/hono/index.mdx near :302-324: note the optional @sentry/deno/import first line and the permission flags.
  • guides/hono/index.mdx near :360: add a Deno-only caveat for outgoing fetch, naming node:http/node:https as the clients that are traced.
  • guides/deno/index.mdx: add an "Outgoing fetch requests" section stating the same limit.

This is the only Deno cell with a real page, and the snippet at :302-324 is correct as far as it goes: errors, route names, isolation, incoming trace continuation, db spans and logs all worked exactly as written. Two things must be added. (1) Install: `deno add npm:@sentry/deno` at :89 is not sufficient for the observed working setup, which needed the packages installed with `npm install` into the project so a real on-disk `node_modules` exists, plus `{"nodeModulesDir": "manual"}` in `deno.json`, because the Deno SDK's import hook resolves through a local `node_modules`. The Deno tab must show the `deno.json` and the npm-based install, not just `deno add`. (2) Outgoing HTTP: a Deno tab caveat under tracing must state that `@sentry/hono/deno` does not instrument the global `fetch()` — an outgoing `fetch()` produces no `http.client` span and receives no `sentry-trace` or `baggage` header, so the downstream service starts a new trace; only `node:http`/`node:https` clients are traced automatically, through `denoHttpIntegration()`. This was re-verified as confirmed-broken in both `static` and `stream` trace lifecycles and with the Deno import hook both on and off. The cause sits below Hono: `@sentry/deno`'s default integration set contains no fetch tracing integration at all, while its breadcrumb integration already installs a fetch instrumentation handler, so the hook fires with no subscriber to start a span or inject headers. SDK-side, the missing piece exists as `fetchIntegration` in @sentry/cloudflare and could be ported to @sentry/deno; the same gap was closed on Deno with shipped exports in the Fastify (`winterCGFetchIntegration()` from @sentry/vercel-edge), Express and SvelteKit (`fetchIntegration()` from @sentry/cloudflare) cells, but neither was run against Hono, so this page states the gap as a limit and names no remedy.

Where the docs stand: docs/platforms/javascript/guides/hono/index.mdx:12 ("supports Hono 4+ across multiple runtimes: Cloudflare Workers, Node.js, Bun, and Deno"); :88-89 (Deno peer-dep tab: `deno add npm:@sentry/deno`); :302-324 (Deno code tab: `import { sentry } from "@sentry/hono/deno"`, `app.use(sentry(app, {...}))`, `Deno.serve(app.fetch)`); :360 ("Report Unhandled Exceptions" heading, no runtime caveats); docs/platforms/javascript/guides/deno/index.mdx:1-230 (whole Deno guide; grep for `fetch|framework|node_modules|nodeModulesDir|@sentry/deno/import|Deno.serve` over guides/deno/ returns only configuration/integrations/breadcrumbs.mdx:23,27)
