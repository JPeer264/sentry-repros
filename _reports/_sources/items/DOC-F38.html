DOC-F38Fastify on Cloudflare: documented noP1proven

Proposed issue limitation-note

Note that Fastify does not run on Cloudflare Workers

Description

Neither guide says anything about this combination. grep -rni "cloudflare|workerd" docs/platforms/javascript/guides/fastify/ returns zero hits, docs/platforms/javascript/guides/fastify/index.mdx:4-9 declares the guide Node-only, and the Cloudflare framework list at docs/platforms/javascript/guides/cloudflare/index.mdx:16-23 names no Node HTTP framework at all. A reader gets no signal either way and spends the time finding out.

The audit ran Fastify 5.12.3 on workerd via wrangler dev with compatibility_date: "2026-05-01" and compatibility_flags: ["nodejs_compat", "enable_nodejs_http_server_modules"], serving through httpServerHandler from cloudflare:node. No wiring made Fastify serve a request, so there is no setup to document and no Sentry capability could be exercised. A control test with a plain node:http server behind the same httpServerHandler config did serve requests, so the Cloudflare half of the shape is fine.

  • Works today: nothing; Fastify never serves a request on Workers.

Known limits:

  • Constructing the app at module scope throws "Disallowed operation called within global scope", because Fastify's boot generates random values and schedules work.
  • Constructing it lazily on the first request then fails when any route is registered, because Fastify's router compiles matchers with new Function and Workers forbid runtime code generation, with no compatibility flag that lifts it.
  • Fastify 4 behaves the same way, so downgrading does not help.
  • Declaring a route schema is not an escape either: ajv (validation) and fast-json-stringify (response serialization) compile with new Function and hit the same wall.

What to change:

  • Add a "Node HTTP frameworks on Workers" note near Known Limitations at docs/platforms/javascript/guides/cloudflare/index.mdx:368, stating that Fastify does not run on Cloudflare Workers and why, and that the Cloudflare half of the shape is not the problem: enable_nodejs_http_server_modules plus httpServerHandler serve requests fine, it is the frameworks that cannot be constructed at module scope.
  • Add a one-line runtime note to docs/platforms/javascript/guides/fastify/index.mdx, scoped to Workers, making clear Fastify on Node.js is unaffected.

The docs are silent, and that silence leads users into a dead end. A page must state that Fastify does not run on Cloudflare Workers behind httpServerHandler, and why: constructing the app at module scope throws a disallowed-global-scope error because Fastify's boot generates random values and schedules work, and lazy construction on first request then hits a second workerd restriction that blocks serving, the ban on runtime code generation that Fastify's router, and ajv and fast-json-stringify behind any route schema, all depend on. No Sentry capability could be exercised. The note should also say what is not at fault: the node:http control behind the same httpServerHandler config served 200s, so the Cloudflare entrypoint works and it is the Node frameworks that cannot be constructed at module scope. The statement must be scoped to Workers; Fastify on Node is unaffected.

Where the docs stand: guides/fastify/index.mdx:4-9 (Node-only by declaration, no workerd mention); guides/cloudflare/index.mdx:16-23 (no Fastify); no httpServerHandler or enable_nodejs_http_server_modules mention anywhere under docs or platform-includes.
