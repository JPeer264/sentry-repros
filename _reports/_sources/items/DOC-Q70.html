DOC-Q70GCP Functions guide details: callback handlers lose the function span, HTTP functions split into two traces, no run step, no logs option, drifting export namesP2proven

Proposed issue docs-change

Add the missing details to the Google Cloud Functions guide: promise-form handlers, the two-trace split, a local run step, the logs option and consistent export names

Description

The Background and CloudEvent Issues snippets (platform-includes/getting-started-config/javascript.gcp-functions.mdx:71-75, :110-114, guides/gcp-functions/index.mdx:110-112) wrap a callback-style handler that throws: the error is captured (auto.function.serverless.gcp_event and gcp_cloud_event, with gcp.function.context), but the callback path never ends the function span, so no function.gcp span arrives; the promise-form Tracing snippets end it correctly. For HTTP functions every invocation yields two segments in two traces, Serverless function execution (function.gcp) and the Node http.server GET, with the error linked to the function trace only, which automatic-instrumentation.mdx:7 does not say.

The guide never says how to run a function locally (index.mdx:24, :82-90); run with npx @google-cloud/functions-framework --target=helloHttp the segment has no faas.name, because the SDK reads FUNCTION_TARGET or K_SERVICE, which Cloud Run sets and the framework does not. index.mdx:32-34 offers no logs onboarding option, so the logs verify include at :176-180 never renders although Sentry.logger.info works with the unmodified config. The export names drift between the config and verify steps (helloEvents against helloBackground and helloEvent), so the entry point has to change with each paste.

What to change:

  • Use the promise form in the Background and CloudEvent Issues snippets, state that HTTP functions produce two root spans, add a local run step with the FUNCTION_TARGET note, add logs to the onboarding options, and use one export name per tab.
