Proposed issue new-page

Add a Fresh 2 on Deno page: what the SDK does and does not instrument

Description

There is no Fresh page at all, and docs/platforms/javascript/guides/deno/index.mdx:1-232 names no framework; the Deno guide directory holds only index.mdx and configuration/integrations/{breadcrumbs,contextlines}.mdx, so the Cloudflare-style guides/*/frameworks/ layout has no Deno counterpart.

Verified on Fresh 2 and Deno 2.9.0: scaffold with deno run -A jsr:@fresh/init@^2, set "nodeModulesDir": "manual" in deno.json, install @sentry/deno into that same node_modules, keep import "@sentry/deno/import"; as the first line of instrument.ts and instrument.ts as the first import of main.ts. Fresh catches route errors itself, so add integrations: [Sentry.captureConsoleIntegration({ levels: ['error'], handled: false })] to Sentry.init to report them; if the app registers its own error handler, call Sentry.captureException there. For database spans, list each driver in both ssr.external and environments.ssr.build.rollupOptions.external in vite.config.ts. Both deno task dev and the deno serve _fresh/server.js build were exercised.

Works today:

  • Errors, via captureConsoleIntegration or an explicit capture in the app's error handler.
  • Incoming sentry-trace/baggage continuation.
  • Database spans for mysql, with the driver externalized as above.
  • Logs.

Known limits:

  • Routes are not named automatically; a middleware that reads ctx.route and calls Sentry.updateSpanName on the root span is required, otherwise transactions carry the raw path with source url.
  • Per-request isolation is not reliable on Deno: the runtime leaks the AsyncLocalStorage store out of a handler that awaits a dynamic import(), so tags, users, contexts and breadcrumbs set during one request appear on later requests.
  • Outgoing fetch() is not instrumented.

What to change:

  • Add docs/platforms/javascript/guides/deno/frameworks/fresh.mdx plus a frameworks/index.mdx listing the Deno frameworks.

Page: guides/deno/frameworks/fresh.mdx (new, following the guides/cloudflare/frameworks/*.mdx pattern), plus a new guides/deno/frameworks/index.mdx listing the supported Deno frameworks

A Fresh 2 page must exist and state that Fresh on Deno is viable but that nothing framework-specific is instrumented automatically — a hand-written middleware is required. It must document, in this order: (1) Setup — scaffold with `deno run -A jsr:@fresh/init@^2`, set `"nodeModulesDir": "manual"` in `deno.json`, keep `import "@sentry/deno/import"` as the first line of `instrument.ts` and `instrument.ts` as the first import of `main.ts`. (2) Errors — Fresh catches route errors itself and returns its own 500 page, so unhandled errors never reach Sentry on their own; the verified fix is `integrations: [Sentry.captureConsoleIntegration({ levels: ['error'], handled: false })]` in `Sentry.init`, which reports them as real exceptions carrying the request's trace id, in both `deno task dev` and the `deno serve _fresh/server.js` build. (3) Route names — spans stay unparameterized unless the app renames them: register a middleware right after `staticFiles()` that reads `ctx.route` and calls `Sentry.updateSpanName` on the root span, which is the only way to get `sentry.segment.name.source: 'route'`. The page must also explain why Fresh's own route enrichment has no effect: the Deno SDK registers an OpenTelemetry TracerProvider but no ContextManager, so `trace.getActiveSpan()` from `@opentelemetry/api` returns `undefined` and the `http.route` Fresh sets there is dropped. (4) Isolation — per-request isolation is not reliable on Deno: Deno leaks the AsyncLocalStorage store out of a handler that awaits a dynamic `import()` (Node does not), so `Sentry.setTag`/`setUser`/`setContext`/`addBreadcrumb` from one request can attach to every later request; the app-level mitigation is to replace the isolation scope in the middleware before `ctx.next()` (new `Sentry.Scope`, `setClient(Sentry.getClient())`, carry over the propagation context and SDK processing metadata). (5) Outgoing fetch — no `http.client` span and no `sentry-trace`/`baggage` headers for native `fetch`; ship the userland `fetchTracingIntegration` built from `addFetchInstrumentationHandler`, `defineIntegration` and `instrumentFetchRequest`. (6) Database spans — `@fresh/plugin-vite` sets `resolve.noExternal: true`, so every instrumented driver must be listed in BOTH `ssr: { external: [...] }` (for `deno task dev`) and `environments: { ssr: { build: { rollupOptions: { external: [...] } } } }` (for `deno task build`); `ssr.external` alone does not survive the build. Incoming trace continuation and logs need no caveat.

Where the docs stand: No page mentions Fresh: `grep -rniE "\bfresh\b" docs/platforms/javascript/` returns only docs/platforms/javascript/guides/cloudflare/features/agents-sdk.mdx:39 ("a fresh conversation ID"), and there is no docs/platforms/javascript/guides/fresh/ directory; docs/platforms/javascript/guides/deno/index.mdx:1-232 is the entire Deno guide (plus configuration/integrations/{breadcrumbs,contextlines}.mdx) and names no framework — its only wiring is `import * as Sentry from "@sentry/deno"` + `Sentry.init` at :43-88, `--allow-net` at :106 and `--allow-read` at :125
