Proposed issue new-page

Add a Fresh 2 on Deno page: what the SDK does and does not instrument

Description

There is no Fresh page at all, and docs/platforms/javascript/guides/deno/index.mdx:1-230 names no framework; the Deno guide directory holds only index.mdx and configuration/integrations/{breadcrumbs,contextlines}.mdx, so the Cloudflare-style guides/*/frameworks/ layout has no Deno counterpart.

Verified on Fresh 2 and Deno 2.9.0: scaffold with deno run -A jsr:@fresh/init@^2, set "nodeModulesDir": "manual" in deno.json, install @sentry/deno into that same node_modules, keep import "@sentry/deno/import"; as the first line of instrument.ts and instrument.ts as the first import of main.ts. Fresh catches route errors itself, so add integrations: [Sentry.captureConsoleIntegration({ levels: ['error'], handled: false })] to Sentry.init to report them; if the app registers its own app.onError("*") handler, call Sentry.captureException inside it instead. For database spans, use mysql@2 and list each driver in both ssr.external and environments.ssr.build.rollupOptions.external in vite.config.ts. Both deno task dev and the deno serve _fresh/server.js build were exercised.

Works today:

  • Errors, via captureConsoleIntegration, or an explicit capture in the app's error handler, or setErrorInterceptor from jsr:@fresh/core/internal.
  • Incoming sentry-trace/baggage continuation.
  • Database spans for mysql@2, with the driver externalized as above.
  • Logs.

Known limits:

  • Routes are not named automatically; a middleware that reads ctx.route and calls Sentry.updateSpanName on the root span is required, otherwise transactions carry the raw path with source url.
  • Per-request isolation is not reliable on Deno: awaiting a dynamic import() inside a request restores that request's store into the root async context, so tags, users, contexts and breadcrumbs set during one request appear on every later request. Mitigate with a first middleware that strips tags, contexts, extra, user, breadcrumbs and attachments off Sentry.getIsolationScope(). Do not use Sentry.withIsolationScope(new Sentry.Scope(), ...) for this: it cleans events but attributes each request's tags to the next transaction.
  • mysql2 cannot be used: under the import hook Deno compiles its require('*.json') as JavaScript (denoland/deno#36240) and the route 500s.
  • Outgoing fetch() is not instrumented.

What to change:

  • Add docs/platforms/javascript/guides/deno/frameworks/fresh.mdx plus a frameworks/index.mdx listing the Deno frameworks.

Page: guides/deno/frameworks/fresh.mdx (new, following the guides/cloudflare/frameworks/*.mdx pattern), plus a new guides/deno/frameworks/index.mdx listing the supported Deno frameworks

A Fresh 2 page must exist and state that Fresh on Deno is viable but that nothing framework-specific is instrumented automatically — a hand-written middleware is required. It must document, in this order: (1) Setup — scaffold with `deno run -A jsr:@fresh/init@^2`, set `"nodeModulesDir": "manual"` in `deno.json`, keep `import "@sentry/deno/import"` as the first line of `instrument.ts` and `instrument.ts` as the first import of `main.ts`. (2) Errors — Fresh catches route errors itself and returns its own 500 page, so unhandled errors never reach Sentry on their own; the verified fix is `integrations: [Sentry.captureConsoleIntegration({ levels: ['error'], handled: false })]` in `Sentry.init`, which reports them as real exceptions carrying the request's trace id, in both `deno task dev` and the `deno serve _fresh/server.js` build. That integration works because Fresh's default error handler console.errors what it swallows, so it goes silent the moment the app registers its own `app.onError("*")` — as do a try/catch middleware and `setErrorInterceptor`. An app with its own handler must call `Sentry.captureException(ctx.error, { mechanism: { type: 'fresh.onError', handled: false } })` inside it; an app without one can use `setErrorInterceptor(app, ...)` from `jsr:@fresh/core@^2.3.3/internal` as the least intrusive alternative. (3) Route names — spans stay unparameterized unless the app renames them: register a middleware right after `staticFiles()` that reads `ctx.route` and calls `Sentry.updateSpanName` on the root span, which is the smallest way to get `sentry.segment.name.source: 'route'`. The page must also explain why Fresh's own route enrichment has no effect: the Deno SDK registers an OpenTelemetry TracerProvider but no ContextManager, so `trace.getActiveSpan()` from `@opentelemetry/api` returns `undefined` and the `http.route` Fresh sets there is dropped. Registering a ContextManager that bridges that key to the active Sentry root span makes Fresh name its own routes with no middleware at all, in dev and in the build, but it is a page of shim code, so the middleware is the shape to document and the bridge is worth naming as the reason a fix belongs in the SDK. (4) Isolation — per-request isolation is not reliable on Deno: awaiting a dynamic `import()` inside a request handler restores that request's AsyncLocalStorage store into the root context, permanently, so `Sentry.setTag`/`setUser`/`setContext`/`addBreadcrumb` from one request attach to every later request. This is not specific to Fresh, to route chunks or to the production build: it reproduces with zero Sentry, under both `Deno.serve` and `node:http`, and in `vite dev` as soon as app code awaits an `import()`; Fresh's build merely guarantees it, because each route chunk is loaded lazily on its first request. The verified mitigation is a first middleware that scrubs the inherited isolation scope (`Sentry.getIsolationScope()`, then clear tags, contexts, extra, user, breadcrumbs and attachments), and the page must warn against the obvious alternative: `Sentry.withIsolationScope(new Sentry.Scope(), ...)` cleans the events but then applies each request's tags to the following transaction. (5) Outgoing fetch — no `http.client` span and no `sentry-trace`/`baggage` headers for native `fetch`; `node:http`/`node:https` clients are traced, and nothing shipped closed the `fetch` gap on this stack, so the page states it as a limit. (6) Database spans — `@fresh/plugin-vite` sets `resolve.noExternal: true`, so every instrumented driver must be listed in BOTH `ssr: { external: [...] }` (for `deno task dev`) and `environments: { ssr: { build: { rollupOptions: { external: [...] } } } }` (for `deno task build`); `ssr.external` alone does not survive the build. Use `mysql@2`: `mysql2` dies on the JSON-require defect under the import hook. Incoming trace continuation and logs need no caveat.

Where the docs stand: No page mentions Fresh: `grep -rniE "\bfresh\b" docs/platforms/javascript/` returns only docs/platforms/javascript/guides/cloudflare/agent-tracing/agents-sdk.mdx:43 ("a fresh conversation ID") and docs/platforms/javascript/common/migration/v10-to-v11/index.mdx:1339 ("a fresh scope"), and there is no docs/platforms/javascript/guides/fresh/ directory; docs/platforms/javascript/guides/deno/index.mdx:1-230 is the entire Deno guide (plus configuration/integrations/{breadcrumbs,contextlines}.mdx) and names no framework — its only wiring is `import * as Sentry from "@sentry/deno"` + `Sentry.init` under "### Initialize the Sentry SDK" at :54, with the init call at :69, `--allow-net` at :100 and `--allow-read` at :119
