Proposed issue new-page

Add a Fastify on Deno page: full instrumentation without the import hook

Description

There is no page for Fastify on Deno. docs/platforms/javascript/guides/fastify/index.mdx:4 declares sdk: sentry.javascript.node, :5 fallbackGuide: javascript.node, and :12-14 is only <PlatformContent includePath="getting-started-primer" /> plus getting-started-node; grep -rni deno docs/platforms/javascript/guides/fastify/ returns zero hits. docs/platforms/javascript/guides/deno/index.mdx:1-232 never mentions Fastify, any framework, nodeModulesDir, or the @sentry/deno/import hook.

Verified on Fastify 5.12.3 and Deno 2.9.0 with @sentry/deno 10.67.0: a package.json with {"type":"module"}, npm install @sentry/deno fastify mysql2 into a real node_modules, deno.json with {"nodeModulesDir": "manual"} and an imports map, an instrument.ts that only calls Sentry.init({ dsn, tracesSampleRate: 1.0 }), imported as the very first line of main.ts, and deno run --allow-net --allow-env --allow-read --allow-sys main.ts. No setupFastifyErrorHandler call and no build step are needed; the Fastify integration is on by default.

Works today:

  • Route errors, mechanism auto.function.fastify, with the server span marked internal_error.
  • GET /users/:id with source route and http.route set, in both trace lifecycles.
  • Per-request isolation and incoming trace continuation.
  • Database spans for mysql2 3.20+, which publishes its own diagnostics channels, with no import hook and no bundler plugin.
  • Logs.

Known limits:

  • Do not add import "@sentry/deno/import": it breaks Fastify at import on Deno.
  • Outgoing fetch() is not instrumented on Deno: no http.client span and no sentry-trace/baggage headers, in either trace lifecycle. node:http/node:https requests are traced and propagated.

What to change:

  • Add docs/platforms/javascript/guides/deno/frameworks/fastify.mdx with the setup above and an explicit warning against the import hook.
  • Put the outgoing fetch limit in guides/deno/index.mdx as a shared runtime note.

Source: runtime docs audit, item DOC-F21, cell M-fastify-deno

Page: guides/deno/frameworks/fastify.mdx (new), explicitly warning against `import "@sentry/deno/import"`; the shared fetch caveat belongs in guides/deno/index.mdx

A Fastify-on-Deno page must exist and must state the opposite of what the other Deno framework pages need: Fastify 5 runs on Deno unchanged and `@sentry/deno` instruments it with NO import hook and NO bundler step, and `@sentry/deno/import` must NOT be used because it breaks Fastify at import. Setup is a `package.json` with `{"type":"module"}`, an npm install of `@sentry/deno` into a real `node_modules`, and `deno.json` with `"nodeModulesDir": "manual"`. With that, errors, route names, isolation, incoming trace continuation, database spans and logs all work. The single documented limitation must be outgoing HTTP: on Deno the SDK does not instrument the global `fetch()` — outgoing `fetch()` calls produce no `http.client` span and carry no `sentry-trace`/`baggage` headers, so traces do not continue into the downstream service. The page must say this is a Deno-runtime property, not a Fastify one, that it applies to every framework on Deno, and that it is not changed by the `traceLifecycle` setting. It must give the user-land fix that works on the shipped build today: register a fetch integration built from `@sentry/core` primitives (the `@sentry/bun` fetch integration body works verbatim, since it depends on nothing Bun-specific).
