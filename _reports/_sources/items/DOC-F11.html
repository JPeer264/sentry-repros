Proposed issue docs-change

Add a Bun section to the Nuxt Nitro deployment presets page

Description

docs/platforms/javascript/guides/nuxt/features/nitro-deployment-presets.mdx:7 says the presets "work out of the box" and nitro-deployment-presets.mdx:9-11 carves out only Cloudflare Pages, while the documented start command at guides/nuxt/index.mdx:72 is node --import ./.output/server/sentry.server.config.mjs .output/server/index.mjs. Nothing under guides/nuxt/ mentions Bun.

Verified on Nuxt 4.5.2 (Nitro 2.13.4) with @sentry/nuxt 10.67.0 (develop, 6f2da7483d) on Bun 1.4.0: build with NITRO_PRESET=bun npx nuxt build and run with bun run .output/server/index.mjs. No inject mode and no start-up flag are needed: on develop, commit ec50b3e8f1 bundles sentry.server.config.ts into the Nitro build and imports it from a generated Nitro plugin, so Sentry.init runs at server startup by itself. Both autoInjectServerSentry modes are deprecated as of that commit and keep working until v12. The sentry.server.config.ts source file stays where it is, but it is no longer emitted to .output/server/sentry.server.config.mjs, which also makes the Node start command at nuxt/index.mdx:72 obsolete on both runtimes. What Bun does need is the server instrumentation: install @sentry/bun alongside @sentry/nuxt and pass integrations: [bunServerIntegration(), fetchIntegration()] from it to the existing Sentry.init in sentry.server.config.ts. The root cause is a runtime gap rather than a preset choice: Bun never publishes the http.server.request.start diagnostics-channel event the Node instrumentation opens the request span from (measured: 0 events on Bun against 1 on Node), so no preset avoids it. bunServerIntegration() is the right integration for the bun preset, which serves through Bun.serve; the default node-server preset also runs under Bun, yields zero spans, and needs bunHttpServerIntegration() instead. The capability list below rests on the three recorded follow-up runs, which all prescribe bunServerIntegration() alone; the pairing with fetchIntegration() was exercised in a further run whose result was never recorded, and that run also observed that with fetchIntegration() alone the http.client span is a root span rather than a child of the request.

Works today, with bunServerIntegration() added:

  • Unhandled server-route errors via the Nitro error hook, with or without the extra integrations
  • http.server spans named GET /users/:id with source route, http.route, and the url.path.parameter.id and params.id attributes
  • Per-request isolation and a fresh trace per request
  • Incoming sentry-trace/baggage continuation
  • mysql2 database spans, provided nitro: { externals: { external: ['mysql2'] } } is set in nuxt.config.ts
  • Sentry.logger log envelopes
  • Events keep sdk: sentry.javascript.nuxt and the Nuxt event processors throughout

Known limits:

  • Without bunServerIntegration() there is no request span at all: every event in the process shares one trace id, a stale transaction name leaks from an unrelated earlier request onto every later event, names are not route-based, incoming trace headers are ignored, and the mysql2 span is dropped as well, because its subscriber is bound with requiresParentSpan: true and has no request span to attach to.
  • The nitro.externals.external entry and the database span are two separate problems. Without the entry the query itself fails with genFunc$1 is not a function, with or without Sentry; with the entry but without bunServerIntegration() the query succeeds and no span is recorded.
  • Drivers that rely on Sentry's build-time channel injection, mysql v2 among them, must stay inside the Nitro bundle. Bun installs no runtime require hook, so an externalized driver of that kind is never instrumented.
  • Unparameterized routes stay method-only (GET) under the stream default and take the URL path (GET /api/ping) under traceLifecycle: 'static'; the source is url in both.
  • Manually captured events still carry no transaction field, even after the request span exists.

What to change:

  • guides/nuxt/features/nitro-deployment-presets.mdx: add a Bun section next to the Cloudflare Pages one covering NITRO_PRESET=bun npx nuxt build, bun run .output/server/index.mjs, the two @sentry/bun integrations (with bunHttpServerIntegration() as the node-server variant) and the Nitro externals rule.
  • guides/nuxt/index.mdx:72: the node --import ./.output/server/sentry.server.config.mjs command no longer matches the SDK, which bundles the server config into the Nitro build; replace it and add bun run .output/server/index.mjs for Bun.
  • guides/nuxt/install/limited-server-tracing.mdx:32 documents autoInjectServerSentry: 'top-level-import', which is now deprecated, and the warning at :16-23 and :19 claims that mode "will not capture data from database calls, queues, ORMs, third-party libraries" — a Node control run with exactly that setting produced db SELECT users, db mysql2.pool.connect and http.client spans, so the restriction as written is stronger than the SDK's behaviour.
  • Document the alternative and its cost: replacing the whole init with @sentry/bun in sentry.server.config.ts produces the same spans, but events then report sdk: sentry.javascript.bun and the Nuxt event processors are dropped.

Page: docs/platforms/javascript/guides/nuxt/features/nitro-deployment-presets.mdx — new "Bun" section alongside the Cloudflare Pages one (and a Bun start command replacing docs/platforms/javascript/guides/nuxt/index.mdx:72)

The presets page's "work out of the box" claim, with only Cloudflare excepted, is contradicted by the `bun` Nitro preset run under `bun run .output/server/index.mjs`: `@sentry/nuxt` uses the Node HTTP instrumentation, which never sees `Bun.serve`, so with the documented setup alone there is no request span — every event shares one trace and one scope across concurrent requests, later events carry the transaction name of an unrelated earlier request, transactions are not route-named, incoming `sentry-trace`/`baggage` is not continued, and the mysql2 span is suppressed for want of a parent. The page must add a Bun section stating that you install `@sentry/bun` alongside `@sentry/nuxt` and add `bunServerIntegration()` from it to `integrations` in `sentry.server.config.ts` (`bunHttpServerIntegration()` on the `node-server` preset), which restores `http.server` segment spans named `GET /users/:id` with `sentry.segment.name.source=route`, per-request trace ids, per-request isolation and the database span, while keeping the `sentry.javascript.nuxt` SDK identity. For the database it must additionally say to stop Nitro from bundling `mysql2` in `nuxt.config.ts` — otherwise every query 500s with `genFunc$1 is not a function`, with or without Sentry — while drivers that need Sentry's build-time injection must stay bundled. The start command at nuxt/index.mdx:72 needs replacing on both runtimes: develop bundles `sentry.server.config.ts` into the Nitro build (commit ec50b3e8f1), so there is no `.output/server/sentry.server.config.mjs` to `--import` any more, and on Bun the command is `bun run .output/server/index.mjs`. On the SDK side, the reason this needs a cross-package import at all is that `patchEventHandler` clones the isolation scope without resetting its propagation context; making it detect `process.versions.bun` would remove the need for `@sentry/bun` in a Nuxt app, and `bunServerIntegration()` is otherwise an undocumented cross-package import for Nuxt users.

Where the docs stand: docs/platforms/javascript/guides/nuxt/features/nitro-deployment-presets.mdx:7 ("provides support for different Nitro deployment presets, most of which **work out of the box**"); nitro-deployment-presets.mdx:9-11 (Cloudflare Pages is the only preset carved out; the file is 11 lines); docs/platforms/javascript/guides/nuxt/index.mdx:72 (`node --import ./.output/server/sentry.server.config.mjs .output/server/index.mjs` as the documented start command); guides/nuxt/install/limited-server-tracing.mdx:19 and :32. `grep -i bun` over guides/nuxt/ and `grep -i nuxt` over guides/bun/ both return 0.
