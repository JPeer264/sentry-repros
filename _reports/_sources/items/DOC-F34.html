DOC-F34SolidStart on Deno: documented noP1proven

Proposed issue new-page

Add a SolidStart on Deno install page and record its instrumentation limits

Description

grep -rni deno over docs/platforms/javascript/guides/solidstart/ returns zero, index.mdx:1-7 names no server runtime, and there is no platform-includes/getting-started-prerequisites/javascript.solidstart.mdx. The tracing verification step at index.mdx:444-470 tells the reader to create src/routes/sentry-test.tsx, throw from it and expect an issue, which never arrives on SolidStart 2. guides/deno/index.mdx:1-18 covers only the Deno SDK, not a node-server Nitro build run under Deno.

Verified on SolidStart 2.0.2 with Nitro 3 beta, Vite 8 and @sentry/solidstart 10.67.0: install with npm and --legacy-peer-deps, and put solidStart({ appRoot: './src' }), sentrySolidStart() imported from @sentry/solidstart/vite, and nitro({ serverDir: './server' }) in vite.config.ts. Initialise in a Nitro startup plugin (server/plugins/sentry.ts) that calls Sentry.init(); no --import preload and no instrument file are needed, because the Sentry Vite plugin bakes the library instrumentation into the bundle. Build with NODE_ENV=production npx vite build on Node — the plugin skips its instrumentation pass in development, and that pass is what produces the database spans — then run the node-server output with PORT=<port> HOST=127.0.0.1 deno run -A .output/server/index.mjs on Deno 2.9.0. For error capture, register a try/catch middleware as the first entry of the array form of createMiddleware and call Sentry.captureException there.

Works today:

  • Incoming sentry-trace/baggage continuation.
  • Database spans for mysql2, injected at build time by the Sentry Vite plugin.
  • Logs.
  • Errors from API routes, with the middleware above; errors thrown inside 'use server' actions are already captured by the shipped withServerActionInstrumentation wrapper, mechanism auto.function.solidstart.
  • Parameterized names, with setHttpServerSpanRouteAttribute from @sentry/server-utils: an onBeforeResponse middleware that rebuilds the pattern from event.params covers API routes, and a useCurrentMatches() call in the Router root covers SSR pages. Verified in both trace lifecycles.
  • Outgoing fetch(), with winterCGFetchIntegration() from @sentry/vercel-edge in the Nitro startup plugin, gated on Deno so a Node build does not get duplicate spans. It bundles cleanly into the node-server output and is an extra install.

Known limits:

  • Unhandled errors from API routes are not captured on their own: SolidStart answers 500 and no event is sent, on Deno and on Node alike, so the guide's own verification snippet reports nothing. The object form of createMiddleware cannot fix this, because neither of its lifecycles wraps the handler; the array form is required, with the existing sentryBeforeResponseMiddleware() spread in through a nested object-form call.
  • The Nitro error hook cannot help either: SolidStart builds its own inner H3 instance whose default onError turns the throw into a 500, so @sentry/nitro's error hook never fires and adding @sentry/nitro as a module changes nothing.
  • The SDK does not name server transactions: SolidStart mounts one catch-all Nitro route, so without the middleware above names arrive as the raw path with source url. setHttpServerSpanRouteAttribute is not re-exported from @sentry/solidstart, so the app has to depend on @sentry/server-utils directly, and only the segment span is renamed; the inner non-segment http.server spans stay GET under the stream lifecycle.
  • Scope data set during one request is inherited by later requests in the process: the first setTag lands on the shared default isolation scope. Node with the same build is clean. The mechanism was not established for this stack.
  • Outgoing fetch() is not instrumented without the integration above; node:http/node:https clients produce http.client spans with headers on Deno either way.

What to change:

  • Add docs/platforms/javascript/guides/solidstart/install/deno.mdx, correct the verification step at index.mdx:444-470, and add the two missing platform-includes.

A page must state that SolidStart 2 is built on Node and its node-server Nitro output runs on Deno 2.9 with @sentry/solidstart, and it must be exact about the build and the plugin imports: `solidStart({ appRoot: './src' })`, `sentrySolidStart()` from `@sentry/solidstart/vite` and `nitro({ serverDir: './server' })` in `vite.config.ts`, `Sentry.init()` in a Nitro startup plugin, and `NODE_ENV=production npx vite build`, because the Sentry plugin skips its instrumentation pass in development and that pass is what produces the database spans a reader is promised. Four findings follow. (1) Unhandled errors from API routes are not captured, on Deno and on Node alike, which is why the guide's own verification step at index.mdx:444-470 tells readers to expect an issue that never arrives. The fix is a try/catch middleware as the first entry of the ARRAY form of `createMiddleware`, rethrowing after `Sentry.captureException`, with `sentryBeforeResponseMiddleware()` spread in through a nested object-form call; the object form cannot do it, because neither of its lifecycles wraps the handler, and the Nitro `error` hook cannot either, because SolidStart's inner H3 instance already turned the throw into a 500. Errors inside `'use server'` actions are the exception: the shipped `withServerActionInstrumentation` wrapper captures those. (2) Server transaction names are not parameterized on SolidStart 2 with Nitro 3 on either runtime, because SolidStart mounts one catch-all route — but that is fixable in user land with a shipped helper: `setHttpServerSpanRouteAttribute` from `@sentry/server-utils`, called from an `onBeforeResponse` middleware that rebuilds the pattern from `event.params` for API routes, and from a `useCurrentMatches()` lookup in the Router root for SSR pages. The page must say the app has to depend on `@sentry/server-utils` directly, since `@sentry/solidstart` does not re-export it, and that only the segment span is renamed. (3) Outgoing fetch produces no span and no trace headers, because the Node SDK relies on undici channels that Deno's fetch never emits; `winterCGFetchIntegration()` from `@sentry/vercel-edge`, added in the Nitro startup plugin behind a Deno guard, restores both and bundles cleanly into the node-server output. (4) Isolation is only partial: the first `setTag` of a request lands on the shared default isolation scope and later requests inherit it, while Node with the same build is clean. The cause was not established for this stack, so the page should state the symptom and not attribute it. Database spans, logs and incoming trace continuation work unmodified. Install needs npm with --legacy-peer-deps for the nitro beta. SDK-side, `@sentry/solidstart` hooking SolidStart's own matcher would remove the route-name middleware entirely.
