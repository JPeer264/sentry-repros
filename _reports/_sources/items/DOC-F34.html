DOC-F34SolidStart on Deno: documented noP1proven

Proposed issue new-page

Add a SolidStart on Deno install page and record its instrumentation limits

Description

grep -rni deno over docs/platforms/javascript/guides/solidstart/ returns zero, index.mdx:1-7 names no server runtime, and there is no platform-includes/getting-started-prerequisites/javascript.solidstart.mdx. The tracing verification step at index.mdx:444-470 tells the reader to throw from an API route and expect an issue, which does not happen on SolidStart 2. guides/deno/index.mdx:1-18 covers only the Deno SDK, not a node-server Nitro build run under Deno.

Verified on SolidStart 2.0.2 with Nitro 3 beta, Vite 8 and @sentry/solidstart 10.67.0: install with npm and --legacy-peer-deps, add sentrySolidStart() and nitro() to vite.config.ts, and initialise in a Nitro startup plugin (server/plugins/sentry.ts) that calls Sentry.init(). Build on Node and run the node-server output with deno run .output/server/index.mjs on Deno 2.9.0. For error capture, register a try/catch middleware as the first entry of the array form of createMiddleware and call Sentry.captureException there.

Works today:

  • Incoming sentry-trace/baggage continuation.
  • Database spans for mysql2, injected at build time by the Sentry Vite plugin.
  • Logs.
  • Errors, with the middleware above.

Known limits:

  • Unhandled errors from API routes are not captured on their own: SolidStart answers 500 and no event is sent, on Deno and on Node alike, so the guide's own verification snippet reports nothing.
  • Server transactions cannot be parameterized by the SDK, because SolidStart mounts one catch-all Nitro route: names arrive as the raw path with source url.
  • Scope data set during the first request to a route is inherited by every later request in the process, a Deno AsyncLocalStorage defect triggered by the first dynamic import of a route chunk; Node with the same build is clean.
  • Outgoing fetch() is not instrumented.

What to change:

  • Add docs/platforms/javascript/guides/solidstart/install/deno.mdx, correct the verification step at index.mdx:444-470, and add the two missing platform-includes.

A page must state that SolidStart 2 is built on Node and its node-server Nitro output runs on Deno 2.9 with @sentry/solidstart, and record four defects with fixes. Unhandled errors from API routes are not captured on Deno; register a try/catch h3 middleware as the first entry of the array form of createMiddleware, which also means the guide's own verification snippet produces no issue as written. Server transaction names cannot be parameterized on SolidStart 2 with Nitro 3 on either runtime, because SolidStart mounts one catch-all route, so transactions arrive as the raw path with source url; a global middleware rebuilding the pattern from event.params is the fix. Outgoing fetch produces no span and no trace headers, because the Node SDK relies on undici channels that Deno's fetch never emits; add a userland fetch integration gated on Deno. Isolation is only partial. Database spans, logs and incoming trace continuation work unmodified. Install needs npm with --legacy-peer-deps for the nitro beta.

Where the docs stand: guides/solidstart/ (index.mdx, install/, features/, profiling/): grep for deno returns zero; index.mdx:1-7 names no server runtime; no platform-includes/getting-started-prerequisites/javascript.solidstart.mdx exists; index.mdx:444-470 is the tracing verification step whose thrown API-route error is never captured on Deno; guides/deno/index.mdx:1-18 covers only the Deno SDK, not a node-server Nitro build run under Deno.
