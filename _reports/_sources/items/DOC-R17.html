DOC-R17Deno guide never mentions deno serve, which is instrumented like Deno.serveP2verified in source

Proposed issue docs-change

Add deno serve to the Deno guide run commands

Description

The Deno guide shows only two ways to start an app: deno run --allow-net=___ORG_INGEST_DOMAIN___ index.ts at docs/platforms/javascript/guides/deno/index.mdx:100 and deno run --allow-read=./src index.ts at :119. The string deno serve appears nowhere under docs/, platform-includes/ or includes/, so a reader using the default-export server form has no confirmation that the SDK covers it.

An export default { fetch } entrypoint started with deno serve is instrumented exactly like Deno.serve. The DenoServe integration proxies Deno.serve (packages/deno/src/integrations/deno-serve.ts:80-93 on develop, :75-88 at the pin), which is what deno serve calls internally. --parallel re-executes the entry module once per worker thread, so a 16-worker run performs 16 Sentry.init calls in one process; a recorded run of 55 requests produced exactly 55 spans, one per request, and per-request tags stayed inside their own worker in all ten checks.

One caveat belongs next to the note: an entry written as the guide shows it, without the import "@sentry/deno/import" hook line, still reports errors and http.server spans under deno serve, but produces no library spans — the module-scope mysql query lost its db span.

What to change

  • Add a deno serve note to the Deno guide alongside the existing run commands.
  • State that a default-export fetch handler is instrumented the same way as Deno.serve.
  • Note that --parallel initializes once per worker without duplicate events and without scope data crossing workers.
  • Say that the entry still needs import "@sentry/deno/import" for library spans.

Status quo. The Deno guide's only run commands are `deno run --allow-net=___ORG_INGEST_DOMAIN___ index.ts` (docs/platforms/javascript/guides/deno/index.mdx:100) and `deno run --allow-read=./src index.ts` (:119). The string `deno serve` appears nowhere under docs/, platform-includes/ or includes/.

On develop. An `export default { fetch }` entrypoint started with `deno serve` is instrumented exactly like `Deno.serve`, because the DenoServe integration proxies `Deno.serve` (packages/deno/src/integrations/deno-serve.ts:80-93 on develop, :75-88 at the pin, the shift coming from a new `@deprecated` JSDoc on `ignoreStatusCodes`), which `deno serve` calls internally. probes/N8 recorded what `--parallel` does: 16 workers in one process, each with its own `Sentry.init` and its own module-scope load, 55 requests producing exactly 55 spans, per-request tags matching their worker in 10 of 10 events, and no session envelope at all, since the Deno SDK ships no release health. The same probe recorded that a docs-shaped entry without `import "@sentry/deno/import"` still reports errors and `http.server` spans under `deno serve` but loses library spans, the mysql `db` span included.

Work item. Add a `deno serve` note to the Deno guide stating that a default-export `fetch` handler is instrumented the same way, that `--parallel` initializes once per worker without duplicating events or leaking scope data between workers, and that the `@sentry/deno/import` hook line is still what buys library spans.
