DOC-F30Astro on Deno: documented wrongP0proven

Proposed issue docs-change

Correct the Astro runtime note: Deno with @deno/astro-adapter works

Description

docs/platforms/javascript/guides/astro/index.mdx:21-29 carries an Alert titled "What runtime do you use?" saying the SDK only works on Node runtimes such as the Node adapter or Vercel with Lambda functions, pointing Cloudflare users elsewhere, and calling other non-Node runtimes not supported. That reads as excluding Deno. grep -rni deno docs/platforms/javascript/guides/astro/ returns zero hits, and guides/deno/ never mentions Astro.

Verified on Astro 7.3.1 in SSR mode (output: 'server') with @deno/astro-adapter 0.6.0 and @sentry/astro 10.67.0 on Deno 2.9.0: install the packages with npm install into a real node_modules rather than deno add, set deno.json to {"nodeModulesDir": "manual"}, add the sentry() integration in astro.config.mjs, keep a root sentry.server.config.js that calls Sentry.init(), add a src/middleware.ts whose first line imports that config, build normally and run the built dist/server/entry.mjs with Deno. The middleware is a required step, not a convenience: without it Sentry.init never runs for requests that only hit .ts/.js endpoint routes, so those requests produce nothing at all.

Works today:

  • Route errors, mechanism auto.middleware.astro, with request URL and source context.
  • GET /users/[id] with source route, in both trace lifecycles.
  • Per-request isolation across concurrent requests.
  • Incoming sentry-trace/baggage continuation.
  • Database spans for mysql2, injected by the Vite plugin @sentry/astro adds during astro build.
  • Logs.

Known limits:

  • Outgoing fetch() is not instrumented on Deno: no http.client span and no sentry-trace/baggage headers, so the downstream service starts a new trace. Adding fetchIntegration from @sentry/cloudflare in sentry.server.config.js restores both, but @sentry/astro does not depend on @sentry/cloudflare, so that package has to be installed on purpose. Calls made with node:http/node:https are traced without it, and a call wrapped in Sentry.startSpan with headers taken from Sentry.getTraceData() also works.
  • A route that only exists as a .ts/.js endpoint is uninstrumented unless src/middleware.ts imports the server config.

What to change:

  • guides/astro/index.mdx:21-29: amend the Alert to name Deno as a supported runtime and link out.
  • Add a Deno framework page for Astro with the @deno/astro-adapter setup, the mandatory middleware import, the npm install @sentry/cloudflare step and the fetchIntegration snippet.
  • common/configuration/integrations/fetchIntegration.mdx:10: it says the integration "only works inside the Cloudflare Workers runtime", which this run disproves.

The runtime Alert must be corrected: Deno is a supported runtime for `@sentry/astro`, not one of the excluded "other non-Node runtimes". A page must state that Astro SSR (`output: 'server'`) with `@deno/astro-adapter` runs under Deno by building normally and running the built `dist/server/entry.mjs` with Deno, that the Sentry packages must be installed with `npm install` into a real `node_modules` (not `deno add`), and that errors, route names, per-request isolation, incoming trace continuation, database spans and logs all work with the standard `sentry.server.config.js` wiring plus a `src/middleware.ts` that imports it. The middleware must be presented as required rather than optional: an endpoint route implemented as `.ts`/`.js` never triggers the server config on its own, so an app whose API routes are the only server code initialises Sentry never. The one limitation to document is outgoing HTTP: requests made with the global `fetch()` are not instrumented on Deno — no `http.client` span and no `sentry-trace`/`baggage` headers — because Deno's native fetch emits none of the `undici:*` `diagnostics_channel` events the Node SDK subscribes to, so the downstream service starts a new trace. Three verified fixes exist and the page should show the first two: add `fetchIntegration` from `@sentry/cloudflare` — one line in `sentry.server.config.js`, but `@sentry/astro` does not depend on that package, so it is a deliberate `npm install @sentry/cloudflare` unlike the SvelteKit case — or use `node:http`/`node:https` for the calls that must be traced; wrapping a single call in `Sentry.startSpan` and attaching `Sentry.getTraceData()` headers also works when only one call matters. The fetchIntegration reference page, which still says the integration only works inside Cloudflare Workers, needs correcting alongside.

Where the docs stand: docs/platforms/javascript/guides/astro/index.mdx:21-29 — Alert titled "What runtime do you use?": "This SDK currently only works on Node runtimes, such as Node adapter or Vercel with Lambda functions.
