Proposed issue docs-change

Correct the Astro runtime note: Deno with @deno/astro-adapter works

Description

docs/platforms/javascript/guides/astro/index.mdx:22-31 carries an Alert titled "What runtime do you use?" saying the SDK only works on Node runtimes such as the Node adapter or Vercel with Lambda functions, pointing Cloudflare users elsewhere, and calling other non-Node runtimes not supported. That reads as excluding Deno. grep -rni deno docs/platforms/javascript/guides/astro/ returns zero hits, and guides/deno/ never mentions Astro.

Verified on Astro 7.3.1 in SSR mode (output: 'server') with @deno/astro-adapter 0.6.0 and @sentry/astro 10.67.0 on Deno 2.9.0: install the packages with npm install into a real node_modules rather than deno add, set deno.json to {"nodeModulesDir": "manual"}, add the sentry() integration in astro.config.mjs, keep a root sentry.server.config.js that calls Sentry.init(), add a src/middleware.ts whose first line imports that config, build normally and run the built dist/server/entry.mjs with Deno.

Works today:

  • Route errors, mechanism auto.middleware.astro, with request URL and source context.
  • GET /users/[id] with source route, in both trace lifecycles.
  • Per-request isolation across concurrent requests.
  • Incoming sentry-trace/baggage continuation.
  • Database spans for mysql2, injected by the Vite plugin @sentry/astro adds during astro build.
  • Logs.

Known limits:

  • Outgoing fetch() is not instrumented on Deno: no http.client span and no sentry-trace/baggage headers, so the downstream service starts a new trace. Adding fetchIntegration from @sentry/cloudflare in sentry.server.config.js, or using node:http/node:https, restores both.

What to change:

  • guides/astro/index.mdx:22-31: amend the Alert to name Deno as a supported runtime and link out.
  • Add a Deno framework page for Astro with the @deno/astro-adapter setup, the middleware import and the fetchIntegration snippet.

The runtime Alert must be corrected: Deno is a supported runtime for `@sentry/astro`, not one of the excluded "other non-Node runtimes". A page must state that Astro SSR (`output: 'server'`) with `@deno/astro-adapter` runs under Deno by building normally and running the built `dist/server/entry.mjs` with Deno, that the Sentry packages must be installed with `npm install` into a real `node_modules` (not `deno add`), and that errors, route names, per-request isolation, incoming trace continuation, database spans and logs all work with the standard `sentry.server.config.js` wiring. The one limitation to document is outgoing HTTP: requests made with the global `fetch()` are not instrumented on Deno — no `http.client` span and no `sentry-trace`/`baggage` headers — because Deno's native fetch emits none of the `undici:*` `diagnostics_channel` events the Node SDK subscribes to, so the downstream service starts a new trace. Two verified fixes must be shown: add `fetchIntegration` from `@sentry/cloudflare` (one extra install, one line in `sentry.server.config.js`; it uses only `@sentry/core` primitives and is runtime-agnostic), or use `node:http`/`node:https` for the calls that must be traced.

Where the docs stand: docs/platforms/javascript/guides/astro/index.mdx:22-31 — Alert titled "What runtime do you use?": "This SDK currently only works on Node runtimes, such as Node adapter or Vercel with Lambda functions. If you use Cloudflare Workers or Cloudflare Pages, refer to our Astro on Cloudflare guide. Other non-Node runtimes, like Vercel's Edge runtime, are currently **not supported**."
