DOC-F13Astro on Bun: documented wrongP0proven

Proposed issue docs-change

Name Bun in the Astro runtime alert and add a Running on Bun section

Description

The runtime alert at docs/platforms/javascript/guides/astro/index.mdx:21-29 says the SDK "currently only works on Node runtimes, such as Node adapter or Vercel with Lambda functions" and that other non-Node runtimes are not supported (:23-27), which reads as excluding Bun. Nothing under guides/astro/ mentions Bun, and nothing under guides/bun/ mentions Astro.

Verified on Astro 7.3.1 with the @astrojs/node ^11.1.5 standalone adapter and @sentry/astro 10.67.0 (develop, 6f2da7483d) on Bun 1.4.0 and re-run on 1.4.2: in astro.config.mjs set output: 'server', the node({ mode: 'standalone' }) adapter, sentry({ sourcemaps: { disable: true }, enabled: { client: false, server: true } }) and vite: { ssr: { noExternal: ['mysql2'] } }, which is required for build-time database instrumentation. Put a root sentry.server.config.mjs guarded with Sentry.isInitialized(), run astro build, then bun --preload ./sentry.server.config.mjs dist/server/entry.mjs. The preload is required, because the integration injects the init only into .astro page chunks, so an app whose first request hits an API route would otherwise run uninstrumented. Install @sentry/bun and add its fetchIntegration() to the server init, guarded on typeof globalThis.Bun !== 'undefined' so Node deployments of the same build do not double-count. Database spans need one more workaround for a Bun bug: Bun's node:diagnostics_channel does not keep a channel alive once it has subscribers, so the SDK reads hasSubscribers = true while the injected wrapper reads false. Pin the channels on globalThis next to Sentry.init() in sentry.server.config.mjs — globalThis.__sentryPinnedChannels ??= ['mysql2:query', 'mysql2:execute', 'mysql2:connect', 'mysql2:pool:connect', 'orchestrion:mysql:query', 'orchestrion:mysql2:query', 'orchestrion:mysql2:execute'].map(name => dc.tracingChannel(name)) — which is harmless on Node and can be applied unconditionally. Loading the driver early is not a substitute here: it fixes mysql2 and not mysql@2.

Works today:

  • Unhandled endpoint errors via the Astro request middleware, mechanism auto.middleware.astro
  • Route names GET /users/[id] with source route and http.route
  • Per-request isolation across concurrent requests
  • Incoming sentry-trace/baggage continuation
  • Outgoing fetch spans and propagation headers, with fetchIntegration() added
  • mysql2 and mysql@2 database spans on both lifecycles and both mysql2 code paths, with the channel pin above
  • Sentry.logger log envelopes

Known limits:

  • The build needs a @sentry/bundler-plugins matching this SDK line; with an older one npx astro build dies with "The requested module @sentry/core does not provide an export named ServerRuntimeClient".
  • contexts.runtime reports node on Bun, so Bun events cannot be told apart from Node ones in Sentry.
  • ContextLines prints Failed to read file: native once per captured event on Bun.
  • Errors thrown while an .astro page renders were not exercised; the error probe is an endpoint. Browser-side capture was not exercised either, because the run used enabled: { client: false, server: true }.

What to change:

  • guides/astro/index.mdx:21-29: amend the alert to name Bun as working on the Node adapter output.
  • Add a "Running on Bun" section to that page with the bun --preload ./sentry.server.config.mjs dist/server/entry.mjs start command, the astro.config.mjs options above, the runtime-gated fetchIntegration(), the channel pin and the capability list.

Source: runtime docs audit, item DOC-F13, cell M-astro-bun

Page: docs/platforms/javascript/guides/astro/index.mdx:21-29 — amend the runtime alert to name Bun, and add a "Running on Bun" section covering the fetch integration and the diagnostics-channel pin

The runtime alert tells a reader that a non-Node runtime is unsupported, but Astro 7.3.1's `@astrojs/node` standalone build (`dist/server/entry.mjs`) runs on Bun with `@sentry/astro` and delivers working endpoint errors, route names, request isolation, incoming trace continuation and logs. The alert must be amended to name Bun explicitly as working on the Node adapter output, and the page must state the two caveats observed. Outgoing `fetch` is not instrumented under Bun, because `@sentry/node`'s HTTP integration listens on undici's `undici:request:*` diagnostics channels and Bun's native fetch does not publish them — install `@sentry/bun` and add its `fetchIntegration()` to `sentry.server.config.mjs`, guarded on `typeof globalThis.Bun !== 'undefined'` so Node deployments of the same build do not double-span. Database spans are dropped because Bun holds diagnostics channels weakly and a channel with subscribers is not kept alive, so every subscription made at `Sentry.init()` is lost on the next tick; the workaround for that Bun bug is to keep the channels reachable by storing them on `globalThis` after `Sentry.init()` (`mysql2:query`, `mysql2:execute`, `mysql2:connect`, `mysql2:pool:connect`, `orchestrion:mysql:query`, `orchestrion:mysql2:query`, `orchestrion:mysql2:execute`), which is harmless on Node and therefore safe to apply unconditionally. The SDK-side fix is for the subscribe sites to retain the channels they subscribe to, which would remove the pin for every Bun user.

Where the docs stand: docs/platforms/javascript/guides/astro/index.mdx:21-29 (the `<Alert level="warning" title="What runtime do you use?">` block; quoted text at :23-27 — "This SDK currently only works on Node runtimes, such as Node adapter or Vercel with Lambda functions... Other non-Node runtimes, like Vercel's Edge runtime, are currently **not supported**."); astro/index.mdx:4 (`sdk: sentry.javascript.astro`). `grep -i bun` over guides/astro/ and `grep -i astro` over guides/bun/ both return nothing.

What ran: Astro 7.3.1 with @astrojs/node ^11.1.5 standalone adapter and @sentry/astro 10.67.0 (develop, 6f2da7483d) on Bun 1.4.0 and re-run on 1.4.2 (darwin arm64), running the Node-adapter build output `dist/server/entry.mjs`. On the re-run the Node control also produced `spans: []` for `GET /db`, so on that machine the database gap was not Bun-specific. Cell record M-astro-bun.
