DOC-Q2The Cloudflare Vite plugin instruments nothing, without warning, when it resolves a different default-named wrangler configP1proven

Proposed issue docs-change

Say on the Vite plugin page that a wrangler config resolved to the wrong file instruments nothing

Description

guides/cloudflare/features/vite-plugin.mdx documents the probing order at :68 and gives wranglerConfigPath its own option entry at :130-148, described as the setting for a config at a custom path. What no page says is what happens when the config is not at a custom path but simply not the one the reader means: with several wrangler files in the project, the plugin resolves the first default-named wrangler.json, wrangler.jsonc or wrangler.toml at the Vite root, reads the entry point and classes from that file, and instruments nothing for the Worker actually being built. Nothing is logged, because the plugin only warns when no config parses at all.

Observed on develop with a Worker whose source has no withSentry call, built in a directory holding more than one wrangler config: before wranglerConfigPath was passed, the run produced an empty sink, an uncaught error in the worker log and no trace-propagation headers. With wranglerConfigPath set and an instrument.server.ts next to the wrangler main, the built Worker delivered the same errors, spans, headers and logs as a hand-written withSentry, with no experimental flag.

What to change:

  • On the Vite plugin page, state that wranglerConfigPath is required whenever the project holds more than one wrangler config, not only when the config sits at a custom path, and that a config resolved to the wrong file instruments nothing while the build still succeeds.
  • Say how to tell: with auto-instrumentation working, the built entry contains a withSentry wrapper; without it there is no wrapper and no plugin output.
  • Remove the _experimental.useDiagnosticsChannelInjection flag from guides/cloudflare/index.mdx:77-92; it is not needed on develop (also DOC-C4).

Source: runtime docs audit, item DOC-Q2, quick start QS-cloudflare, variant vite

Two of the three observations this item started with no longer hold. The instrument.server.* step is documented since commit 9bfe0e96c (sentry-docs#19199) at vite-plugin.mdx:88-99, with the defineCloudflareOptions snippet at :90-97 and, at :99, "If no instrument.server.* file exists, the SDK reads all configuration (DSN, release, environment, sample rate, etc.) from the Worker's env bindings at runtime." And the () => undefined fallback (ENV_FALLBACK_OPTIONS_FN, packages/cloudflare/src/vite/instrumentFile.ts:7) is not a silent failure but a deliberate hand-off: packages/cloudflare/src/options.ts:68 resolves dsn: userOptions.dsn ?? getEnvVar(env, 'SENTRY_DSN'), so the Worker runs without a DSN only when env carries none either. The plugin also does warn when no wrangler config parses, through the Vite logger (packages/cloudflare/src/vite/autoInstrument.ts:34-40): "[sentry] No parseable wrangler config found - auto-instrumentation disabled. Set wranglerConfigPath if your config uses a custom name."

What is left is the case that warning does not cover. The reproduction's own note (quickstarts/cloudflare/README.md:341-347) records it: the directory holds several wrangler configs, a different default-named one was found and used, and the plugin instrumented nothing - "items": [], an uncaught Error: My first Sentry error! in the worker log and {"sentry-trace":null,"baggage":null} at the recorder. A config was found, so no warning fired. Both plugins now get the file explicitly (cloudflare({ configPath }) and sentryCloudflareVitePlugin({ wranglerConfigPath })). The layout is a harness artifact; the failure mode it exposes is not.

What ran: Cloudflare getting-started reproduction, variant vite, on 2026-09-08 with wrangler 4.129.0 and @cloudflare/vite-plugin 1.54.4: quickstarts/cloudflare, results-vite.json. With wranglerConfigPath and the options file in place the variant matched the hand-written withSentry baseline on all ten integrations.
