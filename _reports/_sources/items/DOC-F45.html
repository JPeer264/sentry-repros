Document server route naming for Nuxt on Cloudflare Workers

Description

The combination is documented. docs/platforms/javascript/guides/cloudflare/frameworks/nuxt.mdx:1-11 is a "Nuxt on Cloudflare" page that names Nitro's cloudflare_module preset at :6 and pulls in the shared include at :8-11. The Cloudflare branch of that include is platform-includes/getting-started-complete/javascript.nuxt.mdx:255-316: the wrangler config at :259-262, the warning to delete an existing sentry.server.config.ts at :270-273, the sentryCloudflareNitroPlugin server plugin at :280-287 and the nitroApp variant at :300-310. What no page describes is how the request span is named on Cloudflare: grep -rn -i "route name|segment name" guides/cloudflare/ platform-includes/getting-started-complete/javascript.nuxt.mdx returns zero hits.

Verified on the develop line: Nuxt 4.2 with the cloudflare_module preset, compatibility_date: "2026-05-01", compatibility_flags: ["nodejs_compat"], and server/plugins/sentry.ts registering sentryCloudflareNitroPlugin from @sentry/nuxt/module/plugins. Six of seven capabilities worked with that wiring, with no bundler plugin and no extra Sentry step, but two nuxt.config.ts settings that no page mentions were needed to get there: nitro.cloudflare: { nodeCompat: true, deployConfig: false }, and nitro.alias: { 'readable-stream': 'node:stream' } for the bundled mysql driver to boot under unenv. Install only @sentry/nuxt and @sentry/cloudflare: adding @sentry/nitro pulls nitro@3 in next to Nuxt 4's nitropack. Verification has to run on a build, since the SDK is inert under nuxt dev (orchestrion is skipped in dev and there is no workerd): nuxt build, then wrangler dev.

Works today:

  • Unhandled server route errors through Nitro's error hook, parameterized route names for routes such as server/api/users/[id].ts (GET /api/users/:id, source route, with http.route), per-request isolation, incoming trace continuation, outgoing fetch spans with propagation headers, db spans with no manual bundler step, Sentry.logger logs.

Known limits:

  • A server route with no parameters gets no http.route attribute, so its span is named by HTTP method alone under the default traceLifecycle: 'stream' and from the request URL, with source url, under 'static'. Parameterized routes such as server/api/users/[id].ts are unaffected.
  • Nothing is reported under nuxt dev at all; the instrumentation exists only in a built Worker.

What to change on docs/platforms/javascript/guides/cloudflare/frameworks/nuxt.mdx:

  • Replace the bare include passthrough with a page that keeps the include and adds a "Server Route Names" section stating the parameterless-route limit above, in both trace lifecycles.
  • Note that database spans need no extra Sentry configuration on the Cloudflare presets, and give the two Nitro settings they do need: nitro.cloudflare: { nodeCompat: true, deployConfig: false } and, for the mysql driver, nitro.alias: { 'readable-stream': 'node:stream' }.
  • Show the ship-today fix for parameterless routes in the same section: a second Nitro plugin, registered next to the Sentry one, that hooks beforeResponse, reads event.context.matchedRoute.path and sets http.route on the root span (Sentry.getRootSpan(Sentry.getActiveSpan()) from @sentry/cloudflare) when it carries none.

The documented wiring is correct as far as it goes: six of seven capabilities worked with it, once two undocumented nuxt.config.ts settings were added. The missing piece is server route naming: only routes carrying parameters, such as `/api/users/[id]`, are reported under their route pattern. A parameterless server route such as `/api/health` is reported as bare `GET` under the default `traceLifecycle: 'stream'`, and as the full request URL under `traceLifecycle: 'static'` — in both cases with a URL-derived name rather than the Nitro route pattern. The page must state this limitation and show the ship-today fix: a second Nitro server plugin registered next to the Sentry one, using only public `@sentry/cloudflare` exports (`getActiveSpan`, `getRootSpan`), that hooks `beforeResponse`, reads `event.context.matchedRoute.path` and sets `http.route` on the root span when it has none. On the SDK side the cause is one gate: `updateRouteBeforeResponse` only applies the route when the matched path differs from the request path, and dropping that comparison in a local build gave every route a route-sourced name with no regression on parameterized routes. Two more things the docs never mention were required to run at all: `nitro.cloudflare: { nodeCompat: true, deployConfig: false }` and, for the bundled mysql driver, `nitro.alias: { 'readable-stream': 'node:stream' }`; database spans need no extra Sentry configuration, but they do need those. The SDK is also inert under `nuxt dev`, so a reader verifying the setup must build and run wrangler.
