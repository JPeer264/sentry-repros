DOC-F27Next.js on Deno: documented noP1proven

Proposed issue new-page

Add a Next.js on Deno page and document enableRuntimeChannelInjection

Description

grep -rniE "deno" docs/platforms/javascript/guides/nextjs/ returns zero hits across every subtree, and the reverse grep over guides/deno/ returns zero for Next.js. docs/platforms/javascript/guides/nextjs/index.mdx:4-9 declares sdk: sentry.javascript.nextjs with category server-node. grep -rn "enableRuntimeChannelInjection" docs/ returns nothing repo-wide, so the option that makes this combination work is undocumented; docs/platforms/javascript/common/configuration/options.mdx:755 is where the neighbouring traceLifecycle option lives.

Verified on Next.js 15.5.4 App Router and Deno 2.9.0: deno.json with {"nodeModulesDir": "manual"}, build and start with deno run -A node_modules/next/dist/bin/next build and ... next start, the standard root instrumentation.js and sentry.server.config.js. Two deviations are required: set enableRuntimeChannelInjection: false in Sentry.init(), and add integrations: [winterCGFetchIntegration()] from @sentry/vercel-edge, which is already installed with @sentry/nextjs. Keep the default webpack builder: the build-time instrumentation that carries part of the database story needs it.

Works today:

  • Route handler errors, mechanism auto.function.nextjs.route_handler.
  • GET /users/[id] with source route, plus nested Next.js spans.
  • Per-request isolation and incoming trace continuation.
  • Outgoing http.client spans with sentry-trace/baggage, via winterCGFetchIntegration().
  • Database spans for drivers with native diagnostics channels (mysql2 >= 3.11, ioredis >= 5.11), plus drivers Sentry bundles and transforms at build time (ioredis below 5.11), as long as the app builds with webpack and keeps buildTimeInstrumentation on.
  • Logs.

Known limits:

  • Without enableRuntimeChannelInjection: false, every request returns 500 with SyntaxError: Unexpected token ':', because Deno cannot require() a .json file while the module hook is installed (denoland/deno#36240).
  • With it set, drivers that depend on that runtime hook produce no spans. mysql 2.x and pg stay in Sentry's default server-external packages, and only ioredis is on the list that gets un-externalized for build-time instrumentation, so there is no config knob that rescues them: forcing mysql 2.x to be bundled does produce the span but corrupts the driver, on Node as well as on Deno.
  • Passing --turbopack on Next 15, or setting buildTimeInstrumentation: false, removes the build-time path and with it the ioredis spans.
  • Error events carry no source context lines.
  • contexts.runtime reports { name: "node" } on Deno, so a Deno-hosted Next.js app is indistinguishable from a Node one in Sentry.

What to change:

  • Add docs/platforms/javascript/guides/deno/frameworks/nextjs.mdx.
  • Document enableRuntimeChannelInjection in common/configuration/options.mdx near :755.

A Next.js-on-Deno page must exist. It must state that Next.js 15 App Router builds and serves on Deno 2.9 with `deno run -A node_modules/next/dist/bin/next build` and `... next start`, with `deno.json` `{"nodeModulesDir": "manual"}`, and then give the two deviations from the standard Next.js wiring, both of which are currently undocumented. (1) `enableRuntimeChannelInjection: false` must be set in `Sentry.init()` in `sentry.server.config.js` or every request 500s with `SyntaxError: Unexpected token ':'` — Deno cannot run the diagnostics-channel module hook because `require()` of a `.json` file throws (denoland/deno#36240; a pass-through `Module.registerHooks` with no Sentry in the process fails the same way). The page must document this option, which does not appear anywhere in the docs today. With it set, the database story is three-way and the page must say so: packages that ship their own `diagnostics_channel` are instrumented (mysql2 >= 3.11, ioredis >= 5.11); packages Sentry un-externalizes and transforms during the build are instrumented too, which today means ioredis below 5.11 and requires the webpack builder, so no `--turbopack` on Next 15 and no `buildTimeInstrumentation: false`; and drivers that stay in Sentry's server-external packages, mysql 2.x and pg among them, record nothing, because the runtime hook they would need is exactly the one that must stay off. That last group has no workaround — forcing mysql 2.x into the bundle produces the span and then breaks the driver on Node too — so the page should name the boundary instead of implying a missing setting. (2) Outgoing global `fetch()` produces no `http.client` span and no `sentry-trace`/`baggage` headers, because the Node SDK's HTTP client instrumentation only sees `node:http`/undici; the verified fix needs no extra install — add `integrations: [winterCGFetchIntegration()]` from `@sentry/vercel-edge` (already a dependency of `@sentry/nextjs`) to `Sentry.init()` in `sentry.server.config.js`, which restores both the span and the propagation headers. Errors, route names, isolation, incoming trace continuation and logs all work with no further caveat; one cosmetic caveat is worth a line, that `contexts.runtime` says `node` on Deno, so these events cannot be told apart from Node ones in the UI.

Where the docs stand: `grep -rniE "deno" docs/platforms/javascript/guides/nextjs/` returns 0 hits across all subtrees (index.mdx, manual-setup.mdx, configuration/, tracing/, logs/, profiling/, capturing-errors/, best-practices/), and the reverse `grep -rniE "next\.?js" docs/platforms/javascript/guides/deno/` also returns 0; docs/platforms/javascript/guides/nextjs/index.mdx:4-9 declares `sdk: sentry.javascript.nextjs` with category `server-node`; `grep -rn "enableRuntimeChannelInjection" docs/` returns nothing repo-wide, so the option every Next.js-on-Deno app needs is undocumented; the neighbouring `traceLifecycle` SdkOption sits at common/configuration/options.mdx:755
