Document TanStack Start on Bun: verified setup and its limits

Description

None of the 11 files under docs/platforms/javascript/guides/tanstackstart-react/ contains the string "bun". tanstackstart-react/index.mdx:5-9 declares categories: [javascript, server, server-node, browser], the guide is flagged Beta at manual-setup/index.mdx:17, the single documented start command is node --import ./.output/server/instrument.server.mjs .output/server/index.mjs (manual-setup/index.mdx:358), and the only non-Node runtime named anywhere is Cloudflare, as an exclusion (manual-setup/index.mdx:377).

Verified on TanStack Start (React) 1.168.35 with the Nitro node-server preset and @sentry/tanstackstart-react 10.67.0 (develop, 6f2da7483d) on Bun 1.4.0: the documented wiring builds and runs on Bun as it stands — sentryTanstackStart() from @sentry/tanstackstart-react/vite last in the Vite plugin list (manual-setup/index.mdx:220-241), sentryGlobalRequestMiddleware and sentryGlobalFunctionMiddleware in createStart() in src/start.ts (manual-setup/index.mdx:416-438), and wrapFetchWithSentry on the server entry. No globalThis shim around @sentry/tanstackstart-react is needed; a module-scope database import builds fine. Start with bun --preload ./.output/server/instrument.server.mjs .output/server/index.mjs. Database spans additionally need a workaround for a Bun bug — Bun garbage-collects the node:diagnostics_channel objects the SDK subscribed to, so the subscriptions are gone shortly after startup. Pin them in instrument.server.mjs after Sentry.init: globalThis.__sentryKeepChannelsAlive = ['orchestrion:mysql:query', 'orchestrion:mysql2:query', 'orchestrion:mysql2:execute'].map(name => diagnosticsChannel.tracingChannel(name));. Patching dc.tracingChannel from the preload does not work, so the channel names have to be listed. Use the stream lifecycle for this: under static each database span arrives as its own transaction.

Works today:

  • Unhandled errors from server.handlers routes, with wrapFetchWithSentry on the server entry
  • Sentry.logger log envelopes
  • mysql database spans, with the channel pin above: the same build gave ["middleware globalRequestMiddleware"] without it and ["middleware globalRequestMiddleware", "db SELECT", "db SELECT users"] with it

Known limits:

  • Per-request isolation is recorded broken: three concurrent requests plus a sentinel all carried the tags of the last request and one identical trace id. A process-global isolation scope leaks tags, and would leak user data, between requests with no error anywhere.
  • Incoming sentry-trace/baggage is recorded broken: the headers were ignored and the event kept the process trace id.
  • Outgoing fetch spans are recorded broken with the wiring above.
  • Parameterized route names such as GET /api/user/$id were not produced by the recorded runs.
  • Browser-side capture was not exercised, and contexts.runtime reports node under Bun.
  • Follow-up runs for those four capabilities were carried out with bunHttpServerIntegration() from @sentry/bun added to Sentry.init, and their results were never recorded, so none of the four is stated here as fixed. Their raw output is suggestive, showing an http.client span with populated propagation headers under GET /api/fetch and a root span named GET /api/user/$id from the Vite plugin's inlined route patterns, but it comes from a different app shape and needs one recorded run before a page can promise it.

What to change:

  • tanstackstart-react/manual-setup/index.mdx: add a Bun section giving bun --preload ./instrument.server.mjs .output/server/index.mjs next to the command at :358, the channel pin with its stream-lifecycle note, and the limits above.
  • State on that page that the "No available Node API to register diagnostics-channel injection hooks" warning Bun prints is a false alarm once the Vite plugin has done the build-time injection, so it should not be read as an error.

The page must be equally plain about what is recorded broken on Bun and not promise it: per-request isolation (a process-global isolation scope, so tags and user data leak between concurrent requests with no error), incoming `sentry-trace`/`baggage` continuation, outgoing-`fetch` spans, and parameterized route names such as `GET /api/user/$id`. Follow-up runs that added `bunHttpServerIntegration()` from `@sentry/bun` look like they fix all four, but none of those runs has a recorded result, so the page cannot claim them yet.
