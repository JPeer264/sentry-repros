Document TanStack Start on Bun: verified setup and its limits

Description

None of the 11 files under docs/platforms/javascript/guides/tanstackstart-react/ contains the string "bun". tanstackstart-react/index.mdx:5-9 declares categories: [javascript, server, server-node, browser], the single documented start command is node --import ./.output/server/instrument.server.mjs .output/server/index.mjs (manual-setup/index.mdx:372), and the only non-Node runtime named anywhere is Cloudflare, as an exclusion (manual-setup/index.mdx:391).

Verified on TanStack Start (React) 1.168.35 with the Nitro node-server preset and @sentry/tanstackstart-react 10.67.0 on Bun 1.4.0: keep @sentry/* and @opentelemetry/* external in the server build via build.rollupOptions.external in vite.config.ts, wrap the server entry with wrapFetchWithSentry, install @sentry/bun at the same version and pass integrations: [fetchIntegration(), bunHttpServerIntegration()] to Sentry.init in instrument.server.mjs, guarded on typeof globalThis.Bun !== 'undefined', then start with bun --preload ./instrument.server.mjs .output/server/index.mjs.

Works today:

  • Unhandled errors from server.handlers routes, with wrapFetchWithSentry on the server entry
  • Per-request isolation, one scope and one trace per request
  • Incoming sentry-trace/baggage continuation
  • Outgoing fetch spans with propagation headers
  • Sentry.logger log envelopes

Known limits:

  • Parameterized route names such as GET /api/user/$id are not produced on Bun.
  • Database spans are not recorded on Bun.
  • Without bunHttpServerIntegration() no transaction or span is recorded at all and every request shares one process-wide trace.
  • Browser-side capture was not exercised.

What to change:

  • tanstackstart-react/manual-setup/index.mdx: add a Bun section giving bun --preload ./instrument.server.mjs .output/server/index.mjs next to the command at :372, the two @sentry/bun integrations with the runtime guard, the Vite externals, and the limits above.

Source: runtime docs audit, item DOC-F15, cell M-tanstack-bun

Page: docs/platforms/javascript/guides/bun/frameworks/tanstackstart-react.mdx (new)

A page must say TanStack Start (React) 1.168.35 on the nitro 3 node-server preset runs on Bun 1.4.0 as `bun .output/server/index.mjs`, and give the Bun equivalent of the sole documented start command: `bun --preload ./instrument.server.mjs .output/server/index.mjs`. It must state that with the documented wiring alone the SDK instruments nothing on Bun — no transaction or span at all, so route names such as `GET /api/user/$id` never appear, there is no request isolation, no incoming trace continuation and no outgoing `fetch` span — because Bun does not emit the `http.server.request.start` diagnostics channel the Node SDK relies on. The four fixes must be documented: install `@sentry/bun` at the same version and pass `integrations: [fetchIntegration(), bunHttpServerIntegration()]` to `Sentry.init` in `instrument.server.mjs`, guarded on `typeof globalThis.Bun !== 'undefined'`; wrap the handler call in the server entry with `Sentry.withIsolationScope(() => handler.fetch(request))` on Bun only (on Node the extra fork hides request tags); add a first `vite.config.ts` plugin keeping `@sentry/*` external in the nitro server build, without which `vite build` dies with "Cannot read properties of null (reading 'getVariableForExportName')"; and pin each driver's orchestrion tracing channel in a preload module, since Bun's GC drops the SDK's diagnostics-channel subscriptions and db, cache and AI spans stop being recorded shortly after startup.

Where the docs stand: ~/dev/sentry-docs/docs/platforms/javascript/guides/tanstackstart-react/index.mdx:5-9 (`categories: [javascript, server, server-node, browser]`); ~/dev/sentry-docs/docs/platforms/javascript/guides/tanstackstart-react/manual-setup/index.mdx:372 (the single documented start command, `node --import ./.output/server/instrument.server.mjs .output/server/index.mjs`); manual-setup/index.mdx:391 ("This setup doesn't work for Cloudflare deployments." — the only non-Node runtime named anywhere in the guide).
