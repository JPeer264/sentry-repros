Proposed issue docs-change

Document that errors inside ctx.waitUntil() are not captured

Description

The Cloudflare guide's waitUntil() section at docs/platforms/javascript/guides/cloudflare/index.mdx:376-424 is titled "Spans in waitUntil()" and covers span capture only: the static lifecycle snapshotting the transaction at :382, traceLifecycle: "stream" at :384-386, and forceTransaction: true at :388. Errors are never mentioned, and the sample at :393-420 shows deferred work with no note about failure.

An error thrown or a promise rejected inside ctx.waitUntil(promise) is not captured. The SDK's waitUntil handling is flush and invocation bookkeeping: packages/cloudflare/src/client.ts:285 hands the promise to the invocation's waitUntil and nothing else, and captureException has no occurrence in packages/cloudflare/src/flush.ts. There is no error-capture path on that plumbing, on either trace lifecycle.

The fix belongs in the app, so the page can show it: ctx.waitUntil(work().catch((e) => Sentry.captureException(e)));.

What to change

  • Add a sentence stating that errors thrown or rejected inside ctx.waitUntil() are not captured, on either trace lifecycle.
  • Show the app-side fix, ctx.waitUntil(work().catch((e) => Sentry.captureException(e)));, next to the existing sample.
  • Retitle the section so it does not read as complete waitUntil coverage.

Confirmed for Pages on 2026-09-09: context.waitUntil(Promise.reject(new Error(...))) in a Pages function was not captured, workerd logged Uncaught Error and only the request segment arrived; the section shows Worker code only (QS-cloudflare-pages, variant base).

Status quo. docs/platforms/javascript/guides/cloudflare/index.mdx:376-424 is titled "Spans in `waitUntil()`" and discusses only span capture: the static lifecycle snapshotting the transaction (:382), `traceLifecycle: "stream"` (:384-386) and `forceTransaction: true` (:388), with the sample at :393-420. Errors are not mentioned anywhere in the section.

On develop. packages/cloudflare/src/client.ts:285 (`_registerWithInvocationWaitUntil`, identical at the pin and on develop) only hands the promise to the invocation's `waitUntil`, and `captureException` has zero occurrences in packages/cloudflare/src/flush.ts, so no error-capture path is attached to that plumbing at all — an argument that does not depend on the trace lifecycle. The recorded error evidence is stream lifecycle only: probes/C01 (`/waituntil-throw` and `/waituntil-reject` produce a workerd "Uncaught Error" log and nothing in the sink before the sentinel) and quickstarts/cloudflare/results-waituntil.json (`ctx.waitUntil(Promise.reject(...))`, only the sentinel event arrives). C14 exercises both lifecycles, but for spans, not errors.

Work item. Add a sentence to the section stating that errors thrown or rejected inside `ctx.waitUntil()` are not captured, show the app-side fix `ctx.waitUntil(work().catch((e) => Sentry.captureException(e)));`, and rename the heading so it does not read as full waitUntil coverage. SDK side, C01 and C10 both record that the request span for a throwing request ends with `status: ok` and no `http.response.status_code`, which is a separate defect.
