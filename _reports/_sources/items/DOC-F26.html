DOC-F26NestJS on Deno: documented noP1proven

Proposed issue new-page

Add a NestJS on Deno page with its route-name and fetch limits

Description

No page covers NestJS on Deno. docs/platforms/javascript/guides/nestjs/index.mdx:1-9 declares sdk: sentry.javascript.nestjs, fallbackGuide: javascript.node and category server-node, and grep -rni deno docs/platforms/javascript/guides/nestjs/ returns zero hits. docs/platforms/javascript/guides/deno/index.mdx:1-232 is a beta-flagged manual-setup page for @sentry/deno (Alert at :12-16) that names no framework.

Verified on NestJS 10 (@nestjs/core with @nestjs/platform-express) and @sentry/nestjs 10.67.0 on Deno 2.9.0: install the Sentry packages in a single npm install into a real on-disk node_modules, set deno.json to {"nodeModulesDir": "manual"} with experimentalDecorators and emitDecoratorMetadata in compilerOptions, keep the standard instrument file that calls Sentry.init({ dsn, tracesSampleRate: 1.0 }) from @sentry/nestjs first, and register SentryGlobalFilter as APP_FILTER alongside SentryModule.forRoot(). @sentry/deno is neither used nor needed.

Works today:

  • Handler errors, mechanism auto.http.nestjs.global_filter, linked to the request transaction.
  • Per-request isolation across concurrent requests, with distinct trace ids.
  • Incoming sentry-trace/baggage continuation.
  • Database spans for mysql2, which ships its own diagnostics channels, with no hook and no bundler plugin.
  • Logs.

Known limits:

  • Transaction names are not parameterized on Deno: /users/42 reports GET /users/42 with source url, and under span streaming the span is GET with no source attribute. The route pattern never appears.
  • Without SentryGlobalFilter as APP_FILTER, Nest swallows the error and only the failed transaction arrives.
  • Outgoing fetch() is not instrumented: no http.client span and no sentry-trace/baggage headers. node:http requests are traced and propagated.

What to change:

  • Add docs/platforms/javascript/guides/deno/frameworks/nestjs.mdx with the install, deno.json, init and filter wiring, and a "Known limitations on Deno" section listing the two limits above.

Source: runtime docs audit, item DOC-F26, cell M-nestjs-deno

Page: guides/deno/frameworks/nestjs.mdx (new), with an explicit "Known limitations on Deno" section listing unparameterized route names and uninstrumented global fetch

A NestJS-on-Deno page must exist. It must say NestJS 10 (`@nestjs/core` + `@nestjs/platform-express`) boots on Deno unchanged and that `@sentry/nestjs` works there, with these specifics: install the Sentry packages in a single `npm install` command into a real `node_modules` and set `deno.json` `{"nodeModulesDir": "manual"}`; error capture, per-request isolation, incoming trace continuation, database spans and logs all work. Two limitations must be stated plainly because neither has a workaround the reader can guess. (1) Route names are broken: transaction names are not parameterized on Deno, so `GET /users/123` is not collapsed to the route pattern — the page must say so rather than implying the Node behavior carries over. (2) Outgoing requests made with Deno's built-in global `fetch` are not traced by `@sentry/node` or any framework SDK built on it, including `@sentry/nestjs`: no `http.client` span and no `sentry-trace`/`baggage` headers, because that instrumentation listens on undici's diagnostics channels and Deno's native fetch publishes none of them. The page must ship the fix that was verified to cover both `fetch(url)` and `fetch(new Request(url))` on both trace lifecycles — a small integration built from public `@sentry/core` exports (`defineIntegration` + a headers/URL map + `instrumentFetchRequest`) passed to `Sentry.init` — and note `node:http` as the zero-integration alternative.

Where the docs stand: docs/platforms/javascript/guides/nestjs/index.mdx:1-9 declares `sdk: sentry.javascript.nestjs`, `fallbackGuide: javascript.node`, category `server-node`; `grep -rni deno docs/platforms/javascript/guides/nestjs/` returns 0 hits; docs/platforms/javascript/guides/deno/index.mdx:1-232 is a beta-flagged manual-setup page for `@sentry/deno` (beta Alert at :12-16) that names no framework at all

What ran: NestJS 10 (@nestjs/core + @nestjs/platform-express) with @sentry/nestjs 10.67.0 (develop / v11 line) on Deno 2.9.0 (aarch64-apple-darwin), npm compat, nodeModulesDir "manual". Cell record.
