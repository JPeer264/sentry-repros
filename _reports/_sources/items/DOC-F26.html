Proposed issue new-page

Add a NestJS on Deno page: the boot workaround decides what you get

Description

No page covers NestJS on Deno. docs/platforms/javascript/guides/nestjs/index.mdx:1-9 declares sdk: sentry.javascript.nestjs, fallbackGuide: javascript.node and category server-node, and grep -rni deno docs/platforms/javascript/guides/nestjs/ returns zero hits. docs/platforms/javascript/guides/deno/index.mdx:1-230 is a beta-flagged manual-setup page for @sentry/deno (Alert at :12-16) that names no framework.

Verified on NestJS 10 (@nestjs/core with @nestjs/platform-express, and re-run on @nestjs/platform-fastify) and @sentry/nestjs 10.67.0 on Deno 2.9.0: install the Sentry packages in a single npm install into a real on-disk node_modules, set deno.json to {"nodeModulesDir": "manual"} with experimentalDecorators and emitDecoratorMetadata in compilerOptions, keep the standard instrument file that calls Sentry.init({ dsn, tracesSampleRate: 1.0 }) from @sentry/nestjs first, and register SentryGlobalFilter as APP_FILTER alongside SentryModule.forRoot(). @sentry/deno is neither used nor needed. One more line is mandatory, or the app does not boot on Deno, and the choice decides how much you get. Either add a six-line Module.registerHooks({ load(url, context, nextLoad) { const result = nextLoad(url, context); return url.endsWith(".json") ? { ...result, format: "json" } : result; } }) from node:module in the instrument file, before the @sentry/nestjs import or right after Sentry.init() (both orders verified), and leave the SDK's diagnostics-channel injection on. Or turn the injection off with enableRuntimeChannelInjection: false in Sentry.init, the public option for it, which the Next.js-on-Deno run used on the same runtime.

Works today:

  • Handler errors, mechanism auto.http.nestjs.global_filter, linked to the request transaction.
  • With the JSON load hook and injection left on: GET /users/:id with source route and http.route set, plus express middleware, handler and function AppController.getUser spans, on @nestjs/platform-express and on @nestjs/platform-fastify, in both trace lifecycles.
  • Per-request isolation across concurrent requests, with distinct trace ids.
  • Incoming sentry-trace/baggage continuation.
  • Database spans for mysql2, which ships its own diagnostics channels, with no hook and no bundler plugin.
  • Logs.

Known limits:

  • With injection off, transaction names are not parameterized: /users/42 reports GET /users/42 with source url, under span streaming the span is GET with no source attribute, and there are no express or nest middleware, handler or function spans.
  • With injection on and no JSON load hook, the app does not start: Sentry.init registers module hooks on Deno unconditionally, Deno then compiles every require('*.json') as JavaScript (denoland/deno#36240), and Nest fails with "No driver (HTTP) has been selected" on platform-express and SyntaxError: Unexpected token ':' on platform-fastify.
  • With injection off, only drivers that publish their own diagnostics channels are instrumented; anything that needs the injected channels stays dark.
  • Without SentryGlobalFilter as APP_FILTER, Nest swallows the error and only the failed transaction arrives. SentryModule.forRoot() registers APP_INTERCEPTOR only.
  • Outgoing fetch() is not instrumented: no http.client span and no sentry-trace/baggage headers, because that instrumentation listens on undici's diagnostics channels and Deno's native fetch publishes none. node:http requests are traced and propagated.
  • On Deno the SDK logs "@sentry/server-runtime-injection was bundled into your application" for an app that is not bundled, so that line is no signal of a misconfiguration.

What to change:

  • Add docs/platforms/javascript/guides/deno/frameworks/nestjs.mdx with the install, deno.json, init and filter wiring, both boot options with what each one costs, and a "Known limitations on Deno" section.

Page: guides/deno/frameworks/nestjs.mdx (new), leading with the boot workaround and with an explicit "Known limitations on Deno" section

A NestJS-on-Deno page must exist. It must say NestJS 10 (`@nestjs/core` + `@nestjs/platform-express`) boots on Deno unchanged and that `@sentry/nestjs` works there, with these specifics: install the Sentry packages in a single `npm install` command into a real `node_modules` and set `deno.json` `{"nodeModulesDir": "manual"}` with the decorator compiler options. The first thing the page has to give the reader is the boot workaround, because the documented instrument file does not start on Deno: `Sentry.init` always installs its diagnostics-channel injection there, and with any module hook registered Deno compiles `require('*.json')` as JavaScript (denoland/deno#36240), which is fatal for Nest — express reports "No driver (HTTP) has been selected", fastify throws `SyntaxError: Unexpected token ':'`. Two levers exist and they are not equivalent. Registering a six-line compensating `Module.registerHooks({ load })` that restores `format: 'json'` keeps the injection on, and then Deno behaves like Node: `GET /users/:id` with source `route`, express/nest middleware, handler and function spans, and `auto.http.nestjs.global_filter` error events, on both HTTP adapters and in both trace lifecycles. Setting `enableRuntimeChannelInjection: false` also boots the app, and is the public option for what the run used, but it buys the plain shape: names stay `GET /users/42` with source `url`, there are no framework spans, and only drivers with their own diagnostics channels (mysql2 among them) are traced. The page must state both branches, since a reader who takes the simpler lever will otherwise read the missing route names as a bug. Error capture also needs `{ provide: APP_FILTER, useClass: SentryGlobalFilter }` next to `SentryModule.forRoot()`, which registers only `APP_INTERCEPTOR`; without it every handler throw is swallowed. Two facts belong in the limitations section: outgoing requests made with Deno's global `fetch` are not traced by `@sentry/node` or any framework SDK built on it, so there is no `http.client` span and no `sentry-trace`/`baggage` header (use a `node:http` client if you need propagation), and the SDK's "was bundled into your application" warning fires on Deno for apps that are not bundled. SDK-side, the Deno branch of `hasStableSyncModuleHooks()` returning true unconditionally is what turns a Deno runtime bug into an unbootable app, and a fetch integration in the Node SDK for runtimes without undici channels would close the second gap.

Where the docs stand: docs/platforms/javascript/guides/nestjs/index.mdx:1-9 declares `sdk: sentry.javascript.nestjs`, `fallbackGuide: javascript.node`, category `server-node`; `grep -rni deno docs/platforms/javascript/guides/nestjs/` returns 0 hits; `grep -rn enableRuntimeChannelInjection docs/ platform-includes/` returns 0 hits, so the option the page needs is itself undocumented; docs/platforms/javascript/guides/deno/index.mdx:1-230 is a beta-flagged manual-setup page for `@sentry/deno` (beta Alert at :12-16) that names no framework at all
