Description

docs/platforms/javascript/guides/cloudflare/frameworks/remix.mdx is 60 lines and does not describe a working Workers setup: :39-49 installs only @sentry/remix with no @sentry/cloudflare, and :55-58 embeds the shared include. In that include, the Cloudflare branch at platform-includes/getting-started-complete/javascript.remix.mdx:263-313 covers Cloudflare Pages only, and the "Capture Server-Side Errors" step at :315-347 sits outside any PlatformSection and tells every reader to import from bare @sentry/remix at :333. Separately, guides/cloudflare/features/vite-plugin.mdx:30-47 presents _experimental.useDiagnosticsChannelInjection as required.

Verified on the develop line: Remix v2 (2.17.5) with the Remix Vite plugin on workerd, compatibility_date: "2026-05-01", compatibility_flags: ["nodejs_compat"]. Install @sentry/remix and @sentry/cloudflare. In app/entry.server.tsx, export const handleError = sentryHandleError imported from @sentry/remix/cloudflare. In the worker entry, Sentry.withSentry() from @sentry/cloudflare around a handler built with createRequestHandler(instrumentBuild(remixBuild)). In vite.config.ts, sentryCloudflareVitePlugin() from @sentry/cloudflare/vite at its defaults alongside the Remix plugin, with ssr: { target: 'webworker', noExternal: true }.

Works today:

  • Loader, action and resource-route errors, parameterized route names with http.route, per-request isolation, incoming trace continuation, outgoing fetch spans with propagation headers, db spans from mysql, Sentry.logger logs.

Known limits:

  • Importing from bare @sentry/remix in a webworker SSR build leaves handleError undefined and captures nothing.
  • A route with no loader or action stays method-only.
  • Without sentryCloudflareVitePlugin() there are no database spans and no warning; mysql2 is unusable on workerd.

What to change:

  • Rewrite guides/cloudflare/frameworks/remix.mdx: add @sentry/cloudflare to the install at :39-49, add a Workers entry section, point handleError at @sentry/remix/cloudflare, and add a database-spans section.
  • Correct guides/cloudflare/features/vite-plugin.mdx:30-47 to the shipped buildTimeInstrumentation and autoInstrumentation options, both defaulting to true.

The page contradicts the run on three points and must be rewritten for Workers. (1) Error capture: on Cloudflare Workers and Pages the `handleError` import must come from `@sentry/remix/cloudflare`, never bare `@sentry/remix` — the bare specifier silently captures nothing in a `webworker` SSR build. Both `export const handleError = sentryHandleError` and `wrapHandleErrorWithSentry` work from that subpath, on both trace lifecycles, for loaders, actions, resource routes and thrown 5xx Responses. (2) Request isolation: the worker entry must be wrapped with `withSentry` from `@sentry/cloudflare` around a handler built with `instrumentBuild` from `@sentry/remix/cloudflare`. `wrapRequestHandler` from `@sentry/cloudflare/request` exists only for runtimes that cannot enable `nodejs_compat` (Shopify Oxygen); on Workers it does not establish isolation unless `setAsyncLocalStorageAsyncContextStrategy` is called first. (3) Database spans require the build-time transform: add `sentryCloudflareVitePlugin()` to the Vite config alongside the Remix plugin — defaults are sufficient, `autoInstrumentation: false` is unnecessary, and the connection may sit at module scope or inside the loader — and set `ssr: { target: 'webworker', noExternal: true }`. Without the plugin, queries run normally, no `db` span appears, and the SDK logs no warning. The `_experimental.useDiagnosticsChannelInjection: true` requirement stated on the Vite plugin page is no longer needed on the v11 line and must be corrected there too. Finally, the page must also install `@sentry/cloudflare`, not just `@sentry/remix`.
