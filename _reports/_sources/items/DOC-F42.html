DOC-F42Fresh on Cloudflare: documented noP1proven

Proposed issue new-page

Add a Fresh 2 on Cloudflare Workers page with the esbuild orchestrion build step

Description

Fresh is absent from the docs. There is no guides/fresh/ directory, and the only "fresh" hits under docs/platforms/javascript/ are the ordinary English word (for example guides/cloudflare/agent-tracing/agents-sdk.mdx:43). The Cloudflare framework list at docs/platforms/javascript/guides/cloudflare/index.mdx:16-23 names Astro, Hono, Hydrogen, Next.js, Nuxt, Remix, SvelteKit and TanStack Start and nothing else.

Verified on the develop line: Fresh 2 on workerd with compatibility_date: "2026-05-01" and compatibility_flags: ["nodejs_compat"]. Fresh's own Vite plugin emits _fresh/server.js whose default export is already { fetch }, so no Cloudflare adapter is needed. Keep @sentry/cloudflare and any database driver out of the Fresh SSR bundle via environments.ssr.build.rollupOptions.external, then write a separate wrangler entry that wraps Fresh's server with Sentry.withSentry() from @sentry/cloudflare. For database spans, bundle that wrangler entry yourself with esbuild plus sentryOrchestrionPlugin() from @sentry/server-utils/orchestrion/esbuild, and point wrangler's main at the output. That esbuild build needs a banner defining a globalThis.require backed by static node:* imports, or workerd dies at the first query with "Dynamic require of 'diagnostics_channel' is not supported".

Route names take one middleware in main.ts, registered before app.fsRoutes(): in a finally around ctx.next(), call rootSpan.updateName(`${ctx.req.method} ${ctx.route}`), then rootSpan.setAttribute("http.route", ctx.route) and rootSpan.setAttribute(Sentry.SENTRY_SEGMENT_NAME_SOURCE, "route"), on Sentry.getRootSpan(Sentry.getActiveSpan()) from @sentry/cloudflare. The order matters: the source has to be set after the rename, because both span.updateName() and Sentry.updateSpanName() mark the name custom. The finally matters too, because Fresh's error boundary sits outside user middleware, so a throwing route would otherwise keep the unparameterized name.

Works today:

  • Per-request isolation, incoming trace continuation, outgoing fetch spans with propagation headers, Sentry.logger logs, and db spans through the esbuild orchestrion build.
  • Parameterized route names (GET /users/:id, source route) in both trace lifecycles, with the main.ts middleware above.

Known limits:

  • Nothing a route handler, middleware or page component throws reaches Sentry on its own: Fresh's default error handler catches it and returns a 500, leaving only the request span marked internal_error. Adding Sentry.captureConsoleIntegration({ levels: ["error"] }) to the withSentry options turns Fresh's own console.error(error) into an event, at the cost of reporting every other console.error.
  • Out of the box there are no route names: the request span is named from the URL (static) or the HTTP method alone (stream). Fresh does call getActiveSpan()?.updateName() and set http.route through @opentelemetry/api, but @sentry/cloudflare registers no OpenTelemetry global, so those calls land on a no-op tracer.
  • sentryCloudflareVitePlugin() does not belong in Fresh's vite.config.ts: there is no Cloudflare worker environment for it to instrument, and adding it there is worse than a no-op, it injects the channels and then breaks the driver under workerd through Vite's CJS interop (createRequire(import.meta.url) with unresolvable module ids).
  • mysql 2.x is the driver this ran on; mysql2 is instrumented but its query fails on workerd unless you pass disableEval: true, which this cell did not exercise.

What to change:

  • Add docs/platforms/javascript/guides/cloudflare/frameworks/fresh.mdx with the wiring above and link it from guides/cloudflare/index.mdx:16-23.
  • Add the missing-worker-environment caveat to guides/cloudflare/features/vite-plugin.mdx:13-18, stating that in a Vite build with no Cloudflare worker environment the plugin breaks bundled drivers rather than doing nothing.

Three things follow. Nothing a route handler, middleware or page component throws reaches Sentry on its own, because Fresh's default error handler catches it and returns a 500, leaving the request span marked internal_error; the init-only fix is the console-capture integration for the error level. Out of the box the request span is named by HTTP method only with source url, since Fresh renames through @opentelemetry/api and @sentry/cloudflare registers no OTel global, so the page must show the main.ts middleware registered before the file-system routes that renames the root span from ctx.route in a finally and then sets http.route and SENTRY_SEGMENT_NAME_SOURCE, in that order, because renaming forces the source to custom. Database spans must not come from putting the Sentry Cloudflare Vite plugin in Fresh's config: there is no worker environment for it to instrument, and it injects the channels and then breaks the driver under workerd; instead keep the SDK and the driver external to the SSR build and bundle the wrangler entry separately with the orchestrion esbuild plugin, with a require banner backed by static node: imports. Isolation, incoming trace, outgoing fetch and logs work unaided.
