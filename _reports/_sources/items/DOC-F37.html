DOC-F37Express on Cloudflare: documented noP1proven

Proposed issue new-page

Add an Express on Cloudflare Workers page built with the Sentry Cloudflare Vite plugin

Description

Nothing documents Express on Workers. docs/platforms/javascript/guides/express/index.mdx:4-9 pins sdk: sentry.javascript.node with fallbackGuide: javascript.node, and grepping the Express guide for "cloudflare" or "workerd" returns nothing. In the other direction, the Cloudflare framework list at docs/platforms/javascript/guides/cloudflare/index.mdx:16-23 has no Express entry and httpServerHandler, cloudflare:node and enable_nodejs_http_server_modules appear nowhere under docs/ or platform-includes/.

Verified on the develop line: Express 5 on workerd with compatibility_date: "2026-05-01" and compatibility_flags: ["nodejs_compat", "enable_nodejs_http_server_modules"], served through httpServerHandler from cloudflare:node and wrapped with Sentry.withSentry() from @sentry/cloudflare. Build the Worker with Vite: plugins: [cloudflare(), sentryCloudflareVitePlugin()] from @sentry/cloudflare/vite, then npx vite build && npx wrangler dev --config dist/<worker>/wrangler.json. Keep httpServerHandler({ port: 8080 }) at module scope but create the Express app and call app.listen() inside fetch, memoized on first request: with build-time instrumentation on, a module-scope app.get(...) kills the Worker at startup with "Disallowed operation called within global scope". On a plain wrangler build the same app needs two app-side lines instead: setupExpressErrorHandler(app) from @sentry/server-utils (an extra dependency, since @sentry/cloudflare does not re-export it, so the Sentry.setupExpressErrorHandler(app) form the Express guide shows is undefined in a Worker), and patchExpressModule(express, () => ({})) from @sentry/core/server before the app is built.

Works today:

  • Vite build: unhandled route errors (mechanism auto.http.express), parameterized route names with http.route, per-request isolation across await, incoming trace continuation, outgoing fetch spans with propagation headers, db spans from mysql2 or mysql 2.x nested under the Express handler span, Sentry.logger logs.
  • Plain wrangler build: isolation, incoming trace continuation, outgoing fetch spans and logs unaided; unhandled route errors after setupExpressErrorHandler(app) (mechanism auto.middleware.express); route names and handler/router spans after patchExpressModule(express, () => ({})).

Known limits:

  • A Worker bundled by plain wrangler dev/wrangler deploy gets no route names, no handler spans and no database spans unless you add app-side wiring: setupExpressErrorHandler(app) from @sentry/server-utils (not re-exported by @sentry/cloudflare) for error capture, and patchExpressModule(express, () => ({})) from @sentry/core/server for handler spans and route names, the latter only under the stream trace lifecycle and on a deprecated API.
  • Database spans have no plain-wrangler equivalent at all: the build-time instrumentation of the Vite plugin is what injects the channels, and a wrangler-bundled Worker emits none and logs no warning.
  • vite dev cannot start Express on workerd; build first, then run wrangler against the build output.
  • mysql2 on workerd needs disableEval: true in the connection options.

What to change:

  • Add docs/platforms/javascript/guides/cloudflare/frameworks/express.mdx with the wiring above and link it from guides/cloudflare/index.mdx:16-23.
  • Correct guides/cloudflare/features/vite-plugin.mdx to the shipped options buildTimeInstrumentation and autoInstrumentation, both defaulting to true: the prose at :30 that presents useDiagnosticsChannelInjection as something you must enable, the two snippets at :40-44 and :78-82, and the SdkOption blocks at :150-166 that document _experimental.autoInstrumentation and _experimental.useDiagnosticsChannelInjection as defaulting to false.

A page must say that Express 5 boots unchanged on workerd with the nodejs_compat and enable_nodejs_http_server_modules flags behind httpServerHandler from cloudflare:node, a path that is undocumented today. It must also say that the app has to be created inside fetch rather than at module scope, because with build-time instrumentation on a top-level app.get() fails the Worker with "Disallowed operation called within global scope". On the Vite build errors, route names, isolation, trace continuation, fetch spans, db spans and logs all arrive without further wiring. On a plain wrangler build two app-side lines close the gap: setupExpressErrorHandler(app), imported from @sentry/server-utils, which must be installed because @sentry/cloudflare does not re-export it, reports every route error as unhandled (mechanism auto.middleware.express), and patchExpressModule(express, () => ({})) from @sentry/core/server gives handler and router spans plus parameterized names, though only under the stream trace lifecycle and on an API the SDK marks deprecated. Database spans have no such fallback: they exist only when the Worker is built with Vite and the Sentry Cloudflare plugin; a wrangler-bundled Worker emits none and logs no warning, and vite dev cannot start Express on workerd.

Where the docs stand: guides/express/index.mdx:4-9 (sdk sentry.javascript.node, fallbackGuide javascript.node, server-node; body is one include at :12); guides/cloudflare/index.mdx:16-23 (framework list has no Express); grep for httpServerHandler, cloudflare:node and enable_nodejs_http_server_modules over docs and platform-includes returns zero hits, and the only patchExpressModule hits are the two migration notes at common/migration/v10-to-v11/index.mdx:748 and :1375, neither of which is about Workers; guides/cloudflare/features/vite-plugin.mdx:30, :40-44, :78-82 and :150-166 document the `_experimental` flags as off by default, contradicted by develop packages/cloudflare/src/vite/index.ts:37,60-68,87.
