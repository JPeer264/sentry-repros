Proposed issue docs-change

Rewrite the Fastify integration page around the diagnostics-channel instrumentation and its options

Description

common/configuration/integrations/fastify.mdx:21 says the integration captures spans using @opentelemetry/instrumentation-fastify; neither @sentry/node nor @sentry/server-utils depends on it, and the build subscribes to Fastify's fastify.initialization and tracing:fastify.request.handler:error diagnostics channels itself. The page (:3, :17-27) says the integration adds performance instrumentation and shows no option, while every error event in every working variant carries auto.function.fastify and the integration takes shouldHandleError with the default reply.statusCode >= 500 || reply.statusCode <= 299.

Two behaviours the page should name: on Fastify 4 the reply status is not yet set when the filter runs, so a thrown { statusCode: 404 } error is captured on 4.29.1 and dropped on 5.12.3; and Fastify 4 prints [FSTDEP017] DeprecationWarning once for an unrouted request, because the instrumentation falls back to request.routerPath. The span tree is also undocumented: a segment GET /users/:id, a request handler span and a route-handler span both named handler /users/:id, and one middleware span per instance hook named fastify - onRequest and the like.

What to change:

  • Replace the OpenTelemetry sentence with the diagnostics-channel mechanism, add the error capture, the shouldHandleError option and its default, the Fastify 4 status timing, the FSTDEP017 note and the span tree.
